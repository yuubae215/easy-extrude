# 一拍俯瞰 — 実装前に状態と同一性を先に出す (核 §2 / §1.4)

これから着手する作業「$ARGUMENTS」(引数が無ければ直前の依頼) について、**コードを一行も
書く前に**、以下を成果物として出すこと。憲法 (`CLAUDE.md` / `.claude/rules/`) の自己適用に
任せず、ここで明示的に問われるための入口である。

長い指示文を毎回打たなくて済むよう、この 1 コマンドが「狭く名指しした要求」の実体になっている。

## 出すもの (簡潔に。図は状態が 3 つ以上のときだけ)

### 1. Goal — 解ではなく性質

依頼が解の形 (「ここはキューで」「フラグを足して」) で来ていたら、一段持ち上げて
**欲しい性質**を言い直す (核 §1.2)。より安い解が許されるかもしれない。

### 2. 触る実体の状態表 — **基数を必ず含める**

`docs/STATE_LEDGER.md` を読み、触る実体の行を引く (無ければ新設する行を提示):

| 実体 | 状態集合 | 基数 (0 / 1 / N のどれが正当か) | 権威 (唯一の書き手) |

- **0 個が正当なら**「0 のとき何が起きるか」を書く。無言で既定値に落ちるのは禁止
  (PHILOSOPHY Yellow Card「必須入力の欠落に既定値を与えない」— 幽霊ロボットの先例)。
- **N 個が正当なら**「どれのことか」をどう指すかを書く。
- 累積して 3 状態以上、または不正遷移が事故になるなら、**クラスより先に**状態機械を設計し
  `docs/STATE_TRANSITIONS.md` に節を起こす。不正状態は型で表現不能にする。

### 3. 同一性の所有者

「この実体はどれか」を決める述語は**どこが 1 箇所で持つか**。既存の名前付き述語があれば
それを呼ぶ (例: `isRobotBaseFrame()`)。呼び出し側で `name === X && parentId === null` を
並べ直すのは 1 行でも第二の源 (§1.1)。新設するなら
`src/IdentityContainment.test.js` の `IDENTITY_RULES` に登録して機械に守らせる。

### 4. blast radius — 一言で

ここを変えたとき壊れうる到達可能ノード。即答できないなら、それ自体がトリガ (核 §3) —
依存グラフを起こしてから進む。

### 5. 検証の形 (§1.2 Evidence / Q3)

この変更が正しいことは**何で示すか**: test / type / bench / 実行結果のどれか。
そして新しく決めた規律があるなら「それは書く瞬間にどこで問われるか」— 散文でなく
テスト・CI ステップ・`.claude/hooks/` のいずれかに降ろす。

**選んだ証拠が構造的に見逃す変化を 1 行で宣言する。** 「通った」は *その形の証拠が
見える範囲で* 通ったにすぎない。とくに**入力が毎回変わる**証拠 (キー入力ごとに要求値が
動く数値操作など) は、1 フレーム古い状態を読む欠陥を隠す — **同じ要求を 2 回以上通す**形が
要るかを問う (ADR-098 の e2e は数値 Grab で書かれていたため緑のまま振動を出荷し、
ADR-101 で別途起票することになった)。逆向きも同じ問いの一部で、画面座標に依存しない形を
選んだこと自体が別の欠陥を露出させている (同 PR の `_setSnapMode`)。

### 6. ADR を起票するか

1〜5 の答えが「非自明・不可逆な設計選択を含む」なら ADR を起こす。その場合
**同じ PR で GSN 論証木も起こす (無条件)** — 規律の正本は adr skill
(`.claude/skills/adr/SKILL.md` §GSN 併設) にあるので、ここには写さない (核 §1.1)。

## 出したあと

ユーザーの合意を待ってから実装に入る。1〜5 のうち即答できない項があれば、
それを先に潰す (未成熟な判断は進めるのではなく欠落を表に出す — 核 §1.2)。
変更が局所・可逆・既知なら「reactive のまま進む」と明言して短く切り上げてよい (核 §3) —
このコマンドは重いレンズを常時起こすためのものではない。

## 完了時 — PR を作る (ループを証拠で閉じる, 核 §2 / §5)

実装が終わったら**指示を待たずに** commit → push → **PR を作成する**。
「done」は意図ではなく証拠で閉じるものなので (核 §5「証拠なき完了禁止」)、
PR 本文には上の 1〜6 の答えをそのまま載せる — レビュアが読むのは差分ではなく
**なぜその差分か**であり、それは既に俯瞰で出ている。書き直さずに持っていく:

- **Goal** (§1) — 解ではなく性質。何が成り立てば完了か。
- **状態表** (§2) — 触った実体の基数 (0/1/N) と権威。台帳 `docs/STATE_LEDGER.md` の
  行を同じ PR で更新済みであること。
- **同一性の所有者** (§3) — 新設した述語と、`IDENTITY_RULES` 等の登録先。
- **blast radius** (§4) — 触った到達可能ノードと、**触らなかったと宣言した**もの。
- **検証** (§5) — 実行したコマンドと**実際の結果**。落ちたもの・レーンが無くて
  検証できなかったものは隠さず書く (核 §2「再 Observe」— 通ったことにしない)。
- **ADR / GSN** (§6) — 起票したなら link、しなかったならその判断理由を 1 行。

俯瞰と PR が食い違ったら、食い違いのほうを本文に書く (実装で前提が変わるのは
正常。黙って俯瞰を書き換えると、判断の履歴が消える — 原則 #19)。

例外: ユーザーが「PR は作らないで」と明示した場合、および push 先ブランチが
指定されていない場合のみ。それ以外は確認を挟まず作ってよい。
