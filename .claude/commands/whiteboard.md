# 一拍俯瞰 — 実装前に状態と同一性を先に出す (核 §2 / §1.4)

これから着手する作業「$ARGUMENTS」(引数が無ければ直前の依頼) について、**コードを一行も
書く前に**、以下を成果物として出すこと (§0 の語彙から始める)。憲法 (`CLAUDE.md` / `.claude/rules/`) の自己適用に
任せず、ここで明示的に問われるための入口である。

長い指示文を毎回打たなくて済むよう、この 1 コマンドが「狭く名指しした要求」の実体になっている。

**呼ばれなくても出す場合:** ADR の段 (`S1b` / `M5b` / `PR2` …) の実装を頼まれたら、このコマンドが
打たれていなくても、実装の前にこれを出して合意を待つ (CLAUDE.md §ADR の段の実装)。**後から出しても
同じにはならない** — 先に出せば当事者が判断を変えられるが、後から出すと作ったものの説明になり、
§0 の「語彙は充足」も追認にしかならない (2026-10-24 — ADR-168 S1b を事後に出し、実装を取り消した)。

## 読み手のために書く — 出力の形 (2026-11-07 当事者)

俯瞰の読み手は当事者で、**リポジトリを見返さずに読んで判断できる**ことが成果物の条件である。
語の規律 (初出で言い換える・番号を主語にしない) と内部語の言い換え表は共通の正本
`.claude/READABLE-OUTPUT.md` に従う (ここに写さない)。俯瞰に固有の並びは次のとおり:

1. **要約 (3 行以内)** — 何をするか / いちばん大きいリスク / 決めてほしいことが何個あるか。
2. **決めてほしいこと** — 当事者が選ぶ判断だけを `Q1` `Q2` … で並べる。各 Q は
   「何を決めるか (1 文)」「選択肢」「推奨と理由 (1 文)」。無ければ「なし — 推奨どおり進められる」。
   §0〜§6 の中で出た判断はここへ引き上げ、本文側には `→ Q2` と書くだけにする (同じ判断を 2 か所に書かない)。
3. **§0〜§6** — 各節は下の見出しをそのまま使い、**見出しの直後に「この節に並ぶもの」を 1 行**書く
   (下の各節の引用行がその雛形)。表の列見出しも平易な言葉にしてある。

## 出すもの (簡潔に。図は状態が 3 つ以上のときだけ)

### 0. 言いたいことが、今ある言葉で言えるか (語彙の充足 — 原則 #33)

> この節に並ぶもの: 使う人が言いたい文 2〜3 個と、それぞれが今の言葉で言えるかどうか。

機構より先に、**使う人が言いたい文**を 2〜3 個書き出し (依頼文・当事者の言葉から拾う)、
それが今の語彙 (DSL / 契約 / 画面の語) で言えるかを問う。言えなければ、何が欠けているかを
次の 4 つで名指しする:

1. **1 語 1 事実** — 1 つの語が 2 つの事実を運んでいないか (運んでいれば割る)。
2. **束ねに名前** — いつも一緒に語られる事実の組に名前が在るか (N 個・順序はそこで言える)。
3. **関係にも語** — 束どうしの優先・代替・フォールバックを言う語が在るか
   (要素ごとの数値の優先度に散らさない)。
4. **語は指す先で確かめられるか** — その語が実物のどこを指すかを、走らせる前に見る手段が在るか。

| 言いたい文 | 今の言葉で言えるか | 足りないのは何か (上の 1〜4) | 足す語 / 2 つに割る語 |

**語彙が既に在るなら足さない** — 無いのは線だけで、語を足すと第二の源になる (ADR-129)。
全部の文が今の語で言えるなら「語彙は充足、線の問題」と 1 行書いて §1 へ進む
(出力では「言葉は足りている — 足りないのはつなぐコードだけ」と言い換える)。

**辞書を先に整備する — 設計・実装より前に** (当事者 2026-10-24: 「設計実装の前には、辞書を
整備してから進めるようにしてね。ごちゃごちゃするし」)。足す語・割る語が決まったら、
機構を書く前に次の 2 つを済ませる:

- **辞書の行** — その語の正規形と、人の言い方 (日本語・英語の同義語) を同義語辞書
  `QUOTIENT_TABLE` (`src/context/SynonymQuotient.js`) に置く。分類 (`cat`) と引き方
  (`CATEGORY_SCOPE` — 共有か分類内か) も宣言する。**既存の語と衝突しないか**は辞書の読み込みが
  問う (同じ引き方の中で 1 語が 2 つの鍵に落ちると throw)。衝突したら語を足す前に割り方を決める
  (先例: ADR-168 の `above` は比較演算子と衝突していた)。2 つの事実を言う語 (「上」「載っている」)
  は辞書に入れず、話し手に選ばせる。
- **概念モデルの行** — 語の表を持つ文書 (例: `docs/SPATIAL_RELATION_MODEL.md`) に、語・軸・
  指す先の確かめ方を足す。語の表・辞書・コードの語彙は両向きの census
  (例: `src/SpatialRelationModelDoc.test.js`) で縛り、片方だけに足した語を落とす。

辞書が整う前に機構を書くと、語ごとに読みが散って後から揃えることになる。

### 1. 何が成り立てば完了か (Goal — 解ではなく性質)

> この節に並ぶもの: 完了の条件 (「〜できる」「〜が起きない」の形の文) 1〜3 個。

依頼が解の形 (「ここはキューで」「フラグを足して」) で来ていたら、一段持ち上げて
**欲しい性質**を言い直す (核 §1.2)。より安い解が許されるかもしれない。

### 2. 触るものは何個あってよく、どんな状態をとるか (状態表 — 基数を必ず含める)

> この節に並ぶもの: 今回触るもの 1 つにつき 1 行 — とりうる状態・いくつあってよいか・誰が書き換えるか。

`docs/STATE_LEDGER.md` を読み、触る実体の行を引く (無ければ新設する行を提示):

| 触るもの | とりうる状態 | いくつあってよいか (0 個 / 1 個 / 複数) | 書き換えてよい唯一の場所 |

- **0 個が正当なら**「0 のとき何が起きるか」を書く。無言で既定値に落ちるのは禁止
  (PHILOSOPHY Yellow Card「必須入力の欠落に既定値を与えない」— ロボットが 0 台なのに既定の
  ロボットが勝手に描かれた先例)。
- **複数が正当なら**「どれのことか」をどう指すかを書く。
- 累積して 3 状態以上、または不正遷移が事故になるなら、**クラスより先に**状態機械を設計し
  `docs/STATE_TRANSITIONS.md` に節を起こす。不正状態は型で表現不能にする。

### 3. 「どれのことか」を決める判定はどこに 1 つあるか (同一性の所有者)

> この節に並ぶもの: 「この物はどれか」を判定する関数と、その置き場所 (既存か新設か)。

「この実体はどれか」を決める述語は**どこが 1 箇所で持つか**。既存の名前付き述語があれば
それを呼ぶ (例: `isRobotBaseFrame()`)。呼び出し側で `name === X && parentId === null` を
並べ直すのは 1 行でも第二の源 (§1.1)。新設するなら
`src/IdentityContainment.test.js` の `IDENTITY_RULES` に登録して機械に守らせる。

### 4. 変えると影響が届くのはどこまでか (blast radius — 一言で)

> この節に並ぶもの: 影響が届くファイル・機能と、触らないと決めたもの。

ここを変えたとき壊れうる到達可能ノード。即答できないなら、それ自体がトリガ (核 §3) —
依存グラフを起こしてから進む。

### 5. 正しいことを何で確かめ、その確かめ方は何を見逃すか (検証の形 — §1.2 Evidence / Q3)

> この節に並ぶもの: 走らせる確認 (テスト・コマンド) と、それぞれが見逃すもの 1 行。

この変更が正しいことは**何で示すか**: test / type / bench / 実行結果のどれか。
そして新しく決めた規律があるなら「それは書く瞬間にどこで問われるか」— 散文でなく
テスト・CI ステップ・`.claude/hooks/` のいずれかに降ろす。

**選んだ証拠が構造的に見逃す変化を 1 行で宣言する。** 「通った」は *その形の証拠が
見える範囲で* 通ったにすぎない。とくに**入力が毎回変わる**証拠 (キー入力ごとに要求値が
動く数値操作など) は、1 フレーム古い状態を読む欠陥を隠す — **同じ要求を 2 回以上通す**形が
要るかを問う (ADR-098 の e2e は数値 Grab で書かれていたため緑のまま振動を出荷し、
ADR-101 で別途起票することになった)。逆向きも同じ問いの一部で、画面座標に依存しない形を
選んだこと自体が別の欠陥を露出させている (同 PR の `_setSnapMode`)。

### 6. 設計判断として記録に残すか (ADR)

> この節に並ぶもの: ADR を書くか否かと、その理由 1 文。

1〜5 の答えが「非自明・不可逆な設計選択を含む」なら ADR を起こす。その場合
**同じ PR で GSN 論証木も起こす (無条件)** — 規律の正本は adr skill
(`.claude/skills/adr/SKILL.md` §GSN 併設) にあるので、ここには写さない (核 §1.1)。

## 出したあと

ユーザーの合意を待ってから実装に入る。1〜5 のうち即答できない項があれば、
それを先に潰す (未成熟な判断は進めるのではなく欠落を表に出す — 核 §1.2)。
変更が局所・可逆・既知なら「reactive のまま進む」と明言して短く切り上げてよい (核 §3) —
このコマンドは重いレンズを常時起こすためのものではない。

## 完了時 — PR を作る (ループを証拠で閉じる, 核 §2 / §5)

実装が終わったら**指示を待たずに** commit → push → **PR を作成する**。
「done」は意図ではなく証拠で閉じるものなので (核 §5「証拠なき完了禁止」)、
PR 本文には上の 0〜6 の答えをそのまま載せる — レビュアが読むのは差分ではなく
**なぜその差分か**であり、それは既に俯瞰で出ている。書き直さずに持っていく
(PR 本文も `.claude/READABLE-OUTPUT.md` の語の規律に従う):

- **言葉** (§0) — 言いたい文と、足した / 割った語 (または「言葉は足りている」)。
- **完了の条件** (§1) — 解ではなく性質。何が成り立てば完了か。
- **触るものと個数** (§2) — 触ったものがいくつあってよいか (0/1/複数) と、書き換えてよい場所。
  台帳 `docs/STATE_LEDGER.md` の行を同じ PR で更新済みであること。
- **「どれか」の判定** (§3) — 新設した判定関数と、`IDENTITY_RULES` 等の登録先。
- **影響範囲** (§4) — 触ったものと、**触らなかったと宣言した**もの。
- **確かめたこと** (§5) — 実行したコマンドと**実際の結果**。落ちたもの・レーンが無くて
  検証できなかったものは隠さず書く (核 §2「再 Observe」— 通ったことにしない)。
- **記録** (§6) — ADR / GSN を起票したなら link、しなかったならその判断理由を 1 行。

俯瞰と PR が食い違ったら、食い違いのほうを本文に書く (実装で前提が変わるのは
正常。黙って俯瞰を書き換えると、判断の履歴が消える — 原則 #19)。

例外: ユーザーが「PR は作らないで」と明示した場合、および push 先ブランチが
指定されていない場合のみ。それ以外は確認を挟まず作ってよい。
