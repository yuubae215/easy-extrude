# Algorithms — いま実際に使っている計算と、その置き場所

**この文書は「何をどう計算しているか」の索引である。**「なぜその設計か」は ADR、
「どこに置いてよいか」の規則は `CLAUDE.md` §AI 向けガード (ADR-146 の 3 軸) にあり、
**ここには複製しない** (§1.1)。ここが答えるのは 1 つだけ:

> ある量は**どの式で**、**どのファイルで**、**どちらのレイヤで**計算されているか。

起票の経緯: 当事者の「設計書か何かに使用してるロジックは書くようにして」。
散文は腐るので、各行は**実在するファイル**を名指しし、検査が在るものは検査も名指しする
(名指しの無い記述は次に読む人が確かめられない — ADR-115)。

## 2. 運動学

### 2.1 DH 規約 (standard / distal)

    T_i = Rz(θ_i) · Tz(d_i) · Tx(a_i) · Rx(α_i)

α = `[π/2, 0, 0, π/2, −π/2, 0]` は**構造**であって設定ではない (これが「UR である」
ことの定義)。機種差は 6 つの長さ `d1, a2, a3, d4, d5, d6` だけに閉じる。
UR5e: `d1=0.1625, a2=−0.425, a3=−0.3922, d4=0.1333, d5=0.0997, d6=0.0996`。

**この 6 数は手書きされていない** — `kinematicsDeclarationFromUrdf` が
`public/robot/skeleton_arm.urdf` から導出する。画面に出る腕と探索が解く腕が同じ 1 台で
あることの根拠 (ADR-141)。

### 2.2 FK チェーン (ADR-145 D1)

`forward_kinematics_chain` は累積積の**各段**を返す (7 要素: ベース原点 + 6 関節原点)。
`forward_kinematics` はその最終要素を返す薄いラッパ — 途中段と最終段が別々にずれる
余地を作らないため。

隣り合う原点を結んだ線分が**腕リンクの近似**で、干渉判定 (§3.2) の入力になる。
標準 DH の frame は「リンクの終わり」に在るので、この原点は物理的な関節中心とは
`a_i`/`d_i` ぶんずれる — 線分近似である以上これは誤差の一部であり、**正確な腕の体積が
要るならリンクのメッシュを持つしかない**。

### 2.3 逆運動学 (閉形式・最大 8 解, ADR-127)

軸 2/3/4 が平行という構造から位置 3 自由度と姿勢 3 自由度が代数的に分離でき、
**肩の左右 × 肘の上下 × 手首の反転 = 2³ = 8 解**が得られる。手順:

1. **θ1** — 関節 5 の原点を base の XY へ落とし、肩オフセット `d4` から 2 通り。
2. **θ5** — `cos θ5 = (px·s1 − py·c1 − d4)/d6` から 2 通り (手首の反転)。
3. **θ6** — `T56` の向きから。`|sin θ5| < 1e-7` の**手首特異点では定まらないので 0 を
   宣言的に選ぶ** (「たまたま 0」ではなく「選んだ 0」)。
4. **θ3** — 平面 2 リンク問題へ落として余弦定理から 2 通り (肘の上下)。
   **平面は frame1 の x–y** (α1 = π/2 が z1 を関節 2 の軸に向ける)。x–z で解くと
   肘の角がわずかにずれ、しかも「それらしい」値が出るので値を眺めても気づけない。
5. **θ2** — 肩から手首への向き − 肘が作るオフセット角。
6. **θ4** — 残りの回転を `T34` から読む。

**数値反復が無いので「収束失敗」という状態が存在しない。** 届かない姿勢は
**空**を返し、空は「解が無い」であって「解けなかった」ではない。

検証の形 (原則 #28): 多対一なので `IK(FK(q)) == q` は**求めない**。求めてよい同一性は
商の上の fixpoint、すなわち **`FK(IK(T)) == T` が全解について成り立つこと**。

### 2.4 代表解 (ADR-127 D5)

8 解のうちワイヤに載るのは**決定的に選んだ 1 つ**。基準は**関節総移動量が最小**
(= 原点姿勢に最も近い解)、同点は `inverse_kinematics` の決定的な順序が破る。
順序ではなく量で選ぶのは、入力が少し変わったときに代表解が飛ばないようにするため。

**クライアントも同じ規則を使わなければならない** — 違う代表を選ぶと、画面の腕と
探索が解いた腕が*どちらも正しい解*でありながら別物になる。

> **残し**: 「干渉しない解が見つかるまで 8 解を順に試す」モードは未実装 (DEF-037)。
> 今日は代表解が干渉すれば候補は単に棄却される。

### 2.5 2 つの gauge (ADR-147)

契約に載る候補 frame と IK が解くフランジ目標は**同じ向きではない**:

| | +Z 軸 | 宣言 |
|---|---|---|
| 候補 frame (ワイヤ) | **−approach** | `pose_codec.py` の FRAME_CONVENTION |
| フランジ目標 (IK 入力) | **+approach** | `ur_solver.py` の `FLANGE_Z_IS_APPROACH` |

**「180° 回せばよい」ではない。** どちらも `basisFromZ(z)` で基準 x/y を張り直しており、
参照軸の選び方が z の成分で切り替わる (`|z| < 0.9` か否か) ため、
`basisFromZ(−a)` は `basisFromZ(a)` の符号違いにならない。復元は (approach, roll) まで
戻してから張り直す往復でしか正しくならない。**近道が効かないことは測って焼いてある**
(`CrossLanguageDerivation.test.js` の「楽な近道の否定」)。

## 3. 判定 (ドメイン段階フィルタ)

    候補生成 → リーチ → IK → 把持性 → 可視性 → 干渉 → 加重和スコア → 上位N件

各段で**短絡**するので棄却段は排他 = ファネル恒等式
`生成 = Σ棄却 + 通過` が成り立つ。並びの根拠 (安い順) は `pipeline.py` の
docstring にコスト実測とともに書いてある。

> **並びの根拠は古い** (DEF-038)。ADR-081 の順序は naive IK の 5µs で測られており、
> 再測 (2026-09-21) では最も高い段は干渉ではなく**解析解 IK の 368µs** だった。
> 把持性・可視性を IK の前へ出す余地が在るが、並べ替えは棄却の帰属を変えるので別判断。

### 3.1 障害物の形 (ADR-133 D5)

`obstacles[]` は **kind 判別の union**:

| kind | 幾何 | 距離の式 |
|---|---|---|
| `sphere` | 中心 + 半径 | `distance_point_to_segment(c, a, b) − r` |
| `box` | 中心 + 半外寸 + 姿勢 (OBB) | 箱のローカル系へ戻して AABB 距離、線分方向は黄金分割探索 |

どちらも `surface_distance_to_segment(a, b)` という**1 つの問い**に答える
(原則 #17)。符号つきで、負なら線分は内部を通っている。干渉 (`<= probe_radius` か)・
遮蔽**深さ** (`−値`)・approach clearance (余裕量) はすべて**この同じ量**から導く。

**線分 vs OBB に閉形式を書かない理由**: 点と凸集合の距離は線分パラメータ `t` について
**凸**なので、黄金分割探索は単峰性に乗って大域最小へ収束する。手で書くと面・辺・頂点の
26 通りの分岐になり、**どれか 1 つを落としても「それらしい」値が出る**。
刻み幅を持つサンプリングでは刻みより細い接触を見落とす。

**外接球をやめた理由** (ADR-133 D5 / ADR-145): 球は「棄却側にしか外れない安全な丸め」
として選ばれたが、それは進入経路だけを見ていた頃の話。腕リンクが第二の消費者になった
瞬間、同じ保守性が破綻する — ペデスタル (300×300×120) の外接球は半径 220.5mm で、
**ロボット自身のベースが中心から 60mm** の位置に入る。箱なら据付面で接するだけ。

**空洞は 5 枚** (ADR-133 D2): `innerDimensions` を宣言した実体は床 1 + 壁 4 に展開する
(`src/domain/graspTargets.js: hollowBodyBoxes`)。1 つの箱にするとトレーの中身が
詰まっていることになり、**中へ入る候補がすべて干渉で棄却される**。壁厚は宣言せず
`(outer − inner)/2` から導出する (両方宣言すると食い違える)。上面は開いている。

### 3.2 腕リンクの干渉 (ADR-145)

代表解の FK チェーンから**関節に依存して動く 5 本**のリンク線分を作り、同じ障害物集合と
照合する。**ベース→関節 1 の 1 本は外す** — θ1 の回転軸そのもので原点が `(0,0,d1)` に
固定、つまりどの配置でも同じ場所に在るので候補を区別する力を持たない一方、据付台を
ほぼ常に「衝突」と答えてしまう。

**`JointSolution` を持たない候補では腕を見ない** (型で分岐、原則 #2)。素朴ソルバが返す
占位解は 1 個の数であって 6 関節の配置ではないので、腕のジオメトリを再構成できない。
返るのは**空タプル**で、空は「腕が触れていない」ではなく**「腕を見ていない」**。

### 3.3 near-miss (ADR-079 / ADR-081)

可視性・把持性の Protocol は bool ではなく**不足量**を返す: `0.0` = 合格、正 = その量
だけ足りない、`inf` = その軸では測れない棄却 (視野外 / 接触対なし)。ゲート
(`miss <= 0`) と診断 near-miss を**一つの計算**で賄う (二度走らせない)。

> **測らなかった objective には欄が無い** (ADR-120)。閉じたスコア層に optional 兄弟を
> 生やせないので、区別を運ぶのは**鍵の不在**だけ。0 点と評価不能は値で比べるとまさに
> 同じ数に見える。

## 4. クライアントが解いてよいもの (ADR-146 / ADR-147)

`core/` が居ない環境 (GitHub Pages) では `reachSolution` が常に `undeclared` で返る。
このときクライアントは **§2 の閉形式をそのまま走らせて**腕を描く。

- **姿勢は厳密**。位置も向きも機械精度で候補と一致する (共有フィクスチャで 1e-9 以内)。
- **検証はされていない**。干渉・可視性・把持性・スコアは `core/` しか答えられない。
  だから権威は `unverified` であって `approximate` ではない — **粗いのではなく、
  誰も確かめていない**。表示は半透明のゴーストで、行のキャプションがそう述べる。
- 届かなければ **`null`**。「一番近い配置」は出さない (原則 #11)。

> ADR-144 が実装した**サンプリング探索**(4 サンプル格子 × 8 スタート × 12 ラウンド、
> 許容差 10mm、位置のみ一致) は ADR-147 で**退役した**。閉形式が使える機種で 2 つの
> 答えを持つのは §1.1 違反であり、精度・姿勢・コストのすべてで劣っていた。

## 5. 単位と座標系

- **ワールドはミリメートル** (ADR-136)。ロボティクスは**ワイヤで**メートルへ変換する。
  変換の境界は `src/domain/worldUnits.js` ただ 1 箇所。
- **ROS world frame** (+X 前方 / +Y 左 / +Z 上、右手系)。URDF は ROS 標準のまま読み込み、
  `RobotStage` が掛けるのは一様 ×1000 スケールのみ (軸の入れ替えは無い)。
- 契約は**単位を名指ししない**。長さは「レイアウト自身の長さ単位」。

## 6. この文書の保ち方

- 計算を足したら**表に行を足す**。表に無い計算は「置き場所を誰も決めていない」の印。
- 式そのものが要るのは**自明でないもの**だけ (DH・IK の手順・距離の定義)。
  自明な計算まで書き写すと、コードと文書の 2 つの源ができる (§1.1)。
- **数値 (実測) を書くときは測った日と条件を添える。** 数の無い「速い/遅い」は
  次に読む人が確かめられず、古くなったことにも気づけない (DEF-038 がその実例)。
