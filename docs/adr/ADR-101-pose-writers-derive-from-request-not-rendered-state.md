# 101. pose を計算する入力は「要求 + セグメント開始の写し」だけ — 補助が自分の出力を測り直すのをやめる

- Status: Accepted (実装済み — `_applyStackAssist` の live 読み撤去、入口が適用済み delta を渡す形、live プローブの query 専用宣言、writer の個数検査、症状回帰 2 本)
- Date: 2026-07-27
- Deciders: yuubae215, Claude (pairing)
- Supersedes / Superseded by: なし (ADR-098 が開けた経路に残っていた**鮮度**の欠陥を閉じる)

## Context — Goal と力学 (§1.2 Goal)

当事者の観測:

> Grab でキューブのところまで移動させるときに、一応スタックするのはするけど、
> スタックしたり、戻ったりします。2値で判断してるのでしたっけ？
> ステートマシンだったら、フリックしないと思うのですが。
> とにかく、分身してるように見えるのでなんとかしてほしい。

持ち上げた Goal:

- **G1 — 同じ要求は同じ pose を生む。** ドラッグ 1 セグメントの中で、pose は
  ポインタ位置 (要求) の関数であり、直前のフレームの結果の関数ではない。
- **G2 — 「鮮度」が実体種によって変わらない。** ADR-098 は「載る/載らない」が種で
  分岐しないようにしたが、*測るときの新しさ*は種で分かれたままだった。
- **G3 — 状態の見た目 (HUD の `Stack: ON`・接触 FX) が幾何と同位相で決まる。**
  幾何が振動すれば表示も FX も振動する。源を止める。

### 力学 — 「2 値」は原因ではない。**入力**が原因だった

当事者の問い「2 値で判断してるのでしたっけ？」への答えは **yes だが無関係**である。
`stacking` は確かに真偽値だが、真偽値そのものは振動しない。振動したのは
**その述語の入力**で、入力が*自分の 1 フレーム前の出力*だったために、状態機械で
言えば「A→B→A→B を毎フレーム踏む」形になっていた。2 値を 3 値や enum に増やしても
入力の閉路が残る限り位相が増えるだけで振動は消えない。

閉路の実体は `SceneService._applyStackAssist()` の最初の 2 行だった:

```js
const gZMin   = this._bottomZOf(grabbed)          // ← いま描画されている底
const samples = this._footprintSamplesOf(grabbed) // ← いま描画されている足跡
```

この 2 行が読むのは、**同じ関数呼び出しの数行前に自分が書いた pose** である
(`applyPreviewTranslation` の入口ループが `_applyEntityDelta` で書いている)。
そして「読めるか」が実体種で割れる:

| 実体 | 宣言されたプローブ | 実際に読む先 | 鮮度 |
|------|------------------|------------|------|
| Solid / ImportedMesh / 注釈 | `bottomFaceAndCentroid` × `minCornerZ` | `obj.corners` | **同期** — `_applyEntityDelta` が同じ呼び出しで書いた値 |
| robot_base / CF | `originPoint` × `originZ` | `_worldPoseCache` | **rAF ごと** — `_updateWorldPoses()` は毎フレーム 1 回しか走らない |

`_worldPoseCache` は「エントリが無ければ再計算」しかしない (`worldPoseOf`)。
ドラッグ中は毎フレーム全再計算されて埋まっているので、*書き込みで無効化されない*。
結果、ロボットを掴んでいる間の補助はこう回る:

```
frame N   : 入口ループが床へ置く → 補助が前フレームの pose (= 天面) を読む
            → 「もう載っている」→ 何もしない → 床のまま描画
frame N+1 : 入口ループが床へ置く → 補助が前フレームの pose (= 床) を読む
            → 天面まで持ち上げる → 天面で描画
frame N+2 : … 以下 2 周期
```

実測 (修正前、同一の要求を 5 回通したときの `bottomZ`):

```
[0, 1, 0, 1, 0]      ← ロボット (原点で測る実体)
[1, 1, 1, 1, 1]      ← キューブ (corners で測る実体)
```

連続ドラッグでも同じ形が出る (ポインタをキューブ上へ掃いたときの `bottomZ` 列):

```
修正前: … 0, 0, 1, 0, 1, 0, 1
修正後: … 0, 0, 1, 1, 1, 1, 1
```

「分身しているように見える」の正体はこれで、幾何が毎フレーム 2 値の間を往復して
いた。加えて `stacking` が毎フレーム反転するため `snapTransition()` が
`null → snapshot` を engage と判定し、**接触フラッシュが 1 フレームおきに発火**して
いた (`stackSnapshot(false, …)` は null を返す)。ロボットが 2 箇所で明滅し、
その上でストロボが焚かれていた。

### なぜ ADR-098 で気づけなかったのか

ADR-098 は種の門を外し、`grounded` を 1 つの意味に戻した。その回帰は**数値 Grab**
(`G` → 軸 → 距離 → Enter) で書かれており、キー入力ごとに要求値が*変わる*。要求が
変わる限り、1 フレーム遅れの入力でもいずれ正しい側に落ちるので、最終状態だけを見る
検査は緑になる。振動は「**同じ要求を 2 回以上通す**」か「ポインタを連続で動かす」と
きにしか見えない。

つまり ADR-098 は正しく閉じたが、その隣に**別の軸の非対称**が残っていた:

- ADR-097 / ADR-098 が閉じた軸 = **どの実体に規則が当たるか** (種 → 方針)
- 本 ADR が閉じる軸 = **その規則がどの時点の幾何を見るか** (描画済み → 要求)

同じ `SceneService` の同じメソッドで、片方の軸だけが宣言され、もう片方は
`_worldPoseCache` の更新周期という**実装の都合**に委ねられていた。

### 位置

サービス層 (`SceneService`) に閉じる。ドメイン (`placement.js`) の宣言・純粋関数、
契約・BFF・`core/` は**不変**。ロボット base pose の**値**は安定側へ動く
(振動していたものが止まる) が、契約は動かない。

## Options considered

- **A: `_worldPoseCache` に dirty フラグを持たせ、`worldPoseOf()` が自分で鮮度を
  保証する (原則 #23)** — tradeoff: 根っこは最も正しい。しかし
  `_updateWorldPoses()` は全 CF の再計算に加えて mounts の Wasm 変換・fastened の
  書き戻し・リンクビュー更新という**副作用の束**を持つ。ドラッグ中の読み取り 1 回
  ごとにこれを走らせるのは、性能と副作用の順序の両方で危険が大きい。読み取り側
  (N パネル・`supportOf`) にとって「1 フレーム前 = いま描画されているもの」は
  むしろ正しい答えでもある。**欠陥は読み取りではなく、書き手が読んだこと**。
- **B: 補助の入力を「セグメント開始の写し + 方針が許した delta」にする (採用)** —
  tradeoff: 閉路そのものを断つ。`_policyDelta` が既にその形で書かれているので、
  補助だけが例外だったことが露わになる。live プローブは残るので、次の writer が
  同じ罠を踏む可能性は消えない → 個数検査で問う (下記 Decision 3)。
- **C: `stacking` を 3 値以上の状態機械にする (当事者の直感の直訳)** — tradeoff:
  振動の原因は述語の値域ではなく入力の閉路なので、状態を増やしても位相が増える
  だけで消えない。**症状に名前を付けて原因を隠す**形になる。
- **D: 補助にヒステリシス (前回 stacking なら閾値を緩める) を入れる** — tradeoff:
  振動を「見えなくする」補正であって、pose が履歴に依存する事実は残る。undo /
  数値入力 / 再現テストで「同じ要求から違う結果」が出続ける。
- **E: 現状維持** — tradeoff: ロボットを掴むたびに分身する。ADR-098 が回復した
  「キューブと同じ規則」が、体験としては成立していない。

## Decision — Strategy (§1.2 Strategy)

**案 B。pose を計算する側の入力から「描画済みの状態」を締め出す。**

### 1. 入口が「方針の許した delta」を補助へ渡す

`applyPreviewTranslation` は入口ループで実体ごとの適用済み delta を集め、補助へ
渡す。補助は結果を**測り直さない**:

```
applyPreviewTranslation(...)          appliedDeltas: Map<id, Vector3>
  └ _policyDelta(obj, startCorners, worldDelta) → delta   … 記録して適用
  └ _applyStackAssist(segStartCorners, segStartPositions, appliedDeltas, activeId, movingIds)
```

補助の入力は `_policyDelta` と**同じ不変な源**になる:

| 旧 (描画済みを測る) | 新 (要求から導く) |
|---|---|
| `this._bottomZOf(grabbed)` | `this._segmentStartBottomZ(grabbed, startCorners)` |
| `this._footprintSamplesOf(grabbed)` | `this._destinationSamples(grabbed, startCorners, applied)` |

この 2 つの「スナップショット版の双子」は ADR-098 で既に実在していた
(`_policyDelta` が使っている)。補助だけが双子の片割れを使っていなかった。

### 2. 座らせる Z を「補正量」ではなく「絶対の目標」で表す

旧: `zOffset = 支持面Z − いまの底Z` → `worldDelta + zOffset` を再適用。
新: `seatDeltaZ = 支持面Z − セグメント開始の底Z` を**そのまま Z の delta** にする。

これは同じ式の言い換えではない。旧式は「いまの底」が方針で clamp された後の値
だったため、要求が床下を突いたときに `worldDelta.z` と二重に効いて**座り位置が
足りなくなる**副作用があった (床へ潜らせながらキューブへ載せようとすると天面に
届かない)。絶対目標にすると、床の clamp は各実体の `_policyDelta` が最後に一度
だけ当てる形に戻る。

「もう座っている」の判定も、いまの Z ではなく **要求どうしの比較**になる:
`|seatDeltaZ − applied.z| < SUPPORT_TOLERANCE`。

### 3. live プローブを **query 専用**と宣言し、writer の中で個数を数える

`_footprintSamplesOf` / `_bottomZOf` は消さない — N パネル、`supportOf()`、E2E の
placement スナップショットにとって「いま描画されている姿」は**正しい答え**である。
消すのではなく**役割を宣言**し、機械に問わせる:

`src/PosePolicyOwnership.test.js` に `POSE_COMPUTING_METHODS` (pose を計算する
メソッドの名指し) × `LIVE_PROBES` (`_bottomZOf` / `_footprintSamplesOf` /
`worldPoseOf` / `_worldPoseCache`) を置き、**writer の本体に live プローブが 0 個**で
あることを数える。逆向きに、補助がスナップショット由来の入力を**実際に引いている**
ことも固定する (規則が空回りしていないことの確認 — 原則 #31 の同型)。

散文に書くだけでは足りない理由は憲法 Q3 そのもので、この罠は
**実装を読んでも見えない**: `_bottomZOf(grabbed)` は Solid では新鮮に見え、
robot_base でだけ古い。読んで気づける形をしていないものは、読ませるのではなく
**書いた瞬間に落とす**しかない。

### 4. `stacking` の値域は変えない

当事者の「ステートマシンだったら」に対する明示的な非採用 (案 C)。入力が安定した
時点で 2 値は安定する — 実測でそうなった。値域を増やすのは、増やすべき理由
(区別したい状態が実在する) が立ったときに別 ADR で行う。今回はその理由が無い。

## Consequences — Evidence と tradeoff (§1.2 Evidence)

- **肯定的:**
  - G1 — 同じ要求から同じ pose。ドラッグ中の「載る→戻る」が消え、接触 FX の
    1 フレームおきの再発火も止まる (`stacking` が反転しなくなるため)。
  - G2 — 鮮度が種に依らない。corners で測る実体と原点で測る実体が、同じ規則を
    同じ時点の幾何で受ける。
  - ADR-098 の「載る/載らない」に続いて、「いつの幾何で決めるか」も宣言になった。
    残っていた最後の暗黙が `_worldPoseCache` の更新周期だった。
  - 副産物: 床下を突きながら面へ載せる要求で、座り位置が足りなくなる欠陥
    (Decision 2) が同時に消えた。
- **受け入れるコスト / 否定的:**
  - `_worldPoseCache` は依然として**自分で鮮度を保証しない** (原則 #23 の破れは
    残る)。本 ADR は writer をキャッシュから切り離しただけで、キャッシュ自体は
    直していない。案 A を採らなかった理由は上記のとおりで、次に「ドラッグ中に
    CF の world 位置を読んで何かを決める」要求が立ったときに再検討する。
    その時に引かれる行としてここに残す。
  - 補助の引数が 1 つ増えた (`appliedDeltas`)。入口と補助の結合は強まるが、これは
    「補助は入口の一部であって独立した計算ではない」という事実の表明でもある。

    増えたら表に足すまで数えられない (ADR-098 のプローブ検査と同じ限界で、
    埋め方も同じ)。

## Lens notes

- **レンズ: 原則 #24 (導出→入力の閉路)。** 症状は「フリック」という*表示*の形で
  報告されたが、当てたのは表示ではなく**データフローのグラフ**で、`pose 書き込み →
  _worldPoseCache → 補助 → pose 書き込み` の閉路が 1 本見えた時点で決まった。
  閉路の辺が 1 つ (`_worldPoseCache` の更新が rAF ごと) だけ「遅延辺」だったので、
  周期 2 の振動になる。
- **様態:** 逐次フロー (BPMN) — ドラッグ 1 フレームの処理は決め打ちの順序であり、
  事象駆動の裁量処理ではない。だから「順序の中でどの時点の値を読むか」が設計の
  本体になる。
- **状態機械 (§1.4):** 当事者の直感 (「ステートマシンだったら」) は正しい方向を
  指しているが、この実体で設計すべきだったのは*状態の数*ではなく**遷移関数の
  引数**だった。状態機械が振動しないのは値域が広いからではなく、遷移関数が
  (状態, 入力) の関数であって「自分の出力」を引数に取らないからである。
- **原則 #31 との関係:** 「規則を持つ経路ではなく持たない経路が欠陥」の 4 例目
  (ADR-090 / ADR-093 / ADR-097)。今回欠けていたのは**鮮度の宣言**で、鮮度は
  `mode` や `status` のような欄を持たない — どの実体にも「この値はいつのものか」を
  書く場所が無いので、*在るもの*を読む限り永久に見えない。だから検査は
  「writer の中に**禁じられた形**が何個あるか」を数える形にした。
