# 130. 探索は自分の主語を所有する — 選択は主語ではない

- Status: Accepted (実装済み 2026-08-14 — 入口の union 化・主語の書き込み・偽の阻止文 0 件)
- Date: 2026-08-14
- Deciders: yuubae215, Claude
- Retires: なし — この ADR は形を**足す**のではなく、入口の 2 値を union へ**置き換える**。置換前の形 (`available` の 2 分岐) が戻らないことは `src/GraspSubjectOwnership.test.js` が kind の宣言表で問う
- 段: **G-6** (`docs/grasp/implementation-order.md`)。前提: G-2 / G-3 (ともに完了)
- Supersedes / Superseded by: なし (ADR-110 D4 が決めた「選択が入口を決める」を、**探索が生きていない間**に限定する)

## Context — Goal と力学 (§1.2 Goal)

**Goal:** *「この探索は誰について・何についてか」を述べる場所がちょうど 1 つで、
画面のどの部品もその 1 つを読む。* 手順を進めるという**正常な操作**が、自分自身の
ゲートを踏んで偽の阻止文を出す状態を無くす。

Goal は「あのメッセージを消す」ではない。それは解の形をした要件で、`EntityChecks`
から grasp の行を消しても満たせてしまう (そして ADR-110 が閉じた「主語の無い探索」の
穴が開き直す)。満たしたい性質は**主語の所有者が 1 つであること**で、メッセージが
出なくなるのはその帰結である。

### 観測 — 手順が自分のゲートを踏む

ユーザー報告 (2026-08-14):

> `cell_robotics` を採る → Outliner で `robot_base` → `n` → 「Grasp candidates…」→
> 対象を選ぶ → 面チップで掴む場所 → Grasped カードでハンド → Run
> をしようとすると、**対象を選ぶところで**「base tcp を持ったロボットを選択して」
> みたいなエラーが出る

再現した (Playwright + `?graspStub=solve`、2 クリック):

| 手順 | `EntityChecks` が出す文 |
|---|---|
| パネルを開いた直後 | なし |
| **掴む対象を選ぶ** (Outliner / ビューポート) | `Grasp candidates are solved for a robot; select a robot frame to run one.` |
| ビューポートの空きをクリック | 同上 |

**掴む対象を選ぶには、選択をロボットから外すしかない。** つまりこの手順は、
自分の次の一歩で自分のゲートを踏む構造になっている。

### 力学 1 — 主語に源が 2 つあり、Run が読むのは片方だけ

| 問い | 読んでいる源 | 寿命 |
|---|---|---|
| 入口を出すか (`EntityChecks` → `graspEntryFor`) | **ビューポートの選択** (`nPanelData.robotRole`) | クリックごと |
| 実際に誰について解くか (`runGraspSearch`) | **パネルの pick** (`_selectedRobotId` → `selectRobot`) | 探索セッション |

`openGrasp()` は `nPanelData` も選択も**一切読んでいなかった** — 入口が要求した
選択は、入口を通った瞬間に捨てられていた。§1.1 の違反であり、原則 #1 の
「入口はちょうど一つ」が*形式上は*満たされている (`setMode` 的な入口は 1 つ) のに、
**その入口が premise を運んでいない**という形である。

### 力学 2 — 出た文は嘘である。しかも「丁寧な嘘」

阻止文が出ている間も、その下のパネルは `robot: robot_base` を保持し、Run は通る。
原則 #11 が名指しするのは*無言の no-op* だが、**これはその鏡像**である:

> 阻まれていないのに阻止の理由を出す。

無言の失敗より議論しにくい — 画面は*仕事をしているように見える*ので、ユーザーは
自分の手順を疑う。実際ユーザーは「なんでだと思う？」と訊いた。手順は正しかった。

### 力学 3 — N 台のとき、選んだロボットは捨てられる

`selectRobot(robots, null)` は 1 台なら選択と無関係に解決し、**N 台なら null を返す**
(ADR-090 の正しい判断 — 黙って先頭を採らない)。ところが `_selectedRobotId` は
パネルの pick でしか書かれないので:

- Outliner で 2 台目の `robot_base_2` を選ぶ → 入口は「押せる」と言う
- 押す → パネルは「2 robots in the scene — pick which one to solve for」と言う

**ゲートが要求した宣言を、通った先が知らない。** 1 台のシーンでは両者がたまたま
一致するので、この欠陥は**ロボットが 2 台になった日に初めて見える** — ADR-090 が
「名前で解決すると 2 台目で全部同時に壊れる」と書いたのと同じ形が、同一性ではなく
**選択**の側に残っていた。

### なぜコードを読んでも見えないか (原則 #31)

`EntityChecks` が読んでいないのは `context.grasp` — **探索が生きているかどうか**の欄
である。読んでいない欄は、そこに無い欄と区別がつかない。`graspEntryFor` の実装を
何度読んでも、*読んでいない事実*は出てこない。

同型が一段上にもある: 「入口」という語が、**入る前**の問い (どこから入れるか) と
**入った後**の状態 (いま何をしているか) を同じ 1 つの行で受けていた。行は 1 つでも
問いは 2 つで、2 つ目には答えが無かった。

### 寿命の関係として書くと

```
L(主語) = L(探索セッション)          ← 要求
L(選択) = L(クリック) ≪ L(探索)      ← 実際に読まれていたもの
```

**これは ADR-129 の主題の同族である** — 宣言が、寿命の違う実行時インスタンスに
寄生している。違いは 2 点:

1. ADR-129 は宣言を**文書**へ預ける話 (寿命 = 文書)。ここは**探索セッション**へ
   預ける話で、探索は文書より短命でよい (「いま解いている」は保存すべき事実ではない)。
2. ADR-129 の欠陥は*静かに壊れる* (古い位置での正しい答え)。こちらは**騒がしく
   壊れる** — 出てはいけない文が出る。騒がしいぶん見つかりやすく、実際に見つけたのは
   ユーザーが手順を通した最初の 1 回である。

## Options considered

- **A: `EntityChecks` から grasp の行を消す** — tradeoff: 一番速いが、ADR-110 D2/D4 が
  「選択の無い状態からの経路をこの入口 1 つに畳んだ」判断を無言で取り消す。
  入口が消えると、把持探索は**選択済みの人だけのもの**になる。**却下。**
- **B: 探索が生きている間は行を disabled のまま黙らせる** — tradeoff: 原則 #11 が
  禁じる「無言で押せないボタン」そのもの。しかも「なぜ押せないか」が
  *探索が開いているから*という、ユーザーから見て理解不能な理由になる。**却下。**
- **C: 選択を主語にする** (掴む対象を選ぶと主語が対象へ移る) — tradeoff: 一見自然だが、
  選択は**1 つ**しか無いのに探索の主語は**2 つ** (ロボットと対象) 要る。1 つの選択に
  2 つの役を持たせると、「いまの選択はどっちの役か」というモード変数が生まれる —
  ADR-103 が投影で潰した「3 つの軸を 1 変数に潰す」形の再生産。**却下。**
- **D: 入口の返り値を kind の union にし、入口が主語を書く** — tradeoff: 呼び手
  (`EntityChecks.jsx`) の分岐が 2 → 3 に増え、宣言表を 1 つ足す。**採用。**
  増えたのは分岐ではなく**区別**である: `LIVE` と `BLOCKED` は今日まで
  `available: false` に潰れていた 2 つの別状態で、潰れていたことがこの欠陥だった。

## Decision — Strategy (§1.2 Strategy)

### D1 — 探索の主語の権威は探索スライスにある。選択は主語ではない

`context.robots.selectedId` (と対象側の `context.graspTargets.selectedRef`) が
唯一の権威。`nPanelData` は**表示のための選択の写し**であって、探索の premise では
ない。ビューポートで何を選ぼうと、走っている探索の主語は変わらない。

### D2 — 入口は主語を**書く**

`openGrasp()` は押された時点の選択が robot frame なら、その robot を主語に据える
(`_adoptSelectionAsSubject`)。これで「Outliner で選ぶ → 入口を押す」が N 台でも効く。

- どのロボットの frame かを決めるのは**ドメインの名前付き述語** `robotForFrameId`
  (原則 #25)。`base` でも `tcp` でも同じロボットを返す — tcp を選ぶのはその
  ロボットを選ぶことである。
- **ロボット以外の選択では主語を消さない。** 消すと「掴む対象をクリックする」が
  主語を黙って落とすことになり、この ADR が消している結合そのものになる。
  未宣言 (0) は状態であって既定値ではない (原則 #31) ので、*入口を通っていない*
  ときの 0 と *入口が選択から採れなかった*ときの 0 は同じ扱いでよい — どちらも
  「まだ言っていない」であり、パネルの pick 行がそれを述べる。

### D3 — 入口の返り値は kind の union。`LIVE` と `BLOCKED` は別状態

```
GRASP_ENTRY_KIND = { OPEN, BLOCKED, LIVE }
```

`LIVE` は理由の欄を**持たない**。「探索が生きているのに阻止理由が在る」という
組み合わせがこの欠陥そのものなので、boolean + nullable reason ではなく union に
して**表現不能**にする (原則 #2 / 核 §1.4「不正状態を表現不能に」)。

描画側は `GRASP_ENTRY_ROW_BY_KIND` という**宣言表**を通す。union を返すだけでは、
描く側が `available` だけ見て 2 分岐へ潰し直せる (今日までがその形だった)。
**未宣言の kind で throw** する (ADR-096 の既定表規律)。

`LIVE` のときこの行が言うのは阻止理由ではなく**主語**である:

- 主語が在る → `searching for robot_base — pick the object below`
- 主語が未宣言 (N 台で未 pick) → `this search has no subject yet — pick the robot below`

後者を「選択が悪い」と書かないのが要点 — 未宣言は*まだ言っていない*のであって、
選択の誤りではない (原則 #31)。

### D4 — 探索が生きていないときの判断は 1 ビットも変えない

ADR-110 D4 / ADR-105 D5 が決めた「選択が入口を決める」「0 の種は 2 つ」「未宣言の
実体種は throw」はそのまま。この ADR が限定したのは**探索が生きている間**だけである。

### D5 — 検査は「偽の阻止文の個数」を数える。出た文の正しさでは数えない

母集団は画面に出た文ではなく、**手順が通しうる選択の全種類**である
(`DECLARED_NPANEL_KINDS` + 「選択なし」から導出 — 手で並べると 5 種目の日に
この検査だけが古びる = ADR-102 の `place-list`)。そのすべてで、探索が生きている
間の kind が `LIVE` であること = 阻止文が **0 個**であることを問う。

在る文を辿る検査は定義上これを見ない — 文は正しく実装され、正しく表示されている。
**間違っているのは問いのほうである。**

加えて主語を書く入口の個数を数える (`_selectedRobotId` への代入 = 宣言された 4 つ)。
ADR-097 が pose の入口を数えた形の続きで、欠陥は「規則を持つ経路」ではなく
**規則を持たない経路**だった。

## Consequences — Evidence と tradeoff (§1.2 Evidence)

### 得られるもの

- `docs/dogfooding/ux-scenarios.md` の手順が、**途中で偽のエラーを出さずに**通る。
- N 台のシーンで Outliner の選択が実際に効く (今日は捨てられていた)。
- 「入る前の問い」と「入った後の状態」が別の kind になったので、4 つ目の状態が
  生まれた日に描画が黙って fall-through しない。

### 受け入れるコスト / 否定的

- `EntityChecks.jsx` の分岐が 1 つ増え、宣言表が 1 つ増える (census 登録簿にも 2 行)。
- **`LIVE` のとき入口ボタンは押せるままにした。** 押すと `openGrasp()` が再入し、
  選択が別のロボットならそちらへ主語が移る。これは仕様として意図的だが、
  「押すと主語が変わる」ことがボタンの文言 (`◇ Grasp candidates…`) からは読めない —
  文言は入口のままである。今日は caption が主語を述べることで補っているが、
  **完全ではない**。動詞としての入口の語彙 (ADR-108「入口は動詞である」) を
  `LIVE` 用に持たせるかは、この ADR では決めない。
- 対象側 (`_selectedTargetRef`) には D2 の相当物を入れていない — 対象を選ぶ入口は
  パネルの `<select>` ただ 1 つで、選択から採る経路が最初から無いため。
  対象を 3D で選べるようにする判断は ADR-128 D1 の線 (選択モデルに触らない) の
  向こう側にあり、ここでは開かない。

### 検証 (証拠)

`docs/gsn/adr-130-a-search-owns-its-subject.gsn` が goal ごとの支えの正本。

| 主張 | 問い所 | 実行結果 |
|---|---|---|
| 探索中に偽の阻止文が 0 個 | `src/GraspSubjectOwnership.test.js` | **9 pass** |
| 選択の母集団が実体種の宣言表から導出されている | 同上 (`SELECTION_SHAPES`) | pass |
| 未宣言の kind で throw する | 同上 | pass |
| 主語を書く入口が宣言された 4 つ、かつ全部実在する | 同上 (両方向) | pass |
| 手順が実機で通る (対象を選んでも阻止文が出ない) | Playwright + `?graspStub=solve` | **falseBlock 0 件 / caption = `searching for robot_base — pick the object below`** |

**この証拠が構造的に見逃すもの:** 単体検査は `liveSearch` を**引数で**受け取るので、
`EntityChecks.jsx` が `context.grasp` を読むのをやめても落ちない (読まない欄は
無い欄と同じに見える — この ADR の力学そのもの)。そこだけはソースの走査で押さえて
あるが、走査は「その識別子が在るか」しか見ない。**手順を実機で通す e2e が本命**で、
それは `docs/dogfooding/ux-scenarios.md` の S2 の隣に置く。

## Lens notes

- **§1.1:** 主語の権威は探索スライスただ 1 つ。`nPanelData` は表示の写しであって
  源ではない (`setSelectionSummary` が既に踏んでいる規律と同じ — 写しは源と
  違う名前を持つ)。
- **原則 #2:** kind の union で分岐する。`available` という**値**での分岐が、
  2 つの別状態を 1 つに潰していた。
- **原則 #31:** 読んでいない欄 (`context.grasp`) は、無い欄と区別がつかない。
  数えるべきは在る文ではなく、**出てはいけない場面で出る文の個数**である。
- **ADR-110 との関係:** あちらは「選択の無い状態からの経路を入口 1 つに畳んだ」。
  その判断は生きている — ここで足したのは、**その入口を通った後**という、
  あちらが問うていなかった状態である。
- **ADR-090 との関係:** 「2 台目で初めて見える」形が同一性ではなく選択の側に
  残っていた。ADR-090 が同一性について閉じた穴の、**入口側の写し**である。
