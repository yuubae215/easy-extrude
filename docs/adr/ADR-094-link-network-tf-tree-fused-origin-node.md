# 094. LINK NETWORK を TF ツリーへ回帰 — Solid と Origin CF を 1 ノードに融合し、木辺を骨格に戻す

- Status: Proposed (設計確定・実装は後続 PR。実装完了時に Accepted へ上げる)
- Date: 2026-07-26
- Deciders: yuubae215, Claude (pairing)
- Supersedes / Superseded by: ADR-048 の §2.1「ノード集合」と §2.2.1「未実装の凡例決定」を置き換える (ADR-048 の §2.1 決定的レイアウト・§2.3 パネル寸法・§2.4 データ契約は無改変で継承)
- 状態台帳: `docs/STATE_LEDGER.md` の「LINK NETWORK パネル (可視性)」「LINK NETWORK グラフのノード」行 — **本 ADR 以前はこの実体の行が 1 つも無かった** (原則 #31 の累積器の穴)

---

## Context — Goal と力学 (§1.2 Goal)

### 要件は解の形で来た

> 「LINK NETWORK で Origin が真ん中の行にきて、上に item name、下に Frame が来てると
> 思うんだけど、非常に分かりづらい。これってビューを分けたほうが分かりやすくなったり
> しない? いくつかの視点が一つにまとまってるから分かりづらいのではないかと」

「ビューを分ける」は **解**。§1.2 に従って性質へ持ち上げる。持ち上げの過程で当事者から
出た元意図が決定的だった:

> 「もともと LINK NETWORK を作った経緯としては、ROS の TF ツリーのような
> ジオメトリをグラフ的に表示したビューが欲しかったからです。そこから魔改造したので
> 見づらくなってしまいました」

**G — モバイルの 220×160px で、「この座標系は TF ツリーのどこにいるか」と
「この実体はどの制約で誰と結ばれているか」を、視線を移さず同時に答えられること。**

### 力学 1 — 分割も委譲も成立しない (モバイルが主戦場)

当初は「包含は Outliner に委譲し、視点を分けたいなら NodeEditor のレイヤーフィルタへ」を
検討したが、当事者の運用実態で両方潰れた:

- **Outliner はモバイルでドロワー・既定非表示** (`OutlinerView.js:145` — `translateX(-100%)`)。
- **NodeEditor はほぼ使われていない** (当事者証言 — モバイルで見ていることが多いため)。

つまりモバイルでは **LINK NETWORK が唯一の常設構造ビュー**である。委譲先が画面に無い以上、
このパネルから視点を減らす方向 (減算) は Goal を壊す。当事者の
「SpatialLink の関係性と CF の関係性は同時に見たい」は運用制約から出た正当な要求。

### 力学 2 — これは「2 視点の重畳」ではなく「1 グラフの 2 辺クラス」

重要な訂正。ADR-048 §2.2.1 が既に正確な定式化を持っていた:

> CF ツリーは運動学的**全域木 (spanning tree)**、SpatialLink はループを閉じる辺を含む
> 完全な制約グラフ (URDF 流、ADR-038)

したがって画面に載っているのは分けるべき 2 つの視点ではなく、**1 つのグラフの木辺と
非木辺 (cotree edge)** である。全域木 + 余木辺を同時に描くのは既知の作図問題で、標準解は
「分割」ではなく **「木に幾何 (座標) を持たせ、非木辺を明示的に *余り* として上に乗せる」**。
当事者の「同時に見たい」は正しい目標であり、Goal と可読性は対立していない。壊れているのは
**幾何を持つ側の木が、TF ツリーになっていない**ことである。

### 力学 3 — 魔改造の残渣は 3 つの具体的欠陥

- **D1 ノード集合が 2 種類の実体を 1 軸に混ぜている。** TF ツリーのノードは座標系だけ。
  しかし現状のレイヤ 0 は **Solid** で、これは TF フレームではない (ADR-037 §1 — body frame は
  Origin CF)。ROS の TF ツリーなら Origin が根に来る。「上に item name の行」はこの
  category error が画面にそのまま出たもので、Y 軸は「TF 深さ」でも「包含深さ」でもない
  混合物になっている。**苦情の一次原因はここ。**
- **D2 Origin 行が識別情報を持たない。** Origin CF は Solid ごとにちょうど 1 つ・名前は常に
  `Origin`・編集不可 (ADR-037 §1/§4)。N 個の Solid に対して "Origin" が N 個並ぶ行が、
  `LinkNetworkView.js:345` の `L >= 3` 判定を**単独で成立させて**パネルを最大高 (160px) に
  押し上げ、本命のユーザー CF を潰れた最下行に押し込んでいる。
  傍証: `src/layout/LayoutDecompiler.js:111` は DSL 出力で auto-Origin を **fold** している —
  DSL 層は既に「Origin はユーザーにとって意味を持たない」と判定済みで、パネルだけが
  同意していなかった。
- **D3 木辺と非木辺の視覚差が、元意図と逆を向いている。** 木辺は
  `rgba(255,255,255,0.18)` の最も薄い線 (`LinkNetworkView.js:491`)。TF ツリーとして
  読ませたいなら **木辺こそ骨格**で最も読めるべきである。ADR-048 §2.2.1 は
  「視覚差を強め、凡例を提示する」と決めたが**未実装のまま**残っていた
  (「本 ADR では決定のみ、コードは別途」)。

### 力学 4 — 同じ混乱の 2 回目

ADR-048 §2.2.1 は「ノードが複数の親を持っているように見える」という混乱を既に 1 度
記録している。今回は「行の意味が読めない」という別の顔で 2 回目。同じ根本
(*木の幾何が TF を表していない*) が 2 つの無関係な文脈で出たので、憲法「After fixing a bug」
Q2 の昇格条件を満たす — 個別修正ではなく構造で消す。

## Options considered

- **A: 2 パネルに分割** (当事者の初案) — 包含専用ビューは劣化版 Outliner (同じ事実の第二の源、
  §1.1) になり、制約専用ビューは足場を失って ADR-048 が明示的に排除した「散布した力学
  レイアウト」に戻る。両側で退行。かつモバイルでは 2 枚を置く画面が無い。**却下。**
- **B: パネル内にレンズ切替トグル (構造 / 制約)** — 第二の源は作らないが、
  「同時に見たい」を切替コスト 1 クリックで壊す。パネルの価値は *at a glance* なので
  本末転倒。加えてトグルはモードを 1 つ増やす (§1.4 の閾値を無意味に押し上げる)。**却下。**
- **C: NodeEditor のレイヤーフィルタへ誘導** (`NodeEditorView.js:205` に既存) —
  機能としては既に正しい形で存在するが、当事者はモバイル主用途で NodeEditor を使っていない。
  導線を足しても使われない場所への導線。**却下** (NodeEditor 自体は現状維持)。
- **D: Solid をノードから降格し、囲い (グループ帯) + ラベルにする** — TF ツリーとしては
  正しくなるが、**Solid 自身が SpatialLink の端点になれる** (`_hitAnyEntityForLink` は Solid も
  注釈もヒットする) ため、「帯に矢印が刺さる」という新しい特殊ケースを生む。
  帯の縁を光らせる/帯端に小ノードを出す等の追加意匠が必要で、複雑性が増える。**却下。**
- **E: Solid と その Origin CF を 1 つのノードに融合する** — ↓ 採用。
- **F: 現状維持 + 凡例だけ足す (ADR-048 §2.2.1 の最小実装)** — D3 は緩和するが D1/D2 は残る。
  凡例は「読み方の説明書」であって、読みにくさの原因ではない。説明書が要る絵は
  まだ直っていない。**却下** (凡例自体は E に含めて実施)。

## Decision — Strategy (§1.2 Strategy)

### E1. Solid と Origin CF は 1 つの融合ノードとして描く

当事者の指摘が決め手だった:

> 「Solid は Origin の可視性を上げるためのオブジェクトなので、Solid が存在するなら
> 同じ数だけ Origin は必ず存在します」

Solid : Origin CF は **1:1 全単射**で、Origin は Solid の body frame (ADR-037 §1 —
Solid の重心・姿勢に一致) である。ゆえに両者は画面上 1 つのノードに融合できる:

| | 現状 | 本 ADR |
|---|---|---|
| 行 0 | Solid (item name) | **融合ノード** = TF 根 |
| 行 1 | Origin CF ("Origin" × N) | ユーザー CF |
| 行 2 | ユーザー CF | (消える → `L = 2`) |
| ノードの TF 上の正体 | Solid (TF フレームではない) | **Origin CF** (body frame) |
| ラベル | "Origin" (無情報) | **Solid 名** (body frame の識別名として正しい) |

これが同時に解くもの:

- **D1** — ノード集合が純粋に座標系になり、category error が消える。Y 軸は TF 深さのみを
  意味する。
- **D2** — 無情報の "Origin" 行が消え、`L >= 3` が解け、ユーザー CF が最下行の圧迫から
  解放される。
- **D の特殊ケース** — Solid 端点のリンクは融合ノードに刺さるだけ。囲いという概念ごと
  不要になり、追加意匠はゼロ。
- **「Origin が真ん中」** — Origin は TF 根として**最上段**に来る。ROS ユーザーが
  期待する位置であり、苦情が文字通り消える。

**選択の往復規則** (融合ノードは 2 実体を代表するので明示する): Origin CF は編集ロック済み
(ADR-037 §4) で操作対象になり得ないため、**クリック → Solid を選択**。逆向きは
**Solid / Origin CF いずれの 3D 選択でも融合ノードがハイライト**する。

**融合しない根**: Solid 以外の根 (`annot-line` / `annot-region` / `annot-point` /
`measure` / `sketch` / `imported`) は body frame を持たないので、従来どおり行 0 の
素のノードとして残る。

### E2. 木辺を骨格に戻し、凡例を出す (ADR-048 §2.2.1 の未実装決定の回収)

視覚差の**向き**を反転する。TF ツリーが主題なのだから、木辺 (`parentId`) が最も読める
実線の骨格であり、SpatialLink は色付きの弧としてその上に乗る「余りの辺」として読める
こと。marching-ants を親子線に使わない ADR-048 §2.2 の判断は維持する (アニメーションは
意味的関係の符号)。凡例は「木辺 = TF 親子 / 色付き弧 = 制約」の 2 行で足り、
D1/D2 を直した後は説明書ではなく確認になる。

### E3. レイアウトを純粋関数へ切り出す

`_runLayout()` は現在 `this._nodes` を変異する副作用付きで、原則 #3 (純粋/副作用の分離) に
反しており、そのためにテストが 1 本も無い。
`computeLayout(entityInfos, links) → { nodes, edges, rows }` の純粋関数に切り出し、
`LinkNetworkView` は描画のみを持つ。ADR-048 の核心性質「同一シーン → 同一ピクセル」は
このとき初めて機械で固定される。

### 契約 — 変えないもの

`AppController._updateLinkNetwork()` の `entityInfos` = `{ name, type, parentId }` と
`update(entityInfos, links)` シグネチャは**不変**。融合判定に必要な情報 (Solid か否か =
`type`、親子 = `parentId`) は既に渡っている。ADR-048 §2.4 の「Controller は thin のまま」を
そのまま継承する。

### 非目標 (このADR / このPRでは扱わない)

- `name === 'Origin'` の inline 再導出 **22 箇所 / 10 ファイル**の全面移行
  (`isOriginFrame` / `findOriginFrame` の新設と `IDENTITY_RULES` 登録)。
  これは ADR-090 で `robot_base` に対して潰した「名前で同一性を決める」の再来であり、
  必ずやるが**独立した PR**として行う (当事者判断)。本 ADR の実装は、その述語が
  存在する前提で 23 箇所目を作らないことだけを要求する。→ 下記 §波及。
- パネルのスクロール / ズーム (ADR-048 §2.3 で MVP 外と決めた線を動かさない)。
- NodeEditor の変更。

## Consequences — Evidence と tradeoff (§1.2 Evidence)

### 肯定的

- 苦情が構造ごと消える。「Origin が真ん中」は行が消えることで、「item name が上」は
  それが TF 根のラベルになることで解決する。対症的なラベル調整ではない。
- パネル実効高が 1 行分 (約 1/3) 空く。`L >= 3` が解けるので `MAX_PANEL_H` への
  昇格が起きにくくなり、Map 縦ツールバーとのクリアランス問題 (ADR-048 §2.3) からも
  余裕が生まれる。
- ノードが「TF フレーム」1 種類になるので、将来 ROS TF (`/tf` エコー等) と対応づける
  余地が開く。元意図への回帰。
- ADR-048 §2.2.1 の未実装決定が閉じる。

### 受け入れるコスト / 否定的

- 融合ノードは 2 実体を代表するため、選択の往復に非対称な規則 (クリック → Solid、
  ハイライト ← 両方) が必要になる。規則は 1 箇所に閉じるが、規則自体は増える。
- Solid と Origin CF を別々に見分けたい場面 (Origin CF だけを選びたい等) がパネルから
  できなくなる。Origin CF は編集ロック済みなので実害は無いと判断したが、これは
  **仮説**であり、当事者の実利用で反証されうる。
- 絵が変わるので、ADR-048 §3 が可能性として書いたスクリーンショット回帰の基準線が
  (もし作られていれば) 更新対象になる。

### 検証 (証拠)

**本 ADR 時点の証拠はすべて未来形である** — 実装は後続 PR。Status を Proposed に
留めているのはこのため。証拠として設置するもの:

- `src/view/LinkNetworkLayout.test.js` (新設 — `src/**/*.test.js` は glob 実行なので
  置くだけで走る):
  - **TF 不変条件**: 非根ノードは必ず親より下の行にある / 木辺だけを辿ると
    Solid ごとに単一根へ到達する。← 「Y 軸は TF 深さのみを意味する」という本 ADR の
    新しい規律は、散文ではなく**ここで問われる** (憲法 Q3)。
  - **融合の不変条件**: 融合ノードは常に Origin CF の TF 位置を持ち、ラベルは Solid 名。
    Solid 端点のリンクと Origin CF 端点のリンクが**同一ノードに解決**される。
  - **基数** (原則 #31): 0 リンク (パネル非表示) / ノード 1 個 / **Solid N 個** —
    N でしか出ない欠陥 (行の重なり・ラベル衝突) は 1 個の fixture では絶対に見えない
    (ADR-093 の lockstep と同じ構図)。
  - **決定性**: 同一入力 → 同一出力。ADR-048 の核心性質を初めて機械で固定する。
- 同一性: `isOriginFrame` を `src/IdentityContainment.test.js` の `IDENTITY_RULES` に登録
  (別 PR)。以後の再導出は機械が落とす。
- 実物: モバイル幅 390px の Playwright スクリーンショット。記録様式は
  `docs/dogfooding/README.md`。

証拠が未来形主体なので、鎖の正本は **GSN 論証木
`docs/gsn/adr-094-link-network-tf-tree.gsn`** に外部化する。上の箇条書きは入口であって
goal ごとの支えの有無は木側が持つ (第二の源にしない — 核 §1.1)。木の状態は
`pnpm test:gsn` が検査し、支えの無い goal を機械が落とす。

> **改訂 (2026-07-26)**: 初稿は「1 イテレーションで検証可能な範囲に収まるので木は起こさない」
> と判断していた。この判断は撤回する。核 §3 の GSN トリガは「Evidence が大半未来形」で
> 条件付きだったが、**ADR 起票時は無条件に木を起こす**規律へ改めた
> (`.claude/commands/whiteboard.md` §6)。理由は本 ADR 自身が実例になっている —
> 実装前 ADR の証拠は定義上ほぼ全部が未来形であり、「1 イテレーションで閉じる見込み」は
> 書いた本人の見込みでしかなく、未着手の枝と完了した枝が散文では同じ顔で並ぶ
> (原則 #31)。木にすれば `support-exploring` の宣言が必須になり、機械が問う。

事業木 (`docs/gsn/profit-growth.gsn`) への接続予定先は
`RevenueMaximized → ByAdoptionFunnel → OtherAdoptionBranchesCovered`
(uuid `b8912337-6f34-4ed4-8cf7-87e2beacc70e`) — その goal の assumption が
「本木はコンテキスト入力の枝のみを展開している」と宣言している欠落枠に、モバイルでの
可読性はそのまま入る。**接続は実装 PR で行う**: いま接ぐと証拠が全部未来形のまま事業木の
`ToBeDeveloped` を増やすだけで、木が「証拠実行可能」でなくなる。テストが実在した時点で
solution として吊る (保留理由は `.gsn` の `context BusinessTreeAttachPoint` に記録済み)。

### 波及 (blast radius)

- `src/view/LinkNetworkView.js` — 主戦場 (レイアウト + 描画 + 凡例)。
- `src/view/LinkNetworkLayout.js` (新設) — 純粋レイアウト。
- `src/controller/AppController.js` — **データ契約は不変**。融合ノードのクリックが
  Solid id を返すため、`onSelectEntity` の呼び出し側は無改変で動く。
- `docs/STATE_LEDGER.md` — この実体の行が存在しなかったので新設 (本 PR で実施)。
- **依存する別 PR**: `isOriginFrame` / `findOriginFrame` の新設。本 ADR の実装が
  「これは Origin CF か」をレイアウトで判定するため、述語が無ければ 23 箇所目の
  inline 再導出になる。**述語 PR を先行させる。**
- 変えないもの: Outliner、NodeEditor、SpatialLink ドメイン、契約パッケージ。

## Lens notes

- **グラフ (§1.3)**: blast radius は `LinkNetworkView` から外へほとんど出ない。
  `entityInfos` 契約を動かさない選択がこれを担保している (ADR-048 §2.4 の継承)。
- **状態機械 (§1.4)**: このパネルの可視性は平坦な 3 状態ではなく
  **`forceHidden` (外部オーバーレイ所有) × `collapsed` (ユーザー所有) の直交 2 軸**である。
  平坦化すると「Context DSL デモ中にユーザーが畳んだ」が表現不能になる。台帳の
  「Map 注釈ビューの motion」行 (ADR-093) と同じ形。直交性を明示すれば不正遷移が
  事故にならないため、`STATE_TRANSITIONS.md` の節は起こさない (§5 過剰モデリング禁止)。
- **同一性 (§1.1)**: 本 ADR の実装が触れる「Origin CF の同一性」は既に 22 箇所へ
  散っている。これは ADR-090 が `robot_base` に対して閉じた欠陥の未移行分であり、
  台帳・原則の両方が予告していた再発である。分離 PR で閉じる。
- **様態**: 本件は逐次フロー (BPMN) ではなく描画の純関数であり、状態遷移も
  ユーザー事象駆動 (CMMN 的) だが、いずれのレンズも新しい構造を要求しなかった。
