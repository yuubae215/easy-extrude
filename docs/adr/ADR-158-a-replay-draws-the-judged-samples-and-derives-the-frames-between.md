## Context — Goal と力学

### 要求の来歴

当事者の要求は 3 段で動いた (2026-09-30):

1. 「干渉判定は重いので、バックエンドに処理させてフロントは定期的に共有してもらう。
   リフレッシュレートは 30fps とか」
2. 「もともとフロントと BFF の間には Rust のゼロコピーのアイデアがなかった?」
3. 「干渉の状態遷移は重要。どの状態で干渉したかも分析できる」

(3) は ADR-157 が事実の側 (相の内訳・全相分析) として入れた。(1) は**解の形**で来ている:
「30fps で共有」は手段で、欲しい性質は別にある。この ADR はそれを持ち上げ、再生の設計と
**それを使う場面**を残す。

### (1) を持ち上げる — なぜ「30fps で取りに行く」は形が違うか

干渉判定は**静止したシーンに対する判定**で、入力 (シーン・宣言) が変わらない限り答えも
変わらない。時間とともに変わるのは**ロボットの姿勢**であって判定ではない。したがって
「動いているロボットが各瞬間に当たるか」を見たいなら、必要なのは

- 判定の**事実**を 1 回受け取ること (どの相の、どの時点で、どの部位が、何に当たるか)
- 見せる**フレーム**を手元で作ること

の 2 つで、前者はワイヤ、後者はクライアントの仕事である (原則 #29)。周期で取りに行く形は
原則 #5 (ポーリングしない) と原則 #24 (周期で更新されるキャッシュは閉路の辺) に反し、
しかも同じ答えを毎秒 30 回受け取るだけになる。

量で比べる。候補 1 つ・相 3 つ・相ごとの標本 6 点・標本ごとに関節 6 + TCP 姿勢 7 の実数:

$$B_{\text{once}} = 3 \times 6 \times (6 + 7) \times 4\,\text{B} \approx 0.9\,\text{kB}\quad(\text{JSON で} \approx 3\,\text{kB})$$

これを候補 5 件ぶん**1 回だけ**受け取れば、再生が何分続いても通信は増えない。30fps で
同じ姿勢を送り続けると

$$B_{\text{stream}} = 30\,\text{fps} \times (6 + 7) \times 4\,\text{B} \approx 1.6\,\text{kB/s}$$

で (同じバイナリ換算)、再生 1 秒で一括受け取りを超え、10 秒で約 17 倍になる。しかも**判定されていない姿勢**を運ぶことになる
(送った姿勢のどれが core の判定した標本なのか、受け手には区別できない)。

(2) のゼロコピー (ADR-027) はブラウザ内の Wasm → Worker → メインスレッドの経路で、
メッシュのような大きなバッファを毎フレーム渡すときに効く。上の見積りのとおり再生が運ぶ
事実は kB 単位なので、**この用途ではゼロコピーは要らない**。要るのは経路の速さではなく、
描くものと判定したものが同じであること。

### Goal (性質)

- **G1 (描いたものが判定したもの)**: 再生で「当たった」と見えるフレームは、core が
  判定した標本そのもの (または、その間を補った表示上の補間であると区別できるもの) である。
  補間のフレームを判定済みの姿勢のように見せない。
- **G2 (事実は 1 回、フレームは手元)**: 再生の長さ・速さ・フレームレートは通信量にも
  core の負荷にも効かない。30fps でも 60fps でも、コマ送りでも同じ事実から描く。
- **G3 (場面に効く)**: 下の §使う場面 のうち、少なくとも「棄却の理由を見る」
  (S1) で、パネルの数字だけより早く「どの宣言を変えればよいか」に着く。

## 使う場面の分析

誰が・いつ・何を知りたくて再生を見るかを先に並べる。設計の優先順位はこの表から出る。

| # | 場面 | 見る人 | 知りたいこと | 再生の見せ方 | 価値 (利益の式の項) |
|---|---|---|---|---|---|
| **S1** | **棄却の理由を見る** — 全相分析で「引き上げ × 棚 — 9」と出た | 設計者 | どの瞬間に、どこが、どれくらい食い込むか | 当たった標本で**止まる**。スクラブで前後を見る。当たった部位と障害物を強調 | **L_blind** (どの仕様を変えるかを探すループ) を縮める — 主 |
| **S2** | **宣言を変えて比べる** — 引き上げを 80 → 50mm、向きを worldUp → reverseApproach | 設計者 | 変えたら当たらなくなったか、余裕はどれくらいか | 前回と今回を同じスクラブ位置で並べる (前回は stale と明示) | L_blind / t_m (再評価までの手間) |
| **S3** | **採用候補の通しを見せる** — レビュー・顧客説明・安全確認 | 設計者 → 第三者 | この候補がピック動作の全体を通して何にも当たらないこと | 待機 → 置く までを一定速度で通しで再生。判定していない相は**判定していないと見える**色で | p_operate (画面を読み、信じて使い続ける率) |
| **S4** | **セルの配置を詰める** — 棚・トレー・ロボットの位置を動かしては再探索 | 設計者 | 配置の変更が動作のどこに効くか | 再探索のたびに最後に見ていた相・時点を保って再生し直す (ライブ追従ではない — 再探索はイベント駆動) | L_hidden (後から見つかる依存) |
| **S5** | **現場でスマホで確かめる** — セルの前で | 立会い者 | 画面の候補が目の前の状況と合うか | コマ送り (標本ごと) を既定に。reduced-motion では静止した標本の列 | p_operate |

### この再生で**ない**もの (範囲の外に置くのではなく、まだ決めていない)

- **実機のリアルタイム表示 (デジタルツイン)** — 動いている実ロボットの関節角を流して
  表示する用途。これは**判定の事実**ではなく**観測のテレメトリ**で、ワイヤの性質が違う
  (連続して変わる値なので、ここで初めてストリームと周期が意味を持つ)。要るとしたら別の
  契約・別の経路 (WebSocket 等) の別 ADR である。
- **サイクルタイムの見積り** — 実時間の軸 (何秒で終わるか) は速度・加速度・躍度の制限と
  軌道の時間最適化 (ADR-053 が名指しした ruckig) の答えで、判定とは別の計算である。
  この ADR の時間軸は**相の中の進み具合 s ∈ [0, 1]** であって秒ではない (D3)。

## Options considered

- **A: 判定した標本 (関節 + TCP 姿勢 + 当たり) を 1 回で受け取り、間はクライアントが補間して
  再生する (採用予定)** — tradeoff: response の版上げが 1 回要る。補間のフレームは判定されて
  いないことを見せる規律が要る。
- **B: 30fps で core / BFF から姿勢をストリームする** — tradeoff: 同じ事実を繰り返し運び、
  判定していない姿勢と判定した姿勢が区別できない。core が再生の速さに縛られる。
  実機テレメトリ用の経路としては正しい形なので、その用途が来たら別 ADR で再評価する。
- **C: クライアントが TCP の経路と IK を自分で解いて再生する (ワイヤに何も足さない)** —
  tradeoff: IK の解の選び方 (8 解から代表を選ぶ規則、ADR-127 D5) は**アイデア**なので
  フロントに写せない (ADR-146 軸 1)。プリグラスプの距離も core の既定でワイヤに無い。
  写せば「描いた腕」と「判定した腕」が別の源から来る — ADR-150 が閉じた欠陥の再演。
- **D: 現状維持 (相の内訳と全相分析の数字だけ)** — tradeoff: S1 は数字から想像するしかない。

## Decision — Strategy (Proposed)

### D1. ワイヤに載せるのは「判定した標本」だけ

全相分析 (ADR-157 D6) を求めたとき、core は再生を求められた候補について、**判定に使った
標本の列**を返す:

```jsonc
{ "phase": "lift", "samples": [
    { "s": 0.2, "joints": [...6], "tcp": [x,y,z,qx,qy,qz,qw],
      "hits": [ { "part": "held", "obstacleIndex": 3 } ] },
    ...
] }
```

- `s` は相の中の進み具合 (0 = 相の始点、1 = 終点)。**秒ではない** (D3)。
- `joints` は core が解いた関節角。腕を判定していない相 (今日の lift) は `null` を
  **宣言として**載せ、フロントは腕を描かない (または描くが「判定していない」と見せる)。
- `hits` はその標本で当たったもの。空配列 = その標本で当たらなかった (判定した)。
- 判定していない相は標本を持たない (ADR-157 の `unevaluated{reason}` がそのまま理由)。

どの候補の再生を返すかは求めた側が選ぶ (返した候補の rank、または全相分析の当たりごとの
代表)。**代表の選び方 (どの棄却候補が「典型」か) はアイデア**なので core が決める。

### D2. 間のフレームはクライアントの導出で、判定済みと区別して描く

標本と標本の間は、関節空間の線形補間でフロントが作る (公知の閉形式 — ADR-146 軸 3。
順運動学は既に `src/robotics/urKinematics.js` が導出として持つ)。規律:

- **判定した標本のフレーム**と**補間のフレーム**は描き分ける (例: 標本の瞬間だけ実線の
  輪郭、間は薄く)。補間のフレームに当たりの色を付けない — 補間の姿勢で当たるかは誰も
  判定していない。
- 当たりの強調は「当たった標本」に付く。2 つの標本の間で当たり始めた正確な時刻は
  **分からない**と表示する (「s = 0.4 の標本で初めて当たった」であって「s = 0.33 で接触」
  ではない)。

### D3. 時間軸は相ごとの s で、再生速度とフレームレートはクライアントの設定

- 再生時刻 → (相, s) の写像はクライアントが持つ。相ごとの長さは既定で等分し、
  利用者が速さを変えられる。**フレームレートは契約に現れない** — 30fps も 60fps も
  requestAnimationFrame の都合であって事実ではない。
- 実時間 (秒) の軸を載せるのはサイクルタイムの見積りが決まったとき (ruckig 等による
  時間付け)。そのとき `s` に加えて `t` を**足す**版上げになる。

### D4. 再生の状態は探索・分析と別に持ち、鮮度は導出する

再生は `context.graspAnalysis` の結果 (ADR-157 D6) の上に乗る**表示の状態**
(再生中 / 一時停止 / スクラブ位置) で、ワイヤにも文書にも保存しない。分析が stale に
なれば再生も stale と表示する (鮮度は分析と同じ導出 — 原則 #23)。

### D5. 動きの役割を名指す — 既存の進入スライドとは別物

原則 #30 (Motion Tier) に従い、実装の前に役割を宣言する:

| 動き | 役割 | 何を証明するか |
|---|---|---|
| 既存の進入スライド (ADR-065 Phase 5、400ms の 3 拍) | **Delight** | 何も証明しない。慣例の方向 (ADR-059 §A-3) で描いた演出 |
| この再生 | **Fact** | core が判定した標本の列。当たりはその標本の事実 |

2 つを同じ見た目にしない。進入スライドを「判定された経路」と読ませたら、それは役割を
偽る動き (原則 #30 の不採用条件) になる。再生の所有者は `MotionGovernor`、reduced-motion
の読み取りは `src/theme/motion.js` ただ 1 箇所で、reduced のときは**静止した標本の列**
(コマ送り) を見せる (S5 の既定と同じ形)。

## Consequences — Evidence と tradeoff

- 肯定的: S1 で「どの瞬間にどこが当たるか」が数字ではなく絵で見える。通信量は再生の長さに
  依らない。描いた腕と判定した腕が同じ源から来る。
- 受け入れるコスト / 否定的: response の版上げ 1 回 (v8 → v9 見込み)。全相分析で標本を
  返す候補を増やすと応答が大きくなる (候補数に線形 — 上の見積りで 1 候補 ≈ 3 kB)。
  補間のフレームは判定されていないという規律を画面の描き分けで守る必要がある。
- 検証(証拠): goal ごとの支えの正本は
  `docs/gsn/adr-158-a-replay-draws-the-judged-samples-and-derives-the-frames-between.gsn`。
  Proposed なので証拠は未来形 (木の側で support-exploring / unexplored を宣言)。
- 波及(blast radius): core (phases の標本を捨てずに返す) · 契約 (版上げ) · スタブ
  (標本を捏造しない — 再生はバックエンドのときだけ、ADR-157 D6 と同じ) · フロント
  (再生の状態・スクラブ UI・ゴースト/腕の描画・MotionGovernor)。**触らない**: ADR-017 の
  WebSocket、ADR-027 の Wasm 経路。
