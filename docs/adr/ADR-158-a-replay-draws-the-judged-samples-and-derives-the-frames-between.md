## Context — Goal と力学

### 要求の来歴

当事者の要求は 3 段で動いた (2026-09-30):

1. 「干渉判定は重いので、バックエンドに処理させてフロントは定期的に共有してもらう。
   リフレッシュレートは 30fps とか」
2. 「もともとフロントと BFF の間には Rust のゼロコピーのアイデアがなかった?」
3. 「干渉の状態遷移は重要。どの状態で干渉したかも分析できる」

(3) は ADR-157 が事実の側 (相の内訳・全相分析) として入れた。(1) は**解の形**で来ている:
「30fps で共有」は手段で、欲しい性質は別にある。この ADR はそれを持ち上げ、再生の設計と
**それを使う場面**を残す。

### (1) を持ち上げる — なぜ「30fps で取りに行く」は形が違うか

干渉判定は**静止したシーンに対する判定**で、入力 (シーン・宣言) が変わらない限り答えも
変わらない。時間とともに変わるのは**ロボットの姿勢**であって判定ではない。したがって
「動いているロボットが各瞬間に当たるか」を見たいなら、必要なのは

- 判定の**事実**を 1 回受け取ること (どの相の、どの時点で、どの部位が、何に当たるか)
- 見せる**フレーム**を手元で作ること

の 2 つで、前者はワイヤ、後者はクライアントの仕事である (原則 #29)。周期で取りに行く形は
原則 #5 (ポーリングしない) と原則 #24 (周期で更新されるキャッシュは閉路の辺) に反し、
しかも同じ答えを毎秒 30 回受け取るだけになる。

量で比べる。候補 1 つ・相 3 つ・相ごとの標本 6 点・標本ごとに関節 6 + TCP 姿勢 7 の実数:

$$B_{\text{once}} = 3 \times 6 \times (6 + 7) \times 4\,\text{B} \approx 0.9\,\text{kB}\quad(\text{JSON で} \approx 3\,\text{kB})$$

これを候補 5 件ぶん**1 回だけ**受け取れば、再生が何分続いても通信は増えない。30fps で
同じ姿勢を送り続けると

$$B_{\text{stream}} = 30\,\text{fps} \times (6 + 7) \times 4\,\text{B} \approx 1.6\,\text{kB/s}$$

で (同じバイナリ換算)、再生 1 秒で一括受け取りを超え、10 秒で約 17 倍になる。しかも**判定されていない姿勢**を運ぶことになる
(送った姿勢のどれが core の判定した標本なのか、受け手には区別できない)。

(2) のゼロコピー (ADR-027) はブラウザ内の Wasm → Worker → メインスレッドの経路で、
メッシュのような大きなバッファを毎フレーム渡すときに効く。上の見積りのとおり再生が運ぶ
事実は kB 単位なので、**この用途ではゼロコピーは要らない**。要るのは経路の速さではなく、
描くものと判定したものが同じであること。

### Goal (性質)

- **G1 (描いたものが判定したもの)**: 再生で「当たった」と見えるフレームは、core が
  判定した標本そのもの (または、その間を補った表示上の補間であると区別できるもの) である。
  補間のフレームを判定済みの姿勢のように見せない。
- **G2 (事実は 1 回、フレームは手元)**: 再生の長さ・速さ・フレームレートは通信量にも
  core の負荷にも効かない。30fps でも 60fps でも、コマ送りでも同じ事実から描く。
- **G3 (場面に効く)**: 下の §使う場面 のうち、少なくとも「棄却の理由を見る」
  (S1) で、パネルの数字だけより早く「どの宣言を変えればよいか」に着く。

### この再生で**ない**もの (範囲の外に置くのではなく、まだ決めていない)

- **実機のリアルタイム表示 (デジタルツイン)** — 動いている実ロボットの関節角を流して
  表示する用途。これは**判定の事実**ではなく**観測のテレメトリ**で、ワイヤの性質が違う
  (連続して変わる値なので、ここで初めてストリームと周期が意味を持つ)。要るとしたら別の
  契約・別の経路 (WebSocket 等) の別 ADR である。
- **サイクルタイムの見積り** — 実時間の軸 (何秒で終わるか) は速度・加速度・躍度の制限と
  軌道の時間最適化 (ADR-053 が名指しした ruckig) の答えで、判定とは別の計算である。
  この ADR の時間軸は**相の中の進み具合 s ∈ [0, 1]** であって秒ではない (D3)。

## Options considered

- **A: 判定した標本 (関節 + TCP 姿勢 + 当たり) を 1 回で受け取り、間はクライアントが補間して
  再生する (採用予定)** — tradeoff: response の版上げが 1 回要る。補間のフレームは判定されて
  いないことを見せる規律が要る。
- **B: 30fps で core / BFF から姿勢をストリームする** — tradeoff: 同じ事実を繰り返し運び、
  判定していない姿勢と判定した姿勢が区別できない。core が再生の速さに縛られる。
  実機テレメトリ用の経路としては正しい形なので、その用途が来たら別 ADR で再評価する。
- **C: クライアントが TCP の経路と IK を自分で解いて再生する (ワイヤに何も足さない)** —
  tradeoff: IK の解の選び方 (8 解から代表を選ぶ規則、ADR-127 D5) は**アイデア**なので
  フロントに写せない (ADR-146 軸 1)。プリグラスプの距離も core の既定でワイヤに無い。
  写せば「描いた腕」と「判定した腕」が別の源から来る — ADR-150 が閉じた欠陥の再演。
- **D: 現状維持 (相の内訳と全相分析の数字だけ)** — tradeoff: S1 は数字から想像するしかない。

## Decision — Strategy (Proposed)

### D1. ワイヤに載せるのは「判定した標本」だけ

全相分析 (ADR-157 D6) を求めたとき、core は再生を求められた候補について、**判定に使った
標本の列**を返す:

```jsonc
{ "phase": "lift", "samples": [
    { "s": 0.2, "joints": [...6], "tcp": [x,y,z,qx,qy,qz,qw],
      "hits": [ { "part": "held", "obstacleIndex": 3 } ] },
    ...
] }
```

- `s` は相の中の進み具合 (0 = 相の始点、1 = 終点)。**秒ではない** (D3)。
- `joints` は core が解いた関節角。腕を判定していない相 (今日の lift) は `null` を
  **宣言として**載せ、フロントは腕を描かない (または描くが「判定していない」と見せる)。
- `hits` はその標本で当たったもの。空配列 = その標本で当たらなかった (判定した)。
- 判定していない相は標本を持たない (ADR-157 の `unevaluated{reason}` がそのまま理由)。

どの候補の再生を返すかは求めた側が選ぶ (返した候補の rank、または全相分析の当たりごとの
代表)。**代表の選び方 (どの棄却候補が「典型」か) はアイデア**なので core が決める。

### D2. 間のフレームはクライアントの導出で、判定済みと区別して描く

標本と標本の間は、関節空間の線形補間でフロントが作る (公知の閉形式 — ADR-146 軸 3。
順運動学は既に `src/robotics/urKinematics.js` が導出として持つ)。規律:

- **判定した標本のフレーム**と**補間のフレーム**は描き分ける (例: 標本の瞬間だけ実線の
  輪郭、間は薄く)。補間のフレームに当たりの色を付けない — 補間の姿勢で当たるかは誰も
  判定していない。
- 当たりの強調は「当たった標本」に付く。2 つの標本の間で当たり始めた正確な時刻は
  **分からない**と表示する (「s = 0.4 の標本で初めて当たった」であって「s = 0.33 で接触」
  ではない)。

### D3. 時間軸は相ごとの s で、再生速度とフレームレートはクライアントの設定

- 再生時刻 → (相, s) の写像はクライアントが持つ。相ごとの長さは既定で等分し、
  利用者が速さを変えられる。**フレームレートは契約に現れない** — 30fps も 60fps も
  requestAnimationFrame の都合であって事実ではない。
- 実時間 (秒) の軸を載せるのはサイクルタイムの見積りが決まったとき (ruckig 等による
  時間付け)。そのとき `s` に加えて `t` を**足す**版上げになる。

### D4. 再生の状態は探索・分析と別に持ち、鮮度は導出する

再生は `context.graspAnalysis` の結果 (ADR-157 D6) の上に乗る**表示の状態**
(再生中 / 一時停止 / スクラブ位置) で、ワイヤにも文書にも保存しない。分析が stale に
なれば再生も stale と表示する (鮮度は分析と同じ導出 — 原則 #23)。

### D5. 動きの役割を名指す — 既存の進入スライドとは別物

原則 #30 (Motion Tier) に従い、実装の前に役割を宣言する:

| 動き | 役割 | 何を証明するか |
|---|---|---|
| 既存の進入スライド (ADR-065 Phase 5、400ms の 3 拍) | **Delight** | 何も証明しない。慣例の方向 (ADR-059 §A-3) で描いた演出 |
| この再生 | **Fact** | core が判定した標本の列。当たりはその標本の事実 |

2 つを同じ見た目にしない。進入スライドを「判定された経路」と読ませたら、それは役割を
偽る動き (原則 #30 の不採用条件) になる。再生の所有者は `MotionGovernor`、reduced-motion
の読み取りは `src/theme/motion.js` ただ 1 箇所で、reduced のときは**静止した標本の列**
(コマ送り) を見せる (S5 の既定と同じ形)。

## Consequences — Evidence と tradeoff

- 肯定的: S1 で「どの瞬間にどこが当たるか」が数字ではなく絵で見える。通信量は再生の長さに
  依らない。描いた腕と判定した腕が同じ源から来る。
- 受け入れるコスト / 否定的: response の版上げ 1 回 (v8 → v9 見込み)。全相分析で標本を
  返す候補を増やすと応答が大きくなる (候補数に線形 — 上の見積りで 1 候補 ≈ 3 kB)。
  補間のフレームは判定されていないという規律を画面の描き分けで守る必要がある。
- 検証(証拠): goal ごとの支えの正本は
  `docs/gsn/adr-158-a-replay-draws-the-judged-samples-and-derives-the-frames-between.gsn`。
  Proposed なので証拠は未来形 (木の側で support-exploring / unexplored を宣言)。
- 波及(blast radius): core (phases の標本を捨てずに返す) · 契約 (版上げ) · スタブ
  (標本を捏造しない — 再生はバックエンドのときだけ、ADR-157 D6 と同じ) · フロント
  (再生の状態・スクラブ UI・ゴースト/腕の描画・MotionGovernor)。**触らない**: ADR-017 の
  WebSocket、ADR-027 の Wasm 経路。

## PR1 — 腕を経路に沿って測る (2026-10-15)

### 俯瞰で表に出た食い違い

D1 は標本ごとに `joints` を持つ前提で書かれていたが、Observe すると core の進入相が腕を
判定しているのは**把持姿勢の代表解 1 つだけ** (`PHASE_COVERAGE` の approach × arm =
`atEndOnly`) で、経路に沿って動くのは手の箱だけだった。lift × arm は判定していない
(`unevaluated` — DEF-058)。つまり「標本ごとの関節」は**誰も決めていない値**で、そのまま
載せれば G1 (描いたものが判定したもの) を最初の段で破る。

当事者に「腕を相に 1 個の姿勢へ割る (安い) か、複数の姿勢まで割るか」を問い、答えは
複数の姿勢まで、ただし:

> 測るだけで良いよ。回避しようとしなくてもいい。ピック姿勢で当たるか、途中経路で当たるか、
> 測るだけで良い。(2026-10-15)

### 決定

- **P1 (測る、判定しない)。** 全相分析 (`interferenceAnalysis: allPhases`) のときだけ、
  approach と lift (宣言時) の TCP の直線を 6 点に割って各点で IK を解き直し、腕
  (リンク + ツール区間) が触れる障害物を測る (`phases.arm_segments_along`)。**棄却には
  数えない** — 探索の答え (候補・ファネル・相の内訳) は 1 ビットも変わらない。通常の
  探索は 1 刻みごとに IK を解き直す重さ (DEF-038) を払わない。
- **P2 (回避しない)。** 枝はピック姿勢で判定した代表解から外へ 1 点ずつ、直前の姿勢に
  最も近い解を渡す (`UniversalRobotsIkSolver.solve_near`)。当たらない枝を探しには
  行かない (代替解の探索は DEF-037 のまま)。式は `docs/ALGORITHMS.md` §3.2c。
- **P3 (語を割る — 原則 #33)。** 被覆表に `measuredOnly` を足し、lift × arm を
  `unevaluated` (残し) から移した。「まだ決めていない」と「決めて測るだけ」を 1 語に
  兼ねさせない。`UNEVALUATED_CELLS` は 12 → 11 (残りはすべて DEF-057)。DEF-058 は決着
  (登録簿から行を消した)。
- **P4 (ワイヤ — 契約 v10)。** `interferenceAnalysis.allPhases` に**必須**の `armPath`
  (閉じた kind 判別): `undeclared` (運動学が未宣言 — 0 件ではなく理由) /
  `measured{pathSamples, atPickPose{candidates, hits}, phases[{phase, onPath, onPathOnly,
  noSolutionOnPath, hits}]}`。母集団は `candidatesAnalysed`。相の行は経路が決まっていて
  評価する相だけ (approach は常に、lift は宣言時)。`onPathOnly` = 経路でだけ当たり
  ピック姿勢では当たらない候補 = **今の判定が見ていない当たり**。
- **P5 (画面)。** 分析のカードに「arm, measured … (not used to reject)」として
  ピック姿勢 / 経路 / 経路でだけ を障害物の名前つきで出す。測っていない腕は 0 ではなく
  理由の文 (`ARM_PATH_UNMEASURED_TEXT`)。

### 実測 (同梱テンプレ、2026-10-15)

| テンプレ | 分析した候補 | ピック姿勢で当たる | 進入の経路で当たる | うち経路でだけ | 時間 (通常 → 分析) |
|---|---|---|---|---|---|
| single-arm-pedestal-cell | 36 | 4 (台座) | 2 (台座) | **0** | 13 ms → 81 ms |
| bin-picking-thin-container | 20 | — (運動学未宣言 = `undeclared`) | — | — | 3 ms → 2 ms |

今のテンプレでは「経路でだけ当たる」候補は 0 だった。経路でだけ当たる場面
(プリグラスプの腕の通り道に小さな箱) を置いたテストでは `onPathOnly ≥ 1` になり、
返る候補は変わらないことを固定した。

### 残す段

**未着手** — 再生そのもの (標本 `samples[]` をワイヤに載せる・時刻 → (相, s) の写像・スクラブ・
描き分け・`GraspGhostView` の作り直し) は後続 PR (再生の段)。標本の関節は P2 の枝で解いたもの
になるので、D1 の `joints` は「測った腕」であって判定した腕ではないことを描き分けで
言う (G1 の言い直し: 当たりとして描くのは測った事実、棄却の理由として描くのは判定した事実)。
DEF-059 (満期 `phaseTimeline`) と DEF-069 (同じ満期へ張り替え) が受ける。

## 再生の段 — R1: 判定した標本をワイヤに載せる (2026-11-01)

### 俯瞰で決めた読み方 (当事者合意 2026-11-01 — 6 点すべて推奨案)

Observe で分かった前提: core は PR1 で標本 (`ArmSample`) を既に作っていて、`measure_arm_path` が
数に集計した時点で捨てていた。手・携行物の当たり (`phase_hits`) は相ごとの集合で、s を持たない。
腕を描く入口は `stages.previewSolution` (ADR-135/147) が既に 1 つ在る。全相分析は棄却候補の
姿勢をワイヤに載せていない。

| # | 読み方 | 決定 |
|---|---|---|
| ① | どの候補の標本を返すか (D1 の「求めた側が選ぶ」) | **返した上位 N 件だけ**。棄却候補の代表 (S1 の主眼) は次の段 — 代表の選び方はアイデアなので core が決め、棄却候補の姿勢をワイヤに載せる形が要る (DEF-075) |

| ⑥ | PR の割り方 | R1 = core + 契約 (ワイヤ)、R2 = フロントの再生とゴーストの作り直し (DEF-059 / DEF-069 は R2 で閉じる)。`sampleFrame` / `betweenFrame` は画面の語で、DSL で宣言する語ではないので辞書 (`QUOTIENT_TABLE`) に行を足さない |

### 決定 (R1)

- **R1-1 (判定を割り直す、書き直さない)。** `phases.phase_replay` は判定 (`phase_hits`) と**同じ点・
  同じ幾何**で標本ごとの当たりを組む。標本ごとの当たりの和集合 (+ 判定に使った腕の当たり) は
  `phase_hits(first_only=False)` とちょうど一致する — 一致を `core/tests/test_motion_phases.py` が
  全候補・全評価相で問う (腕あり / なしの両方、当たりの在る場面で。変異 2 つで fail を確認)。
  再生の当たりは判定の**導出**であって第二の判定ではない (§1.1)。
- **R1-2 (線分は区間に帰属させる)。** tcpPath の判定は点ではなく線分なので、標本 i の tcpPath の
  当たりは直前の標本からの区間 [s_{i−1}, s_i] のもの (s = 0 の標本は区間を持たない)。引き上げの
  手・携行物は t ∈ (0, 1] (静止接触を当たりにしない — ADR-157 D5) をそのまま守る。
- **R1-3 (掃引は時点を捏造しない)。** 爪を閉じる相は開→閉の**1 つの掃引体積**で判定している
  (`_finger_sweep`) ので、標本の列ではなく相全体の `hits` だけを返す。時点を割れば判定していない
  瞬間を作ることになる (G1)。
- **R1-4 (ワイヤ — 契約 v11)。** `interferenceAnalysis.allPhases` に**必須**の `replays`
  (rank 順、返した候補ちょうどぶん、0 件なら空配列 — 欄の省略で示さない)。相は評価した相だけ、
  形は相で判別 (approach / lift = `samples[]`、close = `hits`)。秒・fps・再生速度の欄は無い
  (D3 — スキーマと core の両方で欄名の census を問う)。
- **R1-5 (重さ)。** 返した候補だけを組み直す (集計は全候補ぶん、再生は返す候補ぶん)。全相分析の
  ときだけ走る — 通常の探索は 1 ビットも 1 ミリ秒も変わらない。

## 再生の段 — R2: フロントが標本を再生する (2026-11-01)

### 俯瞰で決めた読み方 (当事者合意 2026-11-01 — 5 点すべて推奨案)

Observe で分かった前提: 腕を描く入口 `RobotStageSet.previewSolution` の authority は `solved` /
`unverified` の 2 語で、core が**測っただけ**の腕を言う語が無かった (`unverified` は「クライアントが
解いた」の意味で、入れれば 1 語が 2 つの事実を運ぶ — 原則 #33)。そして R1 は**返した候補**の標本だけを
載せるので、返る候補の判定した部位の当たりは 0 件 — 再生で見える当たりは腕の測った当たりだけ (G3 の
主眼 S1 は DEF-075 まで満たせない、と先に言った)。

| # | 読み方 | 決定 |
|---|---|---|
| ① | 腕の枝が飛ぶ所をどう見分けるか (ワイヤに枝の番号は無い) | 隣り合う標本でどれか 1 つの関節が **> π/2** 変わったら不連続 (`BRANCH_JUMP_RAD`)。表示の閾値で、判定ではない。不連続の区間では直前の標本の腕を保持し、次の標本で切り替える |
| ② | `measured` の腕の見た目 | `unverified` と同じ半透明 (新しい色を足さない — ADR-100)。キャプションで「measured (not used to reject)」と言う |
| ③ | `noSolution` の標本の腕 | 休止姿勢に戻し、その標本に「no joint solution here」と出す (直前の姿勢を持ち越すと今いない TCP の腕を描く) |
| ④ | タイムラインの長さ | 判定した相 = 1、判定していない相 = 1/4 の「not judged — 理由」の区間 (`UNJUDGED_SPAN`) |
| ⑤ | 再生の所有者 (D5 は MotionGovernor と書いていた) | Governor は transient (寿命を誰も追わない物) だけを持つ。再生は**利用者が操作する持続的な表示**なので `GraspController` (状態と時計) + `GraspGhostView` (描画) が持つ。reduced-motion の読み取りは `motion.js` の 1 か所のまま (reduced では ▶ を出さず、コマ送りだけ) |

**D5 との食い違い (⑤)**: D5 の「再生の所有者は `MotionGovernor`」は採らなかった。Governor の契約
(`spawn` → `tick → done` → `dispose`、予算超過で古いものから追い出す) は誰も寿命を追わない一時演出の
ためのもので、▶・一時停止・スクラブで利用者が握り続ける再生を入れると、予算の追い出しが利用者の再生を
黙って消しうる。役割の宣言 (Fact) と reduced-motion の境界 1 か所という D5 の本体は守っている。

### 決定 (R2)

- **R2-1 (語を割る — 原則 #33)。** 腕の authority に `measured` を足した (core が測るためだけに置いた
  腕、または再生が標本の間で補間・保持した腕)。見た目は表 `TRANSLUCENT_BY_AUTHORITY` (`solved` = 実体、
  `unverified` / `measured` = 半透明) が 1 か所で決め、未宣言の authority は throw する (原則 #31)。
  入口は `previewSolution` のまま増やさない (原則 #4)。画面の語なので辞書 (`QUOTIENT_TABLE`) には入れない。
- **R2-2 (時間軸は導出)。** `phaseTimeline` が相を動作の順に区間へ並べ、`replayFrame` が軸の位置から
  フレームを導く (`src/view/GraspReplayMath.js`、純粋)。フレームは 4 種で、**当たりを持つのは
  `sample` と `sweep` だけ**: `between` (標本の間 — TCP は相の直線上、腕は ① の規則で補間か保持、
  当たりは常に空) と `unjudged` (判定していない相 — 最寄りの標本を保持、理由の文) は何にも当たらない
  (G1)。式は `docs/ALGORITHMS.md` §3.2c。core は補間しないので、この補間は第二の源ではない (準拠の
  共有フィクスチャは要らない — 写す相手が無い)。
- **R2-3 (再生ヘッドは時計の関数)。** `playheadAt` は再生を始めた時刻と位置からの関数で、フレームごとに
  積算しない (ADR-166 M7 の規律)。30fps でも 60fps でも同じ時刻は同じ位置 (G2)。再生の長さは
  リクエストを 1 本も増やさない。再生ヘッドが時間に線形なのは演出の曲線の欠落ではない — 軸は相の中の
  進み具合 s という事実で、曲線を掛けると標本の位置を偽る。
- **R2-4 (状態と終わらせる義務)。** 表示の状態は `context.graspReplay` (`null | {rank, at, playing}`、
  書き手は `GraspController` だけ、保存しない)。終わらせる義務は発火する事象の側に書く (原則 #32):
  別の候補を選ぶ・分析をやり直す・`results` を出る・overlay を出る。探索のやり直しのように書き手が
  多い事象は、`_tickReplay` が鮮度を導出して終わらせる (原則 #23)。開いている間、再生はゴーストと腕の
  唯一の書き手で、ホバーでは奪わない (原則 #4)。再生できない理由は `replayFor` が 1 か所で言い、
  パネル (disabled + 理由) とコールバック (toast) が同じ述語を読む。
- **R2-5 (描き分け)。** ゴーストは標本・掃引のフレームで濃く (`SELECT_OPACITY`)、間・判定していない
  区間で薄く。当たった障害物は**リクエストが送った箱そのもの** (ソルバが試した形) を注意色で輪郭にする —
  判定した当たりは実線、測っただけの腕の当たりは破線。accent は「操作の対象」の意味なので使わない
  (ADR-100、`tokens.test.js` の accent の消費者の census が問う)。パネルは当たり始めの時刻を
  「2 つの標本の間で触れ始めた瞬間は分からない」と言う (D2)。
- **R2-6 (進入スライドを M2 へ — DEF-069 決着)。** 進入スライド (Delight) は残し、位置 = `land`
  (outExpo)・色 = `fade` (outQuad) に揃え、不透明度のフェードを時計の関数にした。候補を替えると予覧の
  濃さまで落ちてから戻る (境目 — 採点表の G3)。再生のフレームの上では進入スライドは走らない (D5 — 2 つを
  同じ見た目にしない)。採点表の `GraspGhostView` 行は B → A。

### 検証

- 純粋層: `src/view/GraspReplayMath.test.js` — 時間軸の形 (動作の順・判定した相 = 1・判定していない相
  は理由つき)、判定したのに標本の無い相は throw、**補間と判定していない区間の当たりが 0 個** (2001 点の
  走査)、腕の authority、枝の飛びで保持、`noSolution` / `undeclared` で腕なし、コマ送りが全標本を両向きに
  訪れる、再生ヘッドが fps に依らない、再生できない理由、スキーマに秒・fps・速度の語が無い。
  `src/domain/robotConfig.test.js` — `drawsTranslucent` の表と未宣言で throw。
- 配線: `src/controller/GraspController.test.js` — コマ送りが腕へ `measured` → `solved` を渡し、
  ゴーストへ mm の TCP と箱の輪郭を渡す / 間のスクラブは何にも当たらない / 別の候補を選ぶと終わる
  (**2 回続けて**通す — 1 フレーム古い状態を読む欠陥は 1 回の操作では見えない) / ホバーで奪われない /
  stale で終わる / 再生が時計で進んで終わりで止まる / 分析が無いとき理由を言う。
- **この証拠が見ないもの**: 絵。CI の e2e はスタブで動き、スタブは標本を捏造しない (ADR-157 D6) ので
  再生を通せない。S1 / S5 の実機の確認と、再生と進入スライドが見た目で区別できることは
  `e2e/grasp-replay.spec.js` を満期とする GSN の 2 つの goal が受ける (support-exploring のまま)。
