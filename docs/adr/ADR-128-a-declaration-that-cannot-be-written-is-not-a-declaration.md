# 128. 書けない宣言は宣言ではない — 掴む場所の入力面を決め、届いていない宣言を配線する

- Status: Accepted (実装済み 2026-08-14 — 把持フィーチャの語彙・入力面・3D 確認、`robot.kinematics` 配線、`plan{}` リーチ入力)
- Date: 2026-08-14
- Deciders: yuubae215, Claude
- Retires: なし
- 段: **G-2 の完了 + G-3 のフロント配線** (`docs/grasp/implementation-order.md`)
- Supersedes / Superseded by: なし (ADR-119 が「この ADR では決めない」と残した UI の
  所有者を決め、ADR-127 / ADR-120 の宣言をフロントへ届ける)

## Context — Goal と力学 (§1.2 Goal)

**Goal:** *ソルバが決定した事実が、宣言の欠落によって画面に届かない状態を無くす。
そして掴む場所について、「言っていない」と「どこでもよいと言った」がユーザーにも
機械にも別物として見える。*

同じ形の欠陥が **3 つ**、同時に開いていた。どれも「バックエンドは正しい・テスト済み・
到達不能」であり、**生産する側からは見えない**種類の欠陥である (URDF は正しい、パネルの
欄は正しい、ソルバは正しい)。

| 届いていないもの | 前回セッションの言葉 | 残し |
|---|---|---|
| 掴む場所の宣言 (ADR-119 D2/D3) | 「**UI が未設計**」 | DEF-014 |
| `robot.kinematics` (ADR-127 の解析解 IK) | 「**この ADR の価値はまだ画面に届いていない**」 | DEF-030 |
| `plan{}` リーチ範囲 (ADR-120) | 「フロントが `plan{}` を集めないので『測れた側』へ到達する手段が他に無く」 | STUB `reachDeclared` の存在理由 |

3 つ目がいちばん露骨だった: パネルには **reach weight スライダー**が在るのに、リーチ
範囲を宣言する欄がどこにも無い。ADR-120 は「絶対基準が無い objective は 0 点ではなく
**未評価**」と正しく決めたので、そのスライダーは*評価されえない*量に重みを付けていた。
GitHub Pages のレビュアーが「測れた側」を見るために、スタブへ専用シナリオ
(`?graspStub=reachDeclared`) を足すところまでやっていた — **UI の穴を回避するために
検証用の配線が生えていた**。

ADR-119 が UI を決めなかったのは正しい判断だったが、その結果 D2/D3 は
「宣言できる」と書いてあって**宣言する手段が無い**状態で 3 日置かれた。書けない宣言は
宣言ではない。

## Decision

### D1 — 掴む場所の入力面は **パネル内**。3D は確認であって入力ではない

面チップ (`+x −x +y −y +z −z`) + `anywhere` + `clear` を、それが語る対象
(TargetPicker) の真下に置く。**ADR-099 の選択所有者には触らない** — ビューポートで面を
指す設計は選択モデルを「実体単位」から「面単位」へ広げる話で、ヒットテストの優先順位
(原則 #22)・undo 経路・選択の権威まで波及する。ADR-119 が「別の判断」として切り離した
その線を、ここでも越えない。

代わりに **確認を 3D に返す**: 宣言した面/領域から生成される**サンプル点そのもの**を
ビューポートに描く (`GraspSampleView`)。宣言の*意図*を描くのではなく**ワイヤに載る値**を
描くのは、意図の絵は payload とドリフトしうるからで、それはこのリポジトリが繰り返し
見つけている欠陥 (ADR-117: パネルが、リクエストに載っていない幾何を説明していた) と
同じ形になる。

副産物として **導出の場合も見える**: 宣言が無ければ ADR-118 の導出グリッドが同じ
オーバーレイに出るので、「あなたは*どこを*とは言っていない」が読む文ではなく
**物に付いた絵**になる。沈黙は欄を持たないので、絵を与える (原則 #31)。

### D2 — 語彙は **kind 判別の閉じた union**、状態は **4 つ**

```
graspFeature: { kind: 'anywhere' }
             | { kind: 'faces', faces: [{ face, region? }] }
```

解決した結果の状態は 4 つある — `derived` / `declared-anywhere` / `declared-faces` /
`malformed`。**4 つある理由が ADR-119 D2 そのもの**で、前の 2 つは*同じサンプルを出す*。
点群を比べる検査では区別の消滅が見えないので、証拠は状態の名前について書く。

`malformed` を第 4 の状態として立てたのは、**読めない宣言を `derived` へ倒すのが
「宣言したのに無視された」= D3 が禁じる嘘**だから。しかも下流での見え方は
`candidatesGenerated: 0` という*正しい形の答え*になる (ADR-117 の再演)。倒さず止め、
理由を出す (原則 #11)。

`region` は面の 2 軸に対する **0..1 の正規化矩形**。メートルで持つと、箱をリサイズした
日に領域が面を覆わなくなる。点 1 つに縮退させないのは把持が面積を要求する操作だから
(ADR-119 D2 の語彙選択をそのまま実装した)。

### D3 — 消去は `anywhere` の書き込みではなく **鍵の削除**

`clear` は `graspFeature` を文書から消す。`{kind:'anywhere'}` を書いてしまうと、
ユーザーは二度と「何も言っていない」状態へ戻れず、パネルは**本人がしていない選択**を
表示し続ける。0 を既定値で埋めない、の同型 (原則 #31)。

### D4 — 権威は**文書**。書き手は既存の doc-edit 1 経路

宣言は `specification.layout.entities[].graspFeature` に住み、
`DocBuilder.setEntityGraspFeature` → `ContextController.setGraspFeature` →
`createDocEditCommand` を通る。実行時パラメータとして持つと、リロード・エクスポート・
undo のどれでも消える。

`ContextController.setGraspFeature` は**意図的に `isNegotiation` で守らない** — grasp
パネルは ADR-106 D3 で交渉フロアを出ており、いま住んでいない mode でパネル自身の
コントロールを塞ぐと、理由を表示しようのない無効化になる (原則 #11)。

### D5 — 平行ジョーに 1 面だけの宣言は **gap にする** (対向面を黙って足さない)

`core/` は把持幅を**サンプル点の広がり**から測る。1 面だけ宣言すると幅がほぼ 0 になり、
ゲートは閉じられないハンドを通す — **ADR-118 が直した欠陥が、宣言という正面玄関から
復活する**。対向面を自動で足すのは D3 のマージ禁止に触れるので、足さずに止めて理由を
言う。対は ±X に限らない (上下面で掴むのは正当な意図で、導出集合は既定であって規則
ではない)。

### D6 — 運動学は **URDF から導出**する。写しを作らない

ADR-127 は「同じ 6 数が 2 箇所に在る」冗長を引き受け、DEF-030 で*一致の検査*を計画して
いた。ここではもう一段強く閉じる: 6 数を `public/robot/skeleton_arm.urdf` から**読み出す**
ので、ドリフトしうる写しが存在しない。テストは読み出した値を UR5e の公表値に釘付けし、
URDF が別の腕へ書き換わった日に落ちるようにする。

**kind は構造の主張なので、構造を検査してから出す** — 軸 2/3/4 が平行で手首が直交する
ことを確かめ、満たさない鎖には宣言を出さない (`null` = ADR-127 D3 の安全な既定)。
6 つの「もっともらしい数」を別の腕に対して出すのは、答えが正しく見えるぶん最悪である。

### D7 — フランジ規約の照合先は **フロントが描く形**

ADR-127 D6 は `FLANGE_Z_IS_APPROACH` を宣言し、「自己整合な誤った規約も往復検査を通る」
ので `core/` 内では決着しないと書いた。決着させられる外部の証人は**アプリが描く形**
だけなので、`skeleton_arm.urdf` の `wrist_3_link` のフランジ面 visual を読み戻し、
宣言した軸の上に在ることを検査する。フランジの絵を裏返した日にビルドが落ちる。

### D8 — リーチ範囲は宣言で、既定値ではない

`plan{}` の 3 欄を off 始まりのトグルの下に置く。off = **鍵ごと省略**。発明した範囲は
「測れたように見える余裕」を作り、それは ADR-120 が 0 点と未評価を分けた努力を無に
する。プリセットは*出発点*として `REACH_PRESETS` に宣言し、有効化はユーザーの操作に
残す (ADR-063 の selection-first の既存パターン)。

## Consequences

### 得られるもの

- ADR-119 の D2/D3 が閉じ、**掴む場所がユーザーの語彙になる**。
- ADR-127 の解析解 IK が実際に走る。`ikSolvable` が手首コーンの代理から、関節限界を
  見た事実へ変わる — **1 行も `core/` を触らずに**、宣言を送ることだけで。
- `reach_margin` が初めて測れる。スタブの `reachDeclared` シナリオは役目を終える方向へ
  進む (台帳の宣言どおり)。
- 導出に落ちたことが**画面と 3D の両方に**出る。

### 払うもの / 引き受けなかったもの

- **ビューポートで面を指す入力は無い。** ADR-119 の
  `DocumentOwnedGeometryStaysAcceptable` の反証が来たとき (「ここを掴め、と 3D で
  指したい」) に、選択の所有者ごと決め直す別 ADR が要る。今回の 3D は出力のみ。
- **対象幾何は文書由来のまま。** ビューポートで Solid を動かしても、再コンパイルまで
  サンプルは追随しない (ADR-117 が名指しした非対称をそのまま継承)。
- **`region` の入力欄は UI に無い。** スキーマ・ドメイン・検査は領域を完全に扱うが、
  パネルが書けるのは面までで、領域は `.ctx.json` / テンプレ側から書く。面の 2 軸を
  画面上で正しく名指しする (どちらが u か) 設計が要り、それは 3D 確認と一緒に決める
  ほうが安いと判断した。**宣言できない語彙を足したこと自体がこの ADR の主題**なので、
  ここは意図的な段であり忘れではない → DEF-031。
- **リーチ範囲は腕から導出していない。** UR の DH を送っているので原理的には導出できる
  が、`plan{}` はセルの運用上の制約 (この作業域まで) でもあるので、腕の最大到達を既定に
  すると宣言の意味が変わる。ユーザーが言う。

出てこない — S10 が assert しているのは文字列であって、ビューポートに出た点の位置では
ない。3D オーバーレイはその穴を*狭める*ために足したが、**オーバーレイ自身が焼かれて
いない** (点が正しい面に出ているかを問う検査は無い) → DEF-031。

### 実装で分かったこと

**宣言は ADR-118 の欠陥を正面玄関から連れ戻せる。** D5 は机上の防御ではなく、語彙を
設計している最中に見つけた実在の穴だった: 「ここだけ掴め」と 1 面を宣言する動作は
ユーザーにとって完全に自然で、その結果 `core/` が測る把持幅がほぼ 0 になる。
**宣言を足すという行為は、導出が守っていた不変条件を無効化しうる** — 導出は
「ハンドが触る面」を知っていたが、宣言はそれを知らない。

**3 つの穴が同じ 1 箇所に落ちた。** 把持フィーチャ・運動学・リーチ範囲は別の ADR の
別の段だが、配線先はすべて `GraspController.runGraspSearch` の request 組み立てだった。
「バックエンドは在るがフロントが宣言を送らない」は**場所を共有する欠陥のクラス**で、
1 つ直すときに残り 2 つが同じ視界に入る。

**`?raw` の境界が設計を決めた。** 運動学の宣言を GraspController が直接 import できない
のは、URDF を読む唯一のモジュールが Vite の `?raw` に依存し node テストレーンで動かない
から (ADR-088 の browser-only 境界)。結果として注入になり、それは**テストが
「宣言が届いた」を request の上で assert できる**形でもあった — 制約が正しい形を選ばせた。
