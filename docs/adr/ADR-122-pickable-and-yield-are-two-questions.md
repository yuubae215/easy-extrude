# 122. 「そもそも取れるか」と「何個取れるか」は別の問い — 1 つのドアを共有していた

- Status: Proposed (未実装 — ADR-118 と同じ PR で起票)
- Date: 2026-08-11
- Deciders: yuubae215, Claude
- Supersedes / Superseded by: なし (ADR-078 のシーン層に入口を与える。ADR-090 のゲートは緩めない)

## Context

grasp-search は「この 1 個を、この 1 台で、掴めるか」に答える。要件の議論で、それとは
別に少なくとも 2 つの問いが在ることがはっきりした:

- **pickable** — ワーク外形とツール形状から、**そもそも**取れるか。セルもロボットも要らない。
- **yield** — 供給場所に置かれた N 個から、**何個**取れるか。

### 発見 — pickable は判定が在るのに、聞く手段が無い

`NaiveParallelJawGraspChecker` / `NaiveSuctionGraspChecker` は**ロボットを一切要求しない**。
まさに形状 × ツールの問いである。ところがこれは per-candidate パイプラインの**中**に
住んでいて、リーチ → IK の後ろにいる。そしてフロントは ADR-090 のゲートで
**ロボット無しのリクエストを送れない** (原点に立つ無限リーチの幽霊ロボットを塞いだので)。

**2 つの問いが 1 つのドアを共有していて、幽霊ロボットの穴を塞いだときに形状 × ツールの
問いも一緒に塞がった。** ADR-090 は正しい。塞ぎ方の副作用が見えていなかっただけ。

### 発見 — yield のレーンは実装済みで、誰も呼んでいない

ADR-078 のシーン層 (`core/easy_extrude_core/scene/`) は属性とピック履歴から per-pick の
target / obstacles を導出し、コアAPI は `POST /pick-sequence` を公開している。
**BFF にルートが無く、フロントにクライアントが無く、中立スキーマも無い**
(ADR-078 が public Layout DSL 正本待ちとして deferred にしたまま)。原則 #29 の
「契約あり か 明示的対象外」のどちらでもないワイヤが、ここにもある。

### 配置の語彙について — 二軸案は畳む

議論の途中で「バラ置き / 整列 / バラ積み」を **姿勢の出所** (authored / sensed) と
**ピックが残りを乱すか** (independent / perturbing) の二軸に割る案を出し、一度は採った。
その後の指摘で**畳むことにした**:

崩れるかどうかは状態変化ではなく、**ワーク同士が被って見えなくなる**ことと
**ピック時に互いに干渉する**ことであり、どちらも**論理的に配置された集合の組み合わせから
導出できる**。しかも既に導出されている — `derive_obstacles` が
`{全 static} + {全 dynamic} − {target} − {picked}` を、`viewable_entities` が視線遮蔽を。

導出できるものを宣言すれば第二の源になる (§1.1)。よって**配置は宣言する軸ではなく、
「集合をどう与えるか」の問題**に解ける。

「全体で何個取れるか」の確率は、シミュレーションではなく**実験計画 + 統計的計測**で
扱う。決定的なソルバの外に独立した問題として置くことで、個々の問題が疎になる。
置き場所は既にある: ADR-081 の `ConvergenceBySweetSpot` と `docs/dogfooding/`。

## Decision

### D1 — pickable を独立した問いとして立てる

ロボットを要求せず、形状 × ツールだけを問う経路。ADR-090 のゲートは**緩めない** —
grasp-search に「ロボット無しモード」を足すのではなく、別の問いとして分ける。
同じエンドポイントに 2 つの前提を同居させたことが、そもそもの原因だから。

### D2 — pick-sequence レーンに契約と入口を与える

中立スキーマ (`packages/grasp-contract`) + BFF ルート + フロントのクライアント。
`PickSequenceRequest` / `PickSequenceResponse` は `core/` に pydantic として在るが、
**中立正本が無い**ので、いまは片側だけが契約を持っている状態。

### D3 — 配置は宣言せず、集合から導出する

遮蔽・相互干渉は導出。宣言するのは集合そのもの (エンティティと属性 — ADR-078 の
`kind` / `persistence` が既にその語彙)。

### D4 — 歩留まりは決定的レーンの外

ソルバは `graspable` を決定的に返し続ける。「何個取れるか」の期待値は証拠のレーンで
獲得する。ソルバの入力に戻さない (原則 #24 の閉路を作らない)。

## Consequences

### 得られるもの

- ツールを選ぶ前に「このワークはこのハンドで取れるのか」を聞ける。
- 実装済みで眠っているレーンが使えるようになる。
- 個々の問題が疎になる — pickable は 1 個の幾何、graspable は 1 ピック、yield は集合、
  確率は計測。どれも他の入力にならない。

### 払うもの / 未解決

- D2 は grasp-search 1 本ぶんに近い仕事量 (スキーマ + ルート + クライアント + テスト)。
- **UI が未設計。** pickable の答え (「このハンドでは取れない」) をどこに出すかは、
  ADR-110 が grasp を「主語の隣の検査」に置いたのと同じ問いを、ワークについて解き直す
  ことになる。
- D3 で「バラ積み」という運用の言葉が語彙から消える。ユーザーが使う言葉と、システムが
  持つ語彙がずれる — 提示側で埋める必要がある (導出結果に名前を付けて見せる)。

### 検証 (証拠) — 未実装

| 主張 | 問い所 (予定) |
|------|-------------|
| pickable がロボット無しで答えられる | ロボット宣言なしのリクエストが 200 で返ること |
| ADR-090 のゲートが緩んでいない | grasp-search はロボット無しで依然 `no-robot` で止まること |
| pick-sequence が両端で検証される | 中立スキーマに対する準拠テスト (core / BFF 双方) |
| 遮蔽・干渉が宣言でなく導出である | 配置ラベルを持つ欄が契約に**無い**こと (census) |
