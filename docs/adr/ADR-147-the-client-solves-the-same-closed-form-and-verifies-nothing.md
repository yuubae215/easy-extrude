## Context — Goal と力学 (§1.2 Goal)

**きっかけ:** ADR-145/146 の報告に対して当事者が「近似プレビューってどんなロジック
だっけ？ **8 解出るならいいよ**」と述べた。前段の条件 (8 解 = 決定的な閉形式) は
**現状が満たしていない** — ADR-144 の近似はサンプリング探索で、返すのは最近傍 1 つ、
姿勢は一致させていない。

**Goal (解ではなく性質):** `core/` が居ない環境で腕を見たとき、**見えている姿勢が
候補の姿勢である**と信じてよい。そして**それ以上は何も信じてはいけない**ことが
画面から分かる。

**力学 — なぜ ADR-144 は近似だったのか。** ADR-144 は却下案 B (UR 解析解の JS 移植) を
**§1.1 (同じ計算の源が 2 つに割れる)** で退け、「新しい方程式を 1 行も書かない」ことを
制約にして FK サンプリングへ迂回した。その制約の下では多スタート再サンプルが最善で、
実装は実際によく効いた (100 点中 98% が 1mm 以内)。

**変わったのは制約のほう。** ADR-146 が §1.1 の禁止対象を*複製*から**源が 2 つに
なること**へ精密化し、「公知の閉形式は `src/` に置いてよい — ただし共有フィクスチャの
準拠テストを同じ PR で置くこと」とした。閉形式はその条件を満たせる。

### 近似が近似のまま残ることのコスト (実装前に測った差)

| | ADR-144 の近似 | 閉形式 |
|---|---|---|
| 解の個数 | 最近傍 **1** つ | **最大 8** (肩 × 肘 × 手首) |
| 位置 | 許容差 10mm (100 点中 98% が 1mm 以内) | **機械精度** |
| 姿勢 | **一致させていない** (6 自由度を位置 3 拘束に当てる) | 一致する |
| コスト | 約 57ms / 回 | 反復なし |
| 失敗の形 | 許容差を超えたら null | 届かなければ空 (収束失敗という状態が無い) |

姿勢の行が本質である。近似プレビューの手首は**誰も言っていない向き**を向いており、
それはゴースト表示で「未検証」と述べることで辛うじて正当化されていた。

## Options considered

- **A (採用): 閉形式を `src/` へ導出として持ち、サンプリング探索を退役させる。**
  — tradeoff: `core/` と JS に同じ方程式が並ぶ。準拠フィクスチャ 3 本 (FK / IK / gauge)
  の維持コストを負う。UR 以外の機種が来たら**プレビューは出ない** (出荷モデルは
  `ur5e` ちょうど 1 つ — ADR-141)。
- **B: 両方持ち、UR なら閉形式・それ以外はサンプリング。**
  — tradeoff: 「画面の腕を決める計算」が 2 つになる = §1.1。しかも分岐の片側は
  **出荷機種では一度も通らない**ので、腐っても緑のまま (ADR-103 の退役の腐敗)。却下。
- **C: 現状維持 (ADR-144 のまま)。**
  — tradeoff: 当事者が名指しした条件 (8 解) を満たさない。姿勢の不一致も残る。却下。
- **D: クライアントでも干渉まで見る。**
  — 3 軸で判定すると干渉はアイデアでも重くもなく、**置いてよい側に入りうる**。
  しかし「腕が当たるか」を述べ始めた瞬間、プレビューは*予測*から*判定*へ変わり、
  `core/` の答えと食い違ったときにどちらが正なのかを決める場所が無い。
  本 ADR の Goal (見えている姿勢を信じてよい) の外なので**やらない** — が、
  「対象外」とは書かない (原則 #29 の二状態でいえば**まだ決めていない**)。

## Decision — Strategy (§1.2 Strategy)

**D1. `src/robotics/urKinematics.js` を置く — `core/` の閉形式の導出として。**
`dhTransform` / `matMultiply` / `matInverseRigid` / `forwardKinematicsChain` /
`forwardKinematics` / `inverseKinematics` / `withinJointLimits` /
`representativeSolution` / `dhFromDeclaration`。**規約も規律もそのまま写す**:
手首特異点で θ6 に 0 を「宣言的に選ぶ」こと、届かない姿勢が**空**であること
(「解けなかった」ではない)、関節限界の不在が「限界が無い」ではなく
**「問うていない」**であること。

**D2. gauge も写す (`src/robotics/graspPoseGauge.js`)。**
候補 frame (+Z = −approach) とフランジ目標 (+Z = +approach) は**導出できない取り決め**
であり、180° 回すだけでは一致しない (どちらも `basisFromZ(z)` で張り直し、参照軸が
z 成分で切り替わるため)。復元は (approach, roll) まで戻してから張り直す往復。

**D3. 準拠フィクスチャを 3 本置く (ADR-146 D3 の条件)。** 登録簿は
`CROSS_LANGUAGE_DERIVATIONS`、個数の予算は 1 → **3**。

| subject | 源 | なぜその向きか |
|---|---|---|
| `ur5e-forward-kinematics` | `public/robot/skeleton_arm.urdf` | FK の源は**画面に出る腕** |
| `ur5e-inverse-kinematics` | `core/…/ur_kinematics.py` | IK の源は**探索が解く側** |
| `ur5e-candidate-to-flange` | `core/…/pose_codec.py` | gauge の源は**規約を宣言している側** |

**向きが揃っていないのは誤りではなく、源がどちらに住んでいるかの違い**である。

**D4. 権威の名前を `approximate` から `unverified` へ訂正する。**
改名ではなく**意味の訂正**: 値は粗くない (機械精度)、粗いどころか厳密である。
欠けているのは精度ではなく**検証**で、干渉・可視性・把持性・スコアはどれも `core/`
しか答えられない。`approximate` のままだと**間違った限界**を名乗り続け、次の人が
「精度を上げよう」と既に機械精度の数を改善しに行く。行のキャプションも同じ理由で
「approximation (position only)」→「solved by this browser and checked against nothing」。
クライアント結果の判別子も `clientApproximate` → `clientAnalytic` (ADR-144 D2 の
型分離そのものは不変 — `kind` を使わないことで契約の検証器を構造的に通らない)。

**D5. ADR-144 の D2 / D3 / D4 は一切触らない。** 型分離 (契約の `kind` と
クライアントの `origin` を別の鍵・別の形にする)、ゲート (`reachSolution.kind !==
'solved'` ただ 1 つ、環境フラグを新設しない)、唯一の入口
(`RobotStageSet.previewSolution` が関節角と見え方の**両方**を書く 1 箇所) は
そのまま生きている。**置き換わったのは「何を計算するか」だけで、「誰が書くか」の
構造は動かない。**

**D6 (明示的にやらないこと)。** 却下案 D (クライアント側の干渉判定)。
8 解をユーザーに**選ばせる** UI (今日は代表解だけを描く — 8 解が出ること自体は
`branches` として返るが、画面には出さない)。どちらも「対象外」ではなく
**まだ決めていない**。

## Consequences — Evidence と tradeoff (§1.2 Evidence)

**肯定的:**
- GitHub Pages の腕が候補の姿勢を**厳密に**実現する。位置も向きも機械精度。
- 「近似だから」という言い訳で隠れていた**姿勢の不一致**が消える。
- 1 回 57ms の探索が消え、反復のない代数計算になった。
- `core/` と JS が**同じ規約・同じ代表解**を使うことが機械で問われるようになった。
  これは ADR-141 (画面の腕と探索が解く腕を同じ 1 台にする) の**一段深いところ**での
  同じ主張で、今日まで誰も問うていなかった。

**受け入れるコスト / 否定的:**
- 同じ方程式が 2 言語に並ぶ。**フィクスチャ 3 本を緑に保つ責任**が、`core/` の運動学を
  触る人に生じる (生成器を走らせ忘れると Python 側のテストが落ちる — そのための
  「今の core/ とずれていないか」テストを両フィクスチャに付けた)。
- **UR 以外の機種ではプレビューが出ない。** サンプリングは機種を選ばなかった。
  出荷モデルが `ur5e` ちょうど 1 つ (ADR-141) である今日は差が出ないが、2 台目が
  入った日に「出ない」ことが仕様として現れる。0 は既定値ではなく**宣言された 0**。
- 手首特異点では 2 実装の**関節値が一致しない** (下記)。

**検証 (実行結果):**

| 主張 | 問い所 | 結果 |
|---|---|---|
| 8 解が `core/` と個数・順序ともに一致 | `ur5e-inverse-kinematics.json` の 24 姿勢 | 一致 |
| `FK(IK(T)) == T` (原則 #28 の fixpoint) | 同、全解について | 1e-9 以内 |
| gauge が一致 | `ur5e-candidate-to-flange.json` の 24 姿勢 | 1e-9 以内 |
| gauge の**両分岐**を通っている | `|z| >= 0.9` と `< 0.9` の姿勢の存在を両言語で assert | 通過 |
| 「180° 回すだけ」では一致しない | 素朴な近道を計算して**差が出ることを焼く** | 差が出る |
| 代表解の規則が一致 | 総移動量最小であることを JS 側で assert | 一致 |
| プレビューが候補の姿勢を厳密に実現 | `GraspController.test.js` (FK を 1e-9 で照合) | 一致 |
| `solved` のときクライアントが解かない | 呼び出し**回数**を数える (出力に痕跡が無いため) | 0 回 |
| 届かない候補は `null` | 同 (解こうとした上で「無い」= 呼び出し 1 回) | rest |
| `pnpm test` | JS 全体 | **1372 passed** |
| `pnpm test:core` | pytest | **209 passed** |

**手首特異点での不一致 — 隠さずに数える。** `|sin θ5| ≈ 0` では θ6 が定まらず、実装は
0 を宣言的に選ぶが、その選択は θ1..θ4 の端数を通じて別の関節へ吸収される。つまり
**関節ベクトルは一意でない**ので、2 実装がビット単位で一致する道理が無い。実測
(24 姿勢): 特異でない 23 件は関節値が **1.4e-10 以内**、特異な 1 件だけが **3.0e-8**
ずれ、しかし**姿勢は 2.2e-15**。

ここで許容差を一律に緩めると、特異でないところの本物のずれまで通る。だから緩めず、
**特異な姿勢を名指しして数える** (`SINGULAR_CASE_BUDGET = 1`、超えても下回っても落ちる)。
そのうえで**姿勢は特異点でも 1e-9 で一致すること**を別に問う — 関節値を飛ばした
ケースについて何も主張しないまま終わらせないため。

**実装で分かったこと (原則 #19):**

1. **目標姿勢を 12 桁へ丸めると、特異点の近くでは丸めだけで関節値が 1e-8 動く。**
   フィクスチャの `target` を丸めていたため「フィクスチャを読み直した `core/` が、
   フィクスチャを作った `core/` と違う答えを出す」という状態になり、Python 側の
   テストが落ちた。**目標姿勢は入力**なので丸めない (Python の float は JSON へ
   往復可能な最短表記で出力され、JS の `JSON.parse` が同じ double を復元する)。
2. **`base` の形を取り違えて NaN を作った。** 解決済み宣言は wire 形の**配列**
   (`[x,y,z]`) だが、gauge の初版は `{x,y,z}` を読んでいた。各成分が `undefined` →
   行列が NaN → NaN は比較でどの枝にも入らないので、**解が 0 本という正しい形の
   答え**になって現れた。形が違う入力は計算せず throw するようにした。
   *この PR が「粗い判定は正しい形の嘘を返す」と何度も書いた、まさにその形を自分で
   踏んだ*ので記録しておく。

## Lens notes

- **§1.1:** 禁じられているのは*複製*ではなく**源が 2 つになること**。3 本の
  フィクスチャがその一点を機械に問わせている。向きが揃っていないのは、
  源がどちらに住んでいるかの違い。
- **原則 #2 (型が能力の契約):** クライアント結果は `origin`、契約は `kind`。
  別の鍵・別の形なので、近似結果を契約の検証器へ渡しても構造的に通らない。
- **原則 #11:** 届かなければ `null`。「一番近い配置」は出さない。
- **原則 #28:** `IK(FK(q)) == q` は求めず、`FK(IK(T)) == T` を問う。
- **原則 #31:** 特異点の不一致は**緩めずに数える**。UR 以外で出ないプレビューは
  既定ではなく宣言された 0。
- **ADR-103 (退役の腐敗は緑を出す):** サンプリング探索を「非 UR 用に残す」誘惑を
  退けた理由 — 出荷機種では一度も通らない枝は、腐っても誰も気づかない。
