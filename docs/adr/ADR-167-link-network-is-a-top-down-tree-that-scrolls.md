## Context — Goal と力学 (§1.2 Goal)

### 要求 (当事者、2026-10-21)

> やっぱり、何回も見直してるけど LINK NETWORK の階層図は上から下へツリー構造になってるのが見えるのが一番見やすいと思った

俯瞰で横幅の払い方を 3 択 ((a) パネル内の横スクロール / (b) 兄弟が多いときにパネルを広げる / (c) 全体を縮小し選択の周辺だけ拡大) で問い、当事者は **(a)** を選んだ。
「blender みたいに見たいときにセパレートで出して、見なくてもいいときに範囲外にしまう、とかでもいいけどね」と付記があった — しまう側は既存の折りたたみ (`−`/`+`) が担う。別窓に出す側は本 ADR の範囲外 (§残し)。

**Goal:** *TF ツリーの親子が、上から下への枝分かれとして見える。* ADR-095 の 2 つは手放さない —
**G1** ラベルが常に読める (名前が兄弟の数で縮まない・点に潰れない)、**G2** 深さが辺を辿らずに分かる。

### 力学 — ADR-095 は依頼の形を持ち上げすぎた

ADR-095 の発端も同じ依頼だった (「Mermaid のトップダウン記法みたいに縦にツリー状にできないの?」)。
ADR-095 はそれを Goal へ持ち上げる過程で「当事者が指しているのはファイルツリー形式」と読み替え、
インデントのアウトラインを出した。3 か月使った当事者の答えが上の一文である。

ADR-095 の GSN 木はこの可能性を **反証されうる仮説** として名指ししていた
(`SiblingComparisonLossIsAcceptable` — 兄弟が横に並ばなくなる損失は受け入れられる。
「当事者の実利用でしか反証できずテストでは閉じない」)。反証が来たので、その木に記録した。

ADR-095 が上から下の木を却下した理由は形ではなく **資源配分** だった:

| 軸 | ADR-095 の前提 | 本 ADR |
|----|---------------|--------|
| x | 固定 196px (左端は共有資源 — 原則 #26) | **パネルは固定のまま、中身はスクロールする** |
| y | スクロール可 | スクロール可 (不変) |

希少な固定軸に可変量 (兄弟数) を割り当てたことが `denseMode` (12 個でラベルが全部消える) の原因だった。
x をスクロール可能にすれば、兄弟数は幅を**増やす**だけで**割らない** — G1 と上から下の木は両立する。
両立しなかったのは x を固定と置いた前提のほうで、その前提を変える選択肢は当事者が選ぶものだった。

## Options considered

- **A: 上から下の木 + パネル内の横スクロール (採用)** — パネルの寸法・左端の占有は不変。兄弟は固定幅の列に並び、幅が足りなければスクロールする。払うのは「一度に全体は見えない」こと。
- **B: 兄弟が多いときにパネルを広げる** — 全体が一度に見える。ただし左端の占有 (`EdgeOccupancy`) の再計算が要り、広がったパネルがビューポートを覆う。当事者は選ばなかった。
- **C: 全体を縮小し、選択の周辺だけ拡大** (focus + context) — 全体の形が見える。ただし縮小部分のラベルは読めず (G1 を部分的に捨てる)、実装も重い。
- **D: ADR-095 のアウトラインのまま** — G1・G2 は満たすが、当事者の Goal (枝分かれが見える) を満たさない。

## Decision — Strategy (§1.2 Strategy)

**D1 — 幾何の割り当て。** y = TF 深さ (1 段 `LEVEL_H`)。x = 列スロット (`SLOT_W` 固定幅)。
葉は DFS 順に連続したスロットを取り、親は最初と最後の子の中央に置く (tidy tree の単純形)。
同じ段の 2 ノードは常に 1 スロット以上離れる — 親どうしの葉の区間は互いに素なので、中点の差は 1 以上。
ゆえにラベルは衝突しない (`N Solids — no two nodes on one level are closer than one slot`)。

**D2 — G1 は定数で言う。** ラベル幅 = `SLOT_W − LABEL_PAD`。兄弟数も深さも式に現れない。
名前は語単位で 2 行まで折り返し (`labelLines` — 純粋関数)、残りは 1 つの省略記号で切る。
省略されたときの全名は `<title>` (ホバーのツールチップ) が持つ。場面が混めば**内容が広がり**、パネル内でスクロールする。

**D3 — 木辺は組織図の肘。** 親のラベルの下から幹 → 兄弟を渡す横棒 → 各子への垂線。線分は純粋関数 `treeSegments` が出す (view は座標を計算しない — ADR-094 E3)。

**D4 — 余木辺 (SpatialLink) は木の上に弓で描く。** レーンは x 区間の決定的な区間彩色 (ADR-095 の規則を行区間から列区間へ移しただけ)。
レーンは弓の高さを決め、上のレーンほど高く反る。上限 `MAX_LANES` (3 → **5**。上から下の木では弓どうしが高さで分かれるので、ガターの幅に縛られていた上限を上げられる) を超えた辺は両端の `+N` に数える (原則 #11)。
レーンが 0 本なら弓の余白も 0 (在らないものを先取りしない)。弓の端は点の縁で切る (`arcPath`) — 矢印が点の下に隠れない。

**D5 — スクロール位置の書き手は 2 つ。** 利用者と `_revealSelection` (3D 側で選んだ実体のノードが見えていなければ、そこまでスクロールする)。
後者は**選択が変わったとき**だけ書き、hover や再レイアウトでは書かない — 見回している利用者と取り合わない。
位置そのものは DOM 要素の `scrollLeft`/`scrollTop` が唯一の権威で、JS 側に写しを持たない (ADR-095 の決定を 2 軸へ拡張)。

## Consequences — Evidence と tradeoff (§1.2 Evidence)

### 得られるもの

- 親子が上から下の枝分かれとして見える。兄弟は横に並び、見比べられる (ADR-095 が手放したもの)。
- 名前は 2 行まで切られずに読める (「Robot pedestal」は「Robot ped…」ではなく 2 行)。
- 深さの飽和とバッジが不要になった (縦位置が深さそのもの)。

### 払うもの

- 一度に全体は見えない。220px で同時に見える列は約 3.4 本で、それ以上は横スクロール。
  3D で選んだ実体へは自動でスクロールするが、パネルで全体を眺めるにはスクロールが要る。
- 名前は 2 行 × 約 58px を超えると省略される (全名はツールチップ。タッチではツールチップが出ない)。
- 列の多い場面では弓が長くなり、木の線と交差する。

### 検証 (証拠)

論証木: `docs/gsn/adr-167-link-network-is-a-top-down-tree.gsn` (goal ごとの支えの正本)。
