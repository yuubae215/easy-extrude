# 113. 画面を占めるのは 1 つ、順序を決めるのも 1 つ — 枚数に欄を与える

- Status: Accepted (実装済み — `stage` を 1 欄に統合し 2 枚同時を表現不能に、段と z-index の宣言を `view/ScreenClaim.js` へ集約、全画面オーバーレイ 4 面の宣言と未宣言 0 枚の検査、ドロップダウン帰属の述語を 1 つに畳み再実装 5 箇所を回収、`⋯` の段を 1 つの状態へ)
- Date: 2026-08-04
- Deciders: yuubae215, Claude
- Supersedes / Superseded by: なし (ADR-089 の `home` と ADR-051 の
  `templateGalleryOpen` を **1 欄に統合**する。両者が決めた *中身* — 何を選ばせるか、
  どう読み込むか — は不変で、変えるのは**枚数と順序の所有者**だけ)

## Context — Goal と力学 (§1.2 Goal)

**Goal:** 入口を押したら、その入口が名指しした先へ、**押した回数と無関係に**同じように
着く。画面を占める面が 2 枚立ったとき、勝者が**宣言**から読めること。

出発点はユーザーからの 2 行の報告である。

> ・unexamined 押すとレイアウトテンプレート選択になる。
> ・... 押すと、Start, Export, Import, Context が出るが、それらを押しても何も起こらない。
>   もう一度 ... を押すとコンテキストメニューが変わっている。

実機で両方を再現したところ、**別々の症状に見えて、どちらも「同じ問いに答える規則が
2 箇所にあり、片方だけが正しかった」**という同じ形をしていた。

### 力学 1 — 帰属の述語が 2 実装あり、片方だけが surface を知らなかった

`⋯` の一段目を押しても何も起きない原因は `HeaderMenus.useDropdown` の

```js
if (!btnRef.current?.contains(e.target)) setOpen(false)   // 引金だけを見る
```

にあった。パネルは `position:fixed` で描かれる (ヘッダが `overflow:hidden` なので
中に置けない) から、**パネル内の click は引金の外側**であり、開いた瞬間に閉じる。

同じ問いに `ModeDropdown` は別の答え方をしていた:

```js
btnRef.current.closest('[data-mode-selector]')?.contains(e.target)   // 器を見る
```

こちらは器がパネルを含むので正しく動く。**どちらも単体では妥当なローカル判断**で、
データの二重化と違って grep でも見えない (§1.1 が「導出規則の再実装」として名指しする形)。
実測すると同じ規則は `AddMenu` / `ContextMenu` / `LinkTypePicker` にもあり、**合計 5 実装**
だった。

デスクトップの `VerbMenu` で症状が出なかったのは、行を選べばどのみち閉じるのが
正しいからである — **正しさではなく、症状の出なさが 2 実装を延命させていた**。

#### 力学 1 の第二層 (実装中に判明した)

surface を渡すようにしても、まだ閉じた。React は行の `onClick` で起きた state 変化を
**`document` の `click` リスナが走る前に flush** するので、押された行は既に DOM から
外れている — **切り離されたノードはどこにも含まれない**ので、述語がどれだけ正しくても
「外側」と読む。つまり規則は述語だけでは閉じず、**いつ問うか** (`pointerdown` =
再描画より前) までが規則の一部だった。俯瞰では出せなかった項で、実装が前提を
書き換えた例として残す (原則 #19)。

### 力学 2 — 「同時に何枚立っているか」に欄が無い

`⋯` の 3 行目の症状 (もう一度開くと違うものが出る) は、状態を 2 欄で持っていたことに
由来する: `open` (boolean) と `verb`。この対は `{ open:false, verb:'export' }` を
**表現できてしまい**、閉じる経路が増えるたびに「閉じるときに `verb` も戻す」を
思い出す必要があった。思い出さなかった経路が 1 つあれば再発する。

同じ形が、もっと大きな粒度で全画面オーバーレイにも在った。実測 (走査で導出):

| 面 | flag | z-index | 書き手 |
|---|---|---|---|
| 起動ホーム (工程レイアウト) | `home` | **300** | `AppController` |
| New Project (Context テンプレ) | `templateGalleryOpen` | **300** | `ContextController` |
| rename / confirm | `modal` | 500 | `uiStore.openModal` |
| import ダイアログ | `modal` | **10000** | 同上 |
| 初回ジェスチャヒント | `onboardingVisible` | 500 | `UIViewBridge` |

個々の flag は値を持つので状態として認識されるのに、**枚数**には欄が無い。しかも
上 2 つは**同じ 300 を各ファイルが独立に選んで**おり、両方立ったときの勝者は
`UIShell.jsx` のマウント順 — **どちらのコンポーネントにも書かれていない事実**が
決めていた。負けた面は無言で見えなくなる (原則 #11)。同じファイル内で `10000` が
選ばれていたのも同じ症状の別の面である。

これは原則 #31 が名指しする形そのもの: `mode` / `status` は欄を持つので状態に見えるが、
**基数 (0 枚・N 枚) には欄が無い**ので、*在るもの* (各 flag) を辿る読み方では
永久に見えない。

### 報告 1 行目の決着 (俯瞰と食い違った項 — 隠さず書く)

俯瞰では「`Unexamined` がレイアウトギャラリーを開いている可能性」を残したが、
**実測では開いていない**。`Unexamined` の出口は `onOpenTemplateGallery` ただ 1 本で、
起動ホームを閉じた状態で押すと正しく New Project が出る (ユーザー確認済み)。
つまり 1 行目は**仕様どおりの動作**であり、違和感の実体は別のところにある:

- 起動直後に見た**レイアウト**テンプレ選択と、New Project は**ほぼ同一の見た目**で、
  どちらも「選ぶと現在のシーンを置き換えます」と書いてある。
- 読み取り専用の表示 (`Unexamined`) を押した先が、シーンを置き換える面である。

この語彙の作り分け (Layout DSL 側と Context DSL 側で見出し・説明・破壊性の書き方を
分ける) は**本 ADR の対象外**とユーザーが決めた。したがって**未着手**であり、
`docs/DEFERRAL_LEDGER.md` DEF-011 に残しとして宣言する — 宣言しない残しは記憶で
あって残しではない (ADR-109)。満期は「読み取り専用の表示を押した先がシーンを
置き換えることが押す前に分かる」状態になったとき。

本 ADR が 1 行目について閉じるのは**構造の側**だけである: 2 つのギャラリーは
同じ 1 欄に住むようになったので、**一方が他方の背後に無言で開くことは起こらない**。

## Decision

### D1 — 帰属の述語は 1 つ (`view/DropdownContainment.js`)

`isInsideDropdown(target, { trigger, surface })` を唯一の所有者とし、
**引金と surface の両方を渡すことを型の形で要求する** (片方だけ渡す呼び方は throw)。
`src/IdentityContainment.test.js` の `IDENTITY_RULES` に登録し、再実装を機械が落とす。

規則の走査範囲に `scope: 'all'` を導入した — 従来 `IDENTITY_RULES` は `.jsx` を
見ておらず、表示層に住む規則はそのままでは**空振り**する。既存規則まで一斉に
広げると散文的な一致が増えるので、**広げるのは規則ごとの宣言**にした。
登録した初回実行が、想定していなかった 3 実装 (`AddMenu` / `ContextMenu` /
`LinkTypePicker`) をその場で名指しした。

判定は `pointerdown` で行う (力学 1 の第二層)。

### D2 — `⋯` の段は 1 つの状態 (`view/OverflowMenuState.js`)

```
null                        閉 — 段を持たない (これが本体)
{ level:'verbs' }           一段目
{ level:'objects', verb }   二段目
```

`openMenu()` は**必ず一段目**を返す。「閉じるときに戻す」(= 経路ごとに書き忘れうる
規律) ではなく「**開くときに決まる**」(= 経路が何通り増えても不変) 形にした。

### D3 — 画面の主張は 1 欄、段と z は 1 箇所 (`view/ScreenClaim.js`)

`home` と `templateGalleryOpen` を `uiStore.stage` に統合する:

```
null | { claim: 'launch-home' | 'context-template-gallery' }
```

書く入口は `claimStage(claim)` / `releaseStage(claim)` の**対ちょうど 2 つ**。
**解放は主張の同一性つき**で行う — 誰の主張かを見ずに `null` を書くと、
遅れて来た close が後から立った別の面の主張を消す。

面は 3 段に分ける。段ごとに基数 0..1:

| 段 | 面 | なぜ別段か |
|---|---|---|
| `stage` | 起動ホーム / New Project | 相互排他な「始め方」。1 欄に統合 |
| `coach` | 初回ジェスチャヒント | 4 秒で自動退場する。stage と同居させると mobile 起動でホームが食われて戻らない |
| `dialog` | rename / confirm / import | 下の面**について**問う面。下を消してはならない |

**面は自分で z を選ばない** — `tierZIndex(tier)` が唯一の順序の所有者で、未宣言の
段では throw する (原則 #26 が画面端に課した「共有資源の占有量は 1 箇所で計算する」の
全画面版)。

### D4 — 数えるのは「宣言外の面」と「自分で z を選んだ面」

`src/ScreenClaimCensus.test.js`。母集団は `src/components/**` を走査し、
`position:'fixed'` と `inset:0` を同じ style に持つ箇所から**導出**する
(手書きの面リスト = ADR-102 が語彙から消した `place-list` にしない)。

2 つ数える理由は、**1 つでは元の欠陥を捕まえられない**からである: ADR-113 以前も
4 面はそれぞれ flag を持っていた。壊れていたのは*面の存在*ではなく **面どうしの
順序**で、それは各ファイルの `zIndex: 300` というリテラルに散っていた。
*在るもの* (面) を辿る数え方では出てこない。

## 却下案

### 却下案 A — `⋯` の帰属だけ直し、モーダルの枚数は触らない

報告された症状は消えるが、力学 2 の本体 (枚数に欄が無い) が残る。ユーザーが
明示的に「モーダルの基数に所有者を与える」を選んだ経緯もある。加えて、
症状ベースで直すと**次に全画面オーバーレイを足した人が同じ 300 を選ぶ**ことを
何も止めない — ADR-108 が入口について、ADR-060 が契約について言った
「畳み込みは一度きりの是正であって統治ではない」と同型。

### 却下案 B — 全画面オーバーレイを 1 スロットに統合する (段を作らない)

`stage` / `coach` / `dialog` を 1 欄にすれば「同時に 1 枚」が最強の形で保証される。
**却下**: confirm ダイアログは「いま見ているものについて」問う面なので、下の面を
*消して*はならない。1 欄化は不変条件としては強いが**嘘**であり、mobile 起動では
ジェスチャヒントが起動ホームを食って戻さない実害も出る (段を分けた理由そのもの)。
不変条件は強ければよいのではなく、**現実の形と一致していなければならない**。

### 却下案 C — z-index を各面が持ったまま、値だけを tokens に集約する

`Z.modal = 300` のような定数を共有すれば「同じ 300」は宣言になる。**却下**:
定数を共有しても *同じ値を選んだ 2 枚のどちらが勝つか* は依然マウント順が決める。
問題は値の重複ではなく**順序の不在**なので、共有すべきは値ではなく**段**である。

### 却下案 D — `⋯` を開くたびに `verb` をリセットするコードを close 側に足す

最小の差分で症状は消える。**却下**: 閉じる経路は今 3 つ (外側 click / 行の選択 /
引金の再押下) あり、Esc・画面回転・ルート遷移で増えうる。**規律で守るものは
経路の数だけ破られる** (原則 #23 が「呼び手に事前 refresh を要求する規約は N-1 箇所で
破られる」と言ったのと同じ)。答えは形 — 閉が段を持てないようにすること。
