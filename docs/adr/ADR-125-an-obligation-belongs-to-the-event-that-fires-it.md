# 125. 義務は、それを発火させる事象の側に置く — 条件つき退役を ADR ライフサイクルの欄にする

- Status: Accepted (実装済み 2026-08-12 — `Retires:` 欄 + `pnpm test:adr` の退役検査。ADR-125 以降必須)
- Date: 2026-08-12
- Deciders: yuubae215, Claude
- Retires: GREP:docs/DEFERRAL_LEDGER.md::DEF-026
- Supersedes / Superseded by: なし (ADR-124 の §引き受けなかったもの が名指しした
  「条件つき退役の検出」を設計する。ADR-103 と ADR-100 が手書きした退役検査を一般化する)

## Context — Goal と力学 (§1.2 Goal)

**Goal:** *「A が起きたら B を消す」という約束が、A が起きた日に必ず問われる。*

出発点はユーザーの指摘である —「条件付き退役も設計してほしい。**これ、ADR 運用する
ライフサイクルで必須なんじゃない?**」。これは正しい。以下は実測である。

### 力学 1 — 条件つき退役は corner case ではなく、5 回起きていた

| 実例 | 約束 | 何が起きたか |
|---|---|---|
| ADR-112 / `DocIntake.js` | `PROVISIONAL_UNTIL = 'ADR-108'` — ADR-108 が決めたら畳む | ADR-108 は 2026-08-03 に Accepted。**満期は無言で過ぎ、写しは 7 箇所**が同時に古くなった |
| ROADMAP §Phase S-4 | 「S-4 が完成したら BFF Phase D 表から削除し統合」 | **誰も実行しない。** ADR-123 が畳むまで二重登録のまま |
| ADR-103 / `DS_PENDING` | Map モード退役に伴い enum から消す | **3 リリース残った。** 手書きの `RETIRED_MODE_SHAPES` を作って初めて止まった |
| ADR-100 / 退役した選択色 | `accentActive` を分割して消す | 同上。手書きの `RETIRED_SELECTION_COLORS` |
| ADR-060 の 5 項目 | upstream 実装に追従したら宣言を消す | 3 つ完了・1 つ対象消滅、**宣言だけが「まだ残っている」という嘘を出し続けた** |

5 つとも**無関係な文脈**である (入力の住所 / ロードマップ / 投影 / 配色 / 契約)。
これは corner case ではなく、**ライフサイクルの構造的な穴**である。

### 力学 2 — 検査は既に 2 回、手で書かれている

`src/ProjectionAxisOwnership.test.js` の `RETIRED_MODE_SHAPES` と
`src/theme/tokens.test.js` の `RETIRED_SELECTION_COLORS` は、**同じ検査の手書き実装**である。
仕組みが無いのではない — **思い出した人だけが書いていた**。思い出さなかった 3 件
(ADR-112 / ROADMAP / ADR-060) が腐った。

### 力学 3 — 語彙では検出できない (実測で確定)

ADR-124 は「条件つき退役の検出」を残しにした。今回、削除動詞 (`削除|消す|外す|撤去|
廃止|remove|delete|drop`) × 条件マーカー (`したら|ときに|when|once`) の **2 要素**で
走査したところ **87 hit**、しかしサンプルの**ほぼ全部が偽陽性**だった
(`Fired when` / メソッド名の `delete` / 散文の `removed`)。日本語と英語の両方で
言い回しが無限にあるので、語彙は原理的に届かない。ADR-124 の判断は正しかった。

### 力学 4 — 義務が「消される側」に書かれていた (これが根本)

5 例すべてに共通する形がある: 約束は **消される側の隣**に散文で置かれていた。
`DocIntake.js` の中、ROADMAP の表のセル、enum の隣のコメント。

しかし条件 A が起きるのは**別の場所**である — ADR-108 が Accepted になる、
Phase S-4 が完成する、ADR-103 が実装される。**A が起きた瞬間に、誰も B を読み返さない。**
消される側は自分が死ぬべき時を知っているが、死ぬべき時が来たことを知らない。

そして観測した A は、**ほぼ常に ADR のライフサイクル事象**だった。

## Options considered

- **A: 語彙で検出する** — tradeoff: 実測 87 hit のほぼ全部が偽陽性 (力学 3)。却下。
- **B: 消される側にマーカーを置き、機械可読にする** (`PROVISIONAL_UNTIL` の一般化) —
  tradeoff: 既に存在し、既に効いている (Q2)。しかし**書く側が「これは暫定だ」と
  自覚したときにしか置かれない**。ROADMAP の表のセルに `PROVISIONAL_UNTIL` は書けない。
  カバー範囲が「コード内の暫定」に限られる。
- **C: 義務を発火事象 = ADR の側に置く【採用】** — ADR が「自分が Accepted になったら
  何が消えていなければならないか」を宣言する。tradeoff: ADR を書く人が退役を
  **意識していなければ**書かれない (下記 assumption)。
- **D: 登録簿の行にする (kind 列を足す)** — tradeoff: 満期の機構をそのまま使えるが、
  発火条件がやはり散文になる (「Phase S-4 が完成したとき」)。**C との差は、C では
  発火条件が ADR の Status 遷移そのもの**で、機械が既に読んでいる点である。

## Decision — Strategy (§1.2 Strategy)

### D1 — ADR ヘッダに `Retires:` 欄を置く。**ADR-125 以降は必須**

```
- Retires: なし — この ADR は何も置き換えない
- Retires: GREP:src/store/uiStore.js::mapMode · PATH:src/view/MapModeToolbar.js
```

**「消すものが無い」も宣言である** (既定値で埋めない — 原則 #31)。欄が無ければ落ちる。

番地の書き方は**登録簿の満期 trigger と同じ語彙** (`PATH:` / `GREP:<path>::<regex>`)。
repo 内の何かを指す書き方を統治全体で 1 つにする (§1.1)。

**遡及しない。** 歴史 ADR 124 本の一括改稿は churn に対して得るものが無い
(`check-adr-status.mjs` が台帳参照を ADR-091 以降にだけ効かせたのと同じ判断)。

### D2 — 発火は Status 遷移。両方向を問う

| ADR の Status | `Retires:` が指す先 |
|---|---|
| **Accepted** | **在ってはならない** — 在れば落ちる (退役の義務が履行されていない) |
| Proposed / Draft | **在らねばならない** — 無ければ落ちる (宣言が実物より古い) |
| Rejected / Superseded | 問わない (決定が効いていない) |

逆向きを問うのは ADR-103 の規律である — **退役の腐敗は違反を*見逃す*のではなく
緑を出す**。「もう消えているのに宣言が残っている」は「消し忘れ」と同じくらい嘘である。

### D3 — 消せない退役は、退役ではなく**残し**である

`Retires:` に書いたのに Accepted の時点で消せないなら、それは条件つき退役ではなく
**残し**である。`docs/DEFERRAL_LEDGER.md` の行へ降ろし、`Retires:` からは外す。
この一方通行を守ることで、`Retires:` は常に「もう履行された義務の記録」に収束し、
未履行の義務は登録簿という**数えられる場所**にだけ存在する。

### D4 — A がまだ ADR として存在しないときは、登録簿が受ける

「Phase S-4 が完成したら」のように **A がまだ起票されていない**場合、`Retires:` は
書けない (書く先の ADR が無い)。そのときは登録簿の行にし、満期を
**「A が起票されたとき」**にする — そして A を書く人が `Retires:` を書く。

これは既に DEF-020 が採っている形である。**2 つの機構は競合せず、A の存在で切り替わる。**

## Consequences — Evidence と tradeoff (§1.2 Evidence)

**Evidence:**

- `pnpm test:adr` — `Retires:` の解析・両方向の検査・ADR-125 以降の必須化。
  **この ADR 自身が最初の保持者**で、`GREP:docs/DEFERRAL_LEDGER.md::DEF-026` を退役させる
  (ADR-124 が「条件つき退役の検出は未設計」として登録した行 — 設計した今、消える)。
- **変異で確認済み** — DEF-026 の行を登録簿へ戻すと、この ADR が Accepted なので
  「退役させると宣言した GREP:… がまだ在る」で落ちる。消すと緑。
- 文法は `scripts/adr-status.mjs` (§1.1 — Status と同じモジュール。第二のパーサを作らない)。

**Tradeoff (引き受けたもの):**

- **書く人が退役を意識しなければ `Retires: なし` と書かれる。** 欄の存在は「退役は
  あるか?」を毎回問うが、答えの正しさは検査できない。これは ADR-123 の Q6 宣言表と
  同じ性質の脆さで、**機械が問えるのは欄の有無まで**である。
- **既存 2 つの手書き census は残す** (`RETIRED_MODE_SHAPES` / `RETIRED_SELECTION_COLORS`)。
  動いているものを置き換える価値が無く、ADR-103 / ADR-100 は cutoff より前である。
  新しい ADR は手書きしなくてよい、というのが利得である。

### 引き受けなかったもの (宣言する — 推論させない)

- **段の完了を発火事象にすること**は**未着手**。今日の発火は ADR の Status 遷移だけで、
  「Phase N が完了したら」は D4 のとおり登録簿経由の二段構えになる。順序表の段に
  完了状態の機械可読な表現が無いのが理由 (`- [x]` はあるが段の単位では読めない)。
  段が発火事象になれば D4 の迂回は不要になる。

## Lens notes

- **新しい原則 #32 を提案する** — 「**義務は、それを発火させる事象の側に置く**」。
  力学 1 の 5 例は無関係な文脈にまたがっており、CLAUDE.md Q2 の昇格条件
  (2+ の無関係な文脈) を満たす。#31 (不在には欄が無い) と近いが主張が違う:
  #31 は*数え方*の話、#32 は**義務の置き場所**の話である。B に義務を書くと、
  A が起きたことを B は知らない。
- **§1.1** — `Retires:` は「消される側」と「消す側」の 2 か所に義務が書けてしまう
  状況を、消す側 1 つに寄せる。`PROVISIONAL_UNTIL` は消される側に残るが、あちらは
  「自分がいつまで生きてよいか」を宣言するもので、役割が違う (共存する)。
- **原則 #19 Q3** — ADR を書く瞬間に問われる場所は 2 つある: `.claude/skills/adr/SKILL.md`
  のテンプレ (書く瞬間) と CI (マージの瞬間)。**両方に置く** — テンプレだけだと
  忘れられ、CI だけだと書き方が分からない。
