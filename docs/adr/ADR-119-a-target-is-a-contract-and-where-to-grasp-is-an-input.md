# 119. 掴む対象は契約であり、どこを掴むかは入力である — 無宣言の主役に契約を与える

- Status: Accepted (**D1 2026-08-14 / D2・D3 2026-08-14** — 全 3 判断が実装済み。D2 が「決めない」と残した UI の所有者は **ADR-128** が決め、同じ PR で語彙・入力面・3D 確認・検査が入った)
- Date: 2026-08-11
- Deciders: yuubae215, Claude
- 段: **G-2** (`docs/grasp/implementation-order.md` — grasp レーンの順序表)。前提: なし (G-0 / G-1 と独立)
- Supersedes / Superseded by: なし (ADR-117 が載せた `target` に契約を与え、掴む場所の宣言を足す)

## Context

ADR-117 は `target.surfaceSamples` と `obstacles` をワイヤに載せ、それによって
grasp-search が初めて候補を返すようになった。ところが**この 2 欄はリクエスト
スキーマに宣言されていない**。`graspSearchDeclaration` が宣言しているのは
`objectiveWeights` / `topN` / `plan` / `robot` / `camera` / `gripper` の 6 つで、
`additionalProperties: true` の隙間を通って残りが素通りしている。

つまり **探索が成功するかどうかを決めている当の欄が、契約を持たない唯一の欄**である。
原則 #29 は「全ワイヤは *契約あり* か *明示的に対象外宣言* の二状態のみ」と要求するが、
この 3 欄 (`target` / `obstacles` / `sampling`) はどちらでもない — ただ無い。

もう一つ、要件として出た問いがある: **「どこを掴むかの入力も要りますね」**。
いま掴む場所は完全に導出で、`FACES_BY_GRIPPER_KIND` (ADR-118) が面を選び、
3×3 グリッドが点を決める。ユーザーは「ここを掴んでほしい」と言う手段を持たない。
把持点はワークの機能 (取っ手・平面・逃がし) に依存するので、幾何から導けるとは限らない。

## Decision

### D1 — `target` / `obstacles` をスキーマに宣言する

現在載せている形をそのまま宣言する。リクエスト側の追加なので **`contractVersion` は
上げない** (ADR-083/084 の先例 — 壁は request スキーマを見ない) が、スキーマ本体・
BFF の導出型・`core/` の pydantic・準拠テストは同一 PR で動く。

`sampling` は現在フロントが送っていないので、**明示的に対象外と宣言する**か載せるかを
選ぶ。二状態のどちらかにするのが原則 #29 の要求で、「無い」は選択肢に入らない。

### D2 — 掴む場所を **宣言できる**ようにする (導出は既定のまま)

Layout DSL の Solid に**把持フィーチャ**を任意で持たせ、宣言があればそこから
`surfaceSamples` を作り、無ければ ADR-118 の面導出に落ちる。

これは既定値の押し付けではない: **宣言が無いことと、宣言された「どこでもよい」は
別の状態**として区別する (原則 #31)。導出に落ちたことは画面に出す — 「上面全体から
探しました」と言えるなら、ユーザーは自分が指定していないことに気づける。

フィーチャの語彙は最小から始める (面 + その上の領域)。点 1 つに縮退させないのは、
把持は面積を要求する操作だから (吸引はカップ径、ジョーは指の幅)。

### D3 — 導出と宣言の関係は「宣言が勝つ」1 方向

宣言があればそれだけを使う。導出結果とマージしない — マージすると、ユーザーが
「ここ以外は掴むな」と言ったつもりの宣言が、静かに広げられる。

## Consequences

### 得られるもの

- 主役の欄が契約を持ち、両端で検証される。今は BFF も `core/` も `target` の形を
  検査していない (open payload なので素通り) ので、壊れた target は無言で 0 件になる。
- 「取っ手を掴め」「この面だけ」がユーザーの語彙になる。

### 払うもの / 未解決

- Layout DSL (公開スキーマ) に語彙が増える。`schema/layout-1.0.schema.json` と
  Context DSL 側の `hydratedEntity` の両方 (ADR-117 で後者が前者に遅れていたのを直した
  ばかりで、同じ非対称がまた起きうる)。
- **UI が未設計。** 3D ビューで面や領域を指すのは、いまの選択モデル (実体単位) の外側。
  ADR-099 の選択の所有者に手を入れるのか、把持フィーチャ編集を別のツールにするのかは
  この ADR では決めない。
- 対象幾何が **文書由来でシーン由来でない**という ADR-117 の非対称は残る。掴む場所を
  宣言できるようにすると、その宣言も文書側に住むので、ビューポートで動かしても
  追随しない。どちらが所有するかは別 ADR。

### D1 実装で分かったこと (2026-08-14)

**`sampling` は「対象外宣言」ではなく載せる方を選んだ。** ADR 本文は二択にしていたが、
実測すると `core/` は既に `sampling` の 4 キーを読んでおり (`pipeline.py`)、
`templates/bin-picking-thin-container` は既に送っている。対象外と宣言するのは
事実に反する — 二状態のうち「載せる」しか成立しない。

**宣言そのものは open のまま残した。** `graspSearchDeclaration` の
`additionalProperties: true` はスキーマ自身が「Layout DSL が詳細を統治する」と
書いている意図的な設計で、閉じると `layoutVersion` の統治をこのスキーマへ移すことに
なる。D1 は「3 欄を宣言する」であって「封筒を閉じる」ではない。宣言した**各
オブジェクトは閉じた** — そうしないと、宣言することで得るものが元の open payload と
変わらない。この非対称そのものをテストで焼いた (`hardConstraints` は通り、
`target.graspHint` は落ちる)。

**3 本目の端が死んでいた (DEF-029)。** `packages/grasp-contract` は自前の
conformance suite を持ち `package.json` に script も在るが、ルートからも CI からも
呼ばれておらず、走らせると ajv strict でコンパイルすら通らない (response の
`graspNearestMiss` の discriminator が oneOf 枝に `properties.kind` を持たない)。
結果として `examples/grasp-search-request.json` の `gripper` が `kind` を欠いたまま
v5 に取り残されているのを誰も見ていない。**宣言は在るが読む機械が無い** = ADR-115 と
同型。直すには response スキーマを触る = 版上げを伴うので、次に意図して版を上げる回
(ADR-122 D2) に相乗りさせる。この ADR が主張する「両端」は走っている 2 本で成立して
おり、死んでいるのは 3 本目である。

### D2/D3 実装で分かったこと (2026-08-14 — 詳細は ADR-128)

**宣言は ADR-118 の欠陥を正面玄関から連れ戻せる。** 「ここだけ掴め」と 1 面を宣言する
動作はユーザーにとって完全に自然だが、`core/` は把持幅を**サンプル点の広がり**から測る
ので、平行ジョーで 1 面だけの宣言は幅をほぼ 0 にし、閉じられないハンドを通す。
**宣言を足すという行為は、導出が守っていた不変条件を無効化しうる** — 導出は
「ハンドが触る面」を知っていたが、宣言はそれを知らない。対向面を黙って足すのは D3 の
マージ禁止に触れるので、gap として止めて理由を出す (ADR-128 D5)。

**状態は 2 つではなく 4 つ必要だった。** 本文は「宣言の不在」と「宣言された
どこでもよい」の 2 つを名指ししていたが、実装すると**読めない宣言**が第 3 の実在する
状態として現れる。`derived` へ倒すと「宣言したのに無視された」= D3 が禁じる嘘になり、
しかも下流での見え方は `candidatesGenerated: 0` という*正しい形の答え*になる。

**UI の未設計は「決めなかった」ではなく「書けない宣言を作った」だった。** D2/D3 は
3 日のあいだ「宣言できる」と書かれたまま宣言する手段を持たなかった。ADR-128 の主題は
そこにある。
