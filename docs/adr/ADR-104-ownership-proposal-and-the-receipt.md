# 104. 編集の住所は所有権で決まり、記録は人の行為から始まる — 所有権・提案・証憑モデル

- Status: Proposed
- Date: 2026-08-02
- Deciders: yuubae215, Claude
- Supersedes / Superseded by: なし (ADR-050 の交渉オーバーレイの前提を拡張する)

## Context — Goal と力学 (§1.2 Goal)

**Goal:** 「**誰が何を変えられるか**」と「**何が記録に残るか**」を、モードを 1 つも増やさずに決める。

### 力学 1 — 「自分は誰か」が存在しない

このアプリには `actors` (`vision_engineer` / `robot_engineer` / `mech_engineer`) があり、
それぞれが共有変数に区間を主張する。しかし **`currentActor` に相当する状態は存在しない**。
`src/store/uiStore.js:158` の `personaFilter` は自身のコメントどおり
`persona projection highlight` — **見た目を減光するだけで書き込みを一切ゲートしない**。

結果、**全員が全員の主張を黙って書き換えられる**のが既定になっている。

### 力学 2 — 3D からの主張の書き換えは既に実装済みで、モードに閉じ込められている

`ContextController.js:892` の `createEditAdmissibleCommand` — 領域ウィジェットをドラッグすると
`stated` な admissible として文書に書き戻される undoable な 1 コマンド。
つまり「3D で実体を動かす = 主張が変わる」は**もう動いている**。
ただし `Context ▾ → 領域オーサリング` という**モードの中**でしか起きない。

ADR-103 の Map と同じ形である — **機能は既にあり、モードが不要**。

### 力学 3 — 「発見 / 解消」の 1 軸では編集の住所が決まらない

IA 再設計の途中まで、住所を「**発見** (計算で出る = 戻り値) / **解消** (合意が要る = 場)」の
1 軸で切り、編集を場の側に寄せていた。これは誤りだった。**直交する 2 軸**である:

| 軸 | 決めるもの | 判定 |
|---|---|---|
| **所有権** | 誰が**書ける**か | 自分の主張 = いつでもどこでも / 他人の主張 = 書けない |
| **合意の必要性** | **場に行くか** | 食い違いがあるか |

場は「**変える場所**」ではなく「**合意する場所**」である。

## Decision

### D1. 権限は「鍵の集合」であってモードではない

`keys: Set<actorRef>` を持つ。基数 **`0..N`**:

- `0` — 誰も名乗っていない。**既定値で埋めない**。全員書けるを既定にすると
  「他人の主張を黙って書き換える」が既定になり、誰も書けないを既定にすると
  名乗るまで何も編集できない。どちらも**推論させず選ばせる** (原則 #31)。
- `1` — 通常。
- `N` — **兼務者**。1 人が複数ロールを持つのは小さいチームでは普通。

「今どちらとして書いているか」だと切替が要る = **モード**になる。「どの鍵を持っているか」なら
集合なので**切替が要らない**。`ROBOT_CARDINALITY` (ADR-090) と同じ形の基数だが、
こちらは択一ではなく集合である点が異なる。

### D2. 所有権は実体ごと

グローバルな役割ではなく、**実体が持ち主を持つ** (ロボットベース CF は mech、Robot は robot_eng)。
所有者は `0` も取りうるが、**`0` は 2 種類ある**:

- **宣言済みの 0** — 「本当に所有者がいない」と人が宣言した。正当。
- **未宣言の 0** — **本当にいない / 名乗り忘れ / 誰が名乗るかのチキンレース**の 3 つが潰れている。
  正当なのは 1 つだけなので**警告する**。

正当な 0 は推論させず宣言させる (原則 #31)。宣言されていない 0 の**個数を数えて出す**のは
ADR-100 の ratchet と同じ形。

### D3. 「直接編集不可・提案可」を第三の状態にする

権限は 2 値ではない。実体でも数値でも規則は 1 つ:

```
鍵がある  → 確定 (主張がその場で書き換わる。場には行かない)
鍵がない  → 提案 (ゴースト = 点線・半透明。場の議題が +1)
```

「動かそうとすることはできる」= **提案**。これは repo が既に統治している
**decide / propose の動詞境界** (ADR-056/077、`Decision` の `proposed → agreed`) を
幾何の編集に適用したものであり、新しい概念ではない。

**提案は差分を運ぶ** — `現在値 → 希望値` + **理由**。理由はそのまま `Decision.rationale` に入る。
差分のない提案は「何を承認したのか」が残らず、証憑として不完全になる。

### D4. 記録は人の行為から始まる

```
計算されただけ (揮発)  →  人が場に上げた (議題)  →  決着した (証憑)
```

規則は 1 行:

> **導出値は保存しない。人の行為は保存する。**

- **衝突**は文書から毎回導出できる。保存すると**第二の源**になる (§1.1 / 原則 #24)。
  だから「場を開いて見ているだけ」では何も残らない。
- **議題化 / 承認 / 閉会**は人の行為で再計算できない。だから残す。
- 結論が出なかったことも結論の一種 — **「未決のまま閉会」も証憑に残す**
  (議題化が歴史なら、一方通行に消すのは筋が通らない)。

帰結として **場の議題 = 議題化された衝突 ∪ 提案**。カウンタは 3 本:
`≈ 衝突 (揮発)` / `⚑ 議題 (場にある)` / `◇ 未所有 (未宣言)`。同じ数に足さない —
衝突は**放置すると決まらない**が、提案は**放置しても現状のまま進む**ので、性質が逆である。

### D5. 承認は所有者の鍵を持つ人だけ。単独決定は記録しない

証憑の価値は「**所有者が**良いと言った」ことなので、誰でも押せると `decidedBy` に書く名前の
根拠がない。無効時は**理由を明示**する (repo の disabled-as-quest — 無効フラグとその理由は
**同じ述語の返り値**から来る。無言の no-op は禁止 — 原則 #11)。
衝突の解消は**関与する全員の鍵**が要る (既存の n-ary 合同確定と同形)。

**鍵を全部持つ状態 = スーパーユーザ = 1 人プロジェクト**であり、そこには交渉が存在しない。
`decidedBy` (**合意の証憑**) が要るのは当事者が**複数**のときだけで、
`rationale` (**理由の記録**) は要求を書く時点の別の話である。
したがって**単独決定で証憑が増えないのは欠落ではなく正しい姿** — 通常の編集は
CommandStack (undo) が扱い文書に残らない、という既存の切り分けと一致する。

### D6. 鍵は認証ではない

サーバのないクライアント側チェックは**誤操作防止の鍵**であって認証ではない
(文書 JSON も devtools も開ける)。UI 上でもそう名乗る。
実際のリスクは攻撃者ではなく「**他人の主張をうっかり書き換える**」ことなので、目的は達する。
**鍵の集合という構造は将来も変わらず、チェックだけが後でサーバ側へ移る** —
認証は BFF / `core` の責務であり、フロントは宣言と表示のみ (repo の層規律)。
初期実装はステークホルダごとの初期コードで足りる。

## Consequences

**得るもの**

- モードを 1 つも増やさずに権限を導入できる (D1 が集合であることによる)。
- 「場」が小さくなる。編集は所有権があればどこでも起こり、場に来るのは
  自分だけでは決められないものだけ。**提案が場に議題を入れる仕組み**になり、
  フォームを埋めて交渉を始める必要がなくなる。
- 証憑が既存機構に着地する — 承認は `Decision` として記録され、
  **Why タブ (`WhyBreadcrumb`, ADR-052) でそのまま辿れる**。

**払うもの / 必須の随伴作業**

- `docs/STATE_LEDGER.md` に 4 行 (鍵の集合 / 実体の所有者 / 提案 / 議題)。**コードより先に**。
- 3 状態 (直接編集可 / 直接編集不可・提案可 / —) を型で表す。フラグの散乱で暗黙化しない (§1.4)。
- 編集可否を見た目で区別する既存規約 (入力可 = 枠 + 内側の影 / 表示のみ = 枠なし) に
  第三の見た目 ([✎ 提案]) を足す。

**未解決 (実装前に決める)**

1. **承認が元の主張を更新していない。** 証憑には `200–350 → 200–420` が残るが主張は旧値のまま。
   承認は主張を書き換える行為のはずで、書き換われば衝突数も変わる。
   **証憑を残すことと状態を進めることは同じ 1 操作** (= undoable command) であるべきか。
   既存の `createApproveDecisionCommand` が同じ形を持つ。
2. **同一変数への提案が後勝ちで上書きされる。** 提案どうしの衝突は変数の衝突と同じ棚か。
3. **閉会した衝突の再燃**は新しい議題か前回の続きか。後者なら証憑は枝分かれ履歴になる。
4. **鍵の保有は時間とともに変わる。** 全鍵を持っていた時期の決定は、後から本物の担当者が
   入ったとき「誰も合意していない決定」になる。止めるほどではないが記録しておく。
