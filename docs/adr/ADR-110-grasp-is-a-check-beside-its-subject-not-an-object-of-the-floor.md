# 110. 把持探索は場の対象ではなく、主語の隣の検査である — 動詞を失った行の再分類

- Status: Accepted (実装済み 2026-08-05 — IA Phase 5.1。実測の結果、入口の個数は動かなかった: desktop 7 / mobile 7 の ratchet は**書き換えずに**通った)
- Date: 2026-08-04
- Deciders: yuubae215, Claude
- Supersedes / Superseded by: なし (ADR-105 D5 が決めた「把持は選択駆動で主語の隣」を
  **ヘッダ側にも通す**。ADR-106 D3 が器を動かした結果として残った不整合の是正であり、
  ADR-108 D1 の「入口は動詞で数える」/ D4 の「住所の根拠は動詞である」の適用)

## Context — Goal と力学 (§1.2 Goal)

**Goal:** *メニューの見出しが約束したことと、その中の項目がすることが一致している。*
そして「何も選んでいない状態から把持を調べたい」人が、行き先を名指しされた経路で
そこへ着く。

### 力学 1 — 行の動詞が、器の移動によって静かに変わった

`src/view/HeaderEntrances.js` の `FLOOR_TARGETS` は動詞 `open-floor` (場を開く) の
引数を 4 つ持つ。ADR-106 (Phase 3) が器を下部へ移し、ADR-105 D5 が把持を N パネルへ
移した後、この 4 行は同じ動詞を共有していない:

| 引数 | 押すと何が開くか | まだ「場を開く」か |
|---|---|---|
| `negotiate` | 下部の器 (Matrix / Cluster / …) | **はい** |
| `author` | 下部の器 (領域を 3D で動かす) | **はい** |
| `region-ghosts` | 未確定帯の表示 (場の語彙) | **はい** |
| `grasp` | **N パネル**の把持探索 (`context.grasp` を seed する) | **いいえ** |

トリガのタイトルは今も `'Context-first — requirements / conflicts / negotiation'` である。
4 行目はその約束を果たさない。**ADR-108 D4 が `Nodes` について名指しした欠陥と同型** —
あちらは「表示条件が一致していたから隣に居た」、こちらは「**かつて同じ器を開いていたから
隣に居る**」。どちらも住所の根拠が動詞ではない。

### 力学 2 — 「選択が無いときの経路」がここにしか無い

`src/components/NPanel/NPanel.jsx:127` は `{grasp && <GraspSearchPanel />}` である。
`context.grasp` を seed する経路は 2 つ: ロボットを選んで N パネルから (ADR-105 D5)、
または**このヘッダの行**から。後者は選択を要求しないので、**何も選んでいない状態から
把持探索へ入る唯一の経路**である。

したがって「動詞が合わないから消す」は解ではない。行き先を名指ししない移設は
無言の削除であり (原則 #16)、消えた経路は「押しても何も起きない」より発見が難しい。

### 力学 3 — 選択を要求しない探索は、第二の選択面になりかけている

選択が無いまま把持探索を開くと、主語 (どのロボットが / 何を掴むか) はパネルの中で
選ばれることになる。それは ADR-099 と ADR-107 が 2 本かけて消した形 —
**窓ごとの第二の選択状態** — の再生産である。今日それが害になっていないのは、
パネルが seed 済み FSM を表示するだけで、選択集合を持たないからにすぎない。

### 力学 4 — 実測: これは入口の個数を動かさない (申し送りの前提の訂正)

前回の申し送りは「再分類は入口の個数を動かす判断 = ADR-108 D2 の上界に当たる」と
書いた。数えると**そうならない**。`src/HeaderEntranceCensus.test.js` が数える母集団は
`Header.jsx` の JSX 要素であり、`FLOOR_TARGETS` の行は**入口ではなく引数**である
(それが ADR-108 D1 の要点だった)。

| 変更 | desktop 入口 | D2 の ratchet |
|---|---|---|
| `grasp` 行を `FLOOR_TARGETS` から外す | 7 → **7** | 動かない |
| `grasp` に新しい動詞 (`VerbMenu:SEARCH`) を与える | 7 → **8** | **上げる必要がある** |

つまり ratchet に当たるかどうかは、**再分類そのものではなく、どの案を選ぶか**で決まる。
下の Options が分岐点である。

## Options considered

- **A: 現状維持 (`open-floor` の 4 行目のまま)** — tradeoff: メニューの見出しが嘘を
  つき続ける。ADR-108 D4 を書いた直後の repo が、同じ形を 1 つ残していることになる。
  害は「見つけにくい」だけなので安いが、**ADR-108 の規則が例外を 1 つ持つ**という
  コストは安くない (次に住所を決める人が先例として引く)。
- **B: 行を消す** — tradeoff: 選択が無い状態からの唯一の経路が消える。移設ではなく
  無言の削除 (原則 #16)。**却下。**
- **C: 新しい動詞 `search` を立てて入口を 1 つ増やす (7 → 8)** — tradeoff: 動詞として
  正直 (「調べる」は「場を開く」でも「始める」でもない) だが、**機能 1 つに動詞 1 つ**を
  許すと、動詞の個数が機能の個数に比例し始める。それは ADR-108 が対象について禁じた
  成長を、動詞の側で再発させる形である。D2 の ratchet を上げる根拠としては弱い。
- **D: 把持は「主語の隣の検査」であって場の対象ではない、と分類し直し、選択が無いときの
  経路を N パネルの空状態へ移す (採用)** — tradeoff: ヘッダから 1 行消えるので、
  ヘッダしか見ない人には一時的に「無くなった」ように見える。これは**理由つき disabled**
  (`Select a robot to search grasps`) で受ける — ADR-065 の disabled-as-quest、
  ADR-108 が既に `requires` として持っている機構をそのまま使う。
- **E: `START` の 6 種目にする (`START_ENTRY_BY_KIND` へ 1 行)** — tradeoff: 入口の
  個数は動かず実装も最小だが、`START` の 5 種はすべて「**働き方を始める**」(文書を採る /
  物語を始める / ツアーに入る) であり、把持探索は現在のシーンへの**問い合わせ**である。
  同じ動詞に押し込むと `START` が「何かを始める」という無内容な動詞になり、ADR-108 が
  対象について潰した無限成長を、**動詞の意味の側**で引き受けることになる。

## Decision — Strategy (§1.2 Strategy)

**案 D。** 把持探索は場の対象ではなく、ADR-105 D5 が既に決めたとおり**主語の隣の検査**
である。ヘッダの `open-floor` は「場を開く」だけを引数に持つ。

### D1 — `FLOOR_TARGETS` は 3 行になる

`negotiate` / `author` / `region-ghosts`。3 行とも下部の器を開く = 動詞と一致する。
`grasp` 行は削除ではなく**移設**で、移設先を `RETIRED_FLOOR_TABS` と同じ形の
「引っ越し先の台帳」で名指しする (ADR-106 D3 の先例)。

### D2 — 選択が無いときの経路は N パネルの空状態が持つ

N パネルは選択が無くても描かれる (`NPanel.jsx` のパネル自体は常設 — 原則 #15)。
その空状態に把持探索の入口を**理由つき disabled** で置く:

```
Grasp search…   (disabled)
└ Select a robot to search grasps.
```

ロボットを選ぶと enabled になり、`context.grasp` が seed される。**判定と理由は同じ
返り値から出す** (`availabilityOf` と同じ形 — 原則 #25 / #11)。これにより:

- 経路は消えない (原則 #16 — 行き先が画面に在る)。
- **主語の無い探索が構築できなくなる** (力学 3 — 第二の選択面が生まれる余地を閉じる)。
- 「置く → 届くか見る → 置き直す」が選択の隣で閉じる (ADR-105 D5 の完成)。

### D3 — ヘッダの入口の個数は動かさない (ratchet は上げない)

desktop 7 / mobile 7 のまま。`src/HeaderEntranceCensus.test.js` の baseline は
**変更しない** — 変更が要ったら案 C を選んだ証拠であり、それはこの ADR の決定と
矛盾する。ADR-107 が `SelectionOwnership.test.js` の母集団を「作り直さずに通ること」を
決定の検算に使ったのと同じ形の証拠である。

### D4 — 前提の要求は `REQUIRES` へ 1 行足す

`REQUIRES.ROBOT_SELECTED` + `REQUIREMENT_REASON` の理由文 + `availabilityOf` の
dispatch を**同じコミットで**足す (`availabilityOf` は未宣言の前提で throw するので、
3 つ揃わないと落ちる — ADR-108 が既に置いた安全装置がそのまま効く)。

## Consequences — Evidence と tradeoff (§1.2 Evidence)

- **肯定的:** `Context ▾` の中身が見出しの約束と一致する。ADR-108 D4 の規則が例外を
  持たなくなる。主語の無い把持探索が**構築できなくなる** (力学 3 の芽を閉じる)。
- **受け入れるコスト:** 「何も選ばずにとりあえず把持画面を開く」が 1 手増える
  (ロボットを選ぶ手が要る)。これは ADR-105 D5 が既に受け入れたコストと同じもので、
  そのとき e2e が「`robot_base` を選んで 1 クリックで grasp へ届く」を焼いている。
- **受け入れるコスト (正直な限界):** ロボットが 0 台のシーンでは、この入口は永久に
  disabled のままになる。理由文はそのとき「ロボットを選べ」ではなく「ロボットが無い」で
  なければならない (ADR-090 の 0 台問題)。**理由の分岐は実装時に 2 種として宣言する** —
  1 つの理由文で両方を賄うと、0 台の人には嘘になる。台帳の行は
  `docs/STATE_LEDGER.md` §提案中の実体「把持探索の入口の可用性」(状態 3 / 基数は
  選択 `0..1` × ロボット `0..N` の積)。
- **検証 (証拠):** `docs/gsn/adr-110-grasp-is-a-check-beside-its-subject.gsn`。実装時の
  証拠は 4 つ — (1) `FLOOR_TARGETS` の全行が下部の器を開く (`FloorContainerCensus`)、
  (2) 入口の個数 desktop 7 / mobile 7 が**変わらない**、(3) 選択が無い状態で N パネルの
  入口が理由を持って disabled (e2e)、(4) ロボット選択で enabled → 探索が seed される
  (e2e)。**現時点ではすべて未来形** (Proposed の理由)。
- **波及 (blast radius):** `src/view/HeaderEntrances.js` (`FLOOR_TARGETS` 3 行 +
  `REQUIRES` 1 行 + 理由文 + dispatch)、`src/components/NPanel/NPanel.jsx` (空状態の
  入口)、`src/controller/AppController.js` (`onOpenGrasp` の呼び手が移る)、
  `src/HeaderEntranceCensus.test.js` (baseline は不変・引数の表は更新)。
  **ドメイン・契約・BFF・`core/` は 1 行も変わらない** — 探索の解法には触れない。

## Lens notes

- **§1.3 黒箱:** `GraspSearchPanel` の入力→出力は不変。変わるのは **seed する権利を
  誰が持つか**だけで、パネルの契約 (`context.grasp` が非 null なら描く) には触らない。
- **原則 #31:** 数えるべきは「場のタブが 3 つある」ではなく「**場を開かない引数が
  `open-floor` に 0 個**」である。前者は在るものを辿る数え方で、今日の欠陥を素通りする。
- **原則 #2 (Type Is the Capability Contract):** 案 E を却下した理由は型論でもある —
  `START_KIND` と「シーンへの問い合わせ」を同じ enum に入れると、`startEntryFor` の
  返り値が「働き方の始め方」と「検査の起動」の 2 義になる。

## 実装で変わったこと (2026-08-05)

俯瞰と実装が食い違った点だけを記録する。食い違いのほうを残すのが規律で、
黙って本文を書き換えると判断の履歴が消える (原則 #19)。

### D4 の住所 — `REQUIRES` ではなく entity-scope の宣言表へ

D4 は「`REQUIRES.ROBOT_SELECTED` + `REQUIREMENT_REASON` + `availabilityOf` の
dispatch を同じコミットで足す」と書いていた。**足さなかった。**

`REQUIRES` は**ヘッダの**入口が引く語彙であり、把持探索がヘッダから出た以上、
そこに行を足すと「どの入口からも引かれない前提」が 1 行できる。それは
`assertDeclarationsExist` が各所で落としている**空回りする宣言**そのもので、
しかも今日は誰も数えていない場所に生まれる。

代わりに、判定と理由が同じ返り値から出るという D2 の要件 (`availabilityOf` と
**同じ形**) はそのままに、住所を `src/view/EntityScopeChecks.js` — 既に
「この選択で把持探索が使えるか」を所有しているモジュール — に置いた。
2 種の 0 は `GRASP_BLOCKED_KIND` + `GRASP_BLOCKED_REASON` の対で、未宣言の種は
throw する。

### 基数を渡さない呼びは throw する (D4 の「正直な限界」の実装形)

「理由の分岐は実装時に 2 種として宣言する」を、*宣言し忘れられない*形にした:
`graspEntryFor(null)` は `robotCardinality` が無いと **throw する**。既定を
「ロボットは在る」に倒すと、0 台のシーンで「ロボットを選べ」という嘘が出る —
それは ADR-090 が潰した「欠けた入力に既定値を与える」欠陥と同じ形である。

### N パネルの Checks スロットが常設になった副作用

`{nPanelData && <EntityChecks />}` を無条件描画に変えたので、選択が無くても
`Unexamined` / `Adopt a context document.` が DOM に存在する (パネル自体が
非表示なので hidden)。ADR-105 の e2e 2 本が「DOM 順で最初の一致」を可視要素と
みなしていたため落ち、可視要素へ絞る形へ直した。**2 つ目の宣言された 0 が
生まれた日に、「最初の一致」は「その一致」ではなくなる。**

### 0 台の理由文は e2e から焼いていない (境界の宣言)

起動シーンのロボットを UI から消すには確認モーダルを含む複数手が要り、それを
焼くとテストの主語が「0 台の理由」ではなく「削除フロー」になる (原則 #20)。
2 種の 0 が別々の文言を出すことと、基数を渡さない呼びが throw することは
`src/FloorContainerCensus.test.js` が `graspEntryFor` を直接通して焼いている。
