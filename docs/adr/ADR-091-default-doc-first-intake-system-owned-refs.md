# 091. 入力の起点を「白紙からの生成」から「既定値入り完成文書の訂正」へ — ref をシステム所有にする

- Status: Proposed
- Date: 2026-07-25
- Deciders: yuubae215, Claude
- Supersedes / Superseded by: なし（ADR-063 の段階開示を一段深める。ADR-051 の入口カタログ・ADR-058 の seed 機構はそのまま資産として再利用する）
- References: ADR-063（選択優先インテーク — 白紙入力不能の前提）, ADR-058（fork & tweak / SeedAnchor / IntakeAssist）, ADR-051（要件入力の複数入口 / TemplateCatalog）, ADR-050（正準 doc・シーンは導出）, ADR-049（KPI/criterion/admissible）, ADR-089（起動ホーム画面）, ADR-090（基数を明示状態にする — 台帳の教訓）, PHILOSOPHY #1/#3/#11/#23

## Context — Goal と力学（§1.2 Goal）

### 観測

同一の痛みが 3 度目の dogfooding で報告された（2026-07-25、当事者）:

> コンテキスト入力するユーザが辛い。何入れたらいいかやっぱりわからないし、
> 考えないと入力できないのが辛い。

ADR-051 は入口を増やして**摩擦**を、ADR-058 は埋まった例を見せて**手本の不在**を、
ADR-063 は選択肢を先に出して**想起 (recall)** を、それぞれ下げた。それでも同じ文が
返ってくる以上、残っているのは量の問題ではなく構造の問題である。実コードを読むと
構造は 2 点に特定できる。

**(1) 「白紙フィールドを出さない」は達成されたが、doc 自体は白紙から始まる。**
`createBlankDoc()` (`src/context/DocBuilder.js:25`) は actors / variables /
requirements をすべて空配列で返し、Template Gallery の `guided` エントリの source は
`{ kind: 'blank' }` (`src/context/TemplateCatalog.js`)。つまり ADR-063 が用意した
「選ぶだけ」の正規ルートの第一歩は、**空の文書に最初のエントリを生産すること**である。
`WizardCatalog` の各ステップは `minEntries: 1` で committed なエントリを要求するので、
生産しない限り一歩も進めない。選択肢は先に出るようになったが、**選択の結果として
ユーザが値を作る**という向きは変わっていない。

**(2) 選択もまた判断であり、判断には自分の答えが要る。**
チップが並んでいれば「どれが自分に当たるか」を決めねばならず、決めるには自分の答えを
既に知っている必要がある。recognition は recall より安いが**ゼロではない**。
「考えないと入力できない」はまさにこの残余コストの名前である。

人間にとって最も安い入力行為は、生成でも選択でもなく **訂正**である。提示された答えが
自分のものと違うと気付くのは*照合*であって想起ではなく、事前知識なしに実行できる。
ADR-058 の fork & tweak はこの性質を既に発見していたが、**例外パス**（例から fork した
ときだけ有効）に留まっていた。

**(3) 付随して — 同一性をユーザに考えさせている。**
各フォームの先頭欄は `RefField`（`src/components/Context/IntakePanel.jsx:593`）で、
`a_robot` のような識別子の命名を要求する。ref は doc 内の同一性であって**システムの
所有物**（§1.1）であり、人間が発明する理由はどこにもない。最初に対面する欄が命名で
あることは、活性化エネルギーの純粋な上乗せになっている。

### Goal（解でなく性質で）

1. **0 入力で妥当な成果物が既に在る。** 何も入力しなくても validator が走り、
   3D が出て、checks が読める状態から始まる。入力は*思考の結果*ではなく
   *思考の道具*になる（現状は「考える → 入力する → 結果を見る」で、考える負荷が
   すべて前倒しになっている）。
2. **ユーザの仕事が訂正に還元される。** 合っているところは触らない。触った箇所だけが
   「自分のもの」になり、その進捗が見える。
3. **同一性をユーザに書かせない。** ref は採番の 1 箇所が所有し、上級者にだけ開示する。

### 力学・制約

- 正準は doc、シーンは導出（ADR-050）。既定値を持ち込んでも第二の源を作らない。
- 書き込み経路は不変（`DocBuilder` → command → `ContextService`、原則 #1）。
  本 ADR は**起点の中身**と**フォームの見せ方**を変えるだけで、経路を増やさない。
- 既定値は *例* であって *真実* ではない。ユーザが訂正しないまま提出すれば、
  もっともらしいが本人のものでない doc が成立してしまう（本 ADR の主要リスク）。
- 公開スキーマ（`schema/context-0.4.schema.json`）を変えずに実現したい。
  「まだ既定のまま」を表す新しいフィールドを生やすのは、閉じた層に optional 兄弟を
  足すのと同型の悪手（原則 #29 の精神）。

## Options considered

- **A: 現状維持（カタログ拡充を続ける）** — tradeoff: 追加コストは最小だが、同じ痛みの
  3 度目の報告であり、外挿は既に 2 回失敗している。むしろ選択肢を増やすほど「どれか」の
  判断コストは上がる（選択の逆説）。
- **B: NL インテークを主経路へ昇格** — tradeoff: ADR-063 Option B と同じ理由で却下。
  「何を入れたらいいか分からない」ユーザは自然言語でも言語化できず、保守的抽出は
  unknown を量産してフォームでの確定作業に戻る。問題が場所を変えるだけ。
- **C: 既定値入りの完成 doc を起点にし、ユーザの仕事を訂正に還元する【採用】** —
  tradeoff: 既定値カタログという継続的な保守資産を引き受ける。さらに「訂正されない
  既定値」が黙って成果物になるリスクを、可視化で緩和する義務を負う。
- **D: 「わからない/あとで」を一級市民にし、未確定のまま通過できるようにする** —
  有効だが、doc エントリに confirmed / unconfirmed / unknown の状態を導入するため
  状態台帳の閾値（核 §1.4）に乗り、状態機械の設計が先に要る。**C と直交して効く**ので
  本 ADR には含めず、後続 ADR に分ける（1 ADR = 1 決定、§1.1）。

## Decision — Strategy（§1.2 Strategy）

**C** を採る。ADR-063 の段階開示を、その上に一段積んで完成させる:

```
既定文書（何もしない: 完成した答えが既に在る）           ← 本 ADR で新設
  ⊃ ガイド付き（ウィザード: 選ぶ）                        ← ADR-063
    ⊃ 支援付き（フォーム + チップ/式アセット: 選んで改変）  ← ADR-058
      ⊃ エキスパート（未記入フォーム: 自作 — 廃止しない）    ← ADR-051
```

### 1. 既定文書を起点にする

`DocBuilder` に純粋関数 `createDefaultCellDoc(name)` を新設する。妥当な既定値の
入った**完成した** doc（actors / variables / requirements が埋まっており、
`ContextValidator` がエラー 0 で通り、checks が意味のある結果を返す）。

- Template Gallery の `guided` の source を blank から既定文書へ差し替える。
- `createBlankDoc()` は**廃止しない** — ADR-063 が既に「空のプロジェクトはエキスパート
  専用の位置づけへ」と決めており、その位置に「空から作る（上級者）」として残す。
- 既定文書は**版管理されたカタログ資産**として扱う（ADR-063 のカタログ運用ループを継承）。
  既定が的外れなら「訂正しかできない」は「全部訂正する」に退行するため、既定の質が
  そのまま UX の質になる。

### 2. 「まだ既定のまま」は既存の seed 機構で表す（新しい印を発明しない）

既定文書を採用するとき、同じ文書を `authorSeed` にも載せる（**自分自身を seed とする**）。
これだけで ADR-058 の既存機構がそのまま意味を持つ:

- `matchesSeed`（`IntakeAssist.js`）による seed-diff tint が「この欄はまだ既定のまま」を
  示し、ユーザが上書きした瞬間に tint が落ちる = **自分のものになった進捗**が見える。
- `SeedAnchorHint` が編集中に「既定はこうだった」を残す = 訂正の取り消しが目で戻せる。

スキーマ変更も新しい状態も不要で、第二の源も生まれない（§1.1）。ただし `SeedChips` は
「まだ doc に無い例を複製する」ための道具なので、self-seed では **doc に既に存在する ref
の chip を出さない**よう絞る（さもなくば全 chip が `_copy` を作る誘惑になる）。

### 3. 既定のまま提出できる静かな失敗を可視化する（原則 #11）

「訂正されない既定値」は本設計が引き受けるリスクであり、**緩和は必須**とする。
純粋関数 `pristineCount(doc, seed)`（`IntakeAssist` に置く。比較は `matchesSeed` の
再利用 — 判定の源は 1 つ）でまだ既定のままの欄を数え、ウィザードの review 段と
Checks パネルに「まだ既定のまま N 件」を出す。ブロックはしない（正直に告げるだけ）。

### 4. ref をシステム所有にする

- 純粋関数 `mintRef(kind, humanName, existingRefs)` を `IntakeAssist` に置く。
  採番は既存 `suggestRef` の一意化ロジックを**呼ぶ**（複製しない — §1.1）。
- フォームの先頭欄は ref ではなく **name（人間の言葉）**にする。ref は name から鋳造し、
  「詳細」の折り畳みの中に `ref (advanced)` として表示する。手入力による上書きは
  そこにだけ残す（エキスパート脱出口を潰さない — ADR-063 の規律）。
- 編集モードの `LockedRef` の意味は不変（ref は同一性、rename は remove + re-add）。
- **権威は 1 箇所**（原則 #1）: ref を書くのは `mintRef` か advanced の明示的上書きのみ。

## Consequences — Evidence と tradeoff（§1.2 Evidence）

### 肯定的

- 0 入力で checks と 3D が出るので、ユーザは**モデルを見ながら考えられる**。
  Goal 1 の「入力が思考の道具になる」がここで満たされる。
- ウィザードの `stepGaps` は committed エントリを数える実装なので、既定文書では
  最初から満たされる。結果として各ステップの意味が「生産する」から
  **「確認して、違えば直す」**へ変わる（ステップの prompt 文言も同時に改める）。
- 最初に対面する欄が識別子から人間の言葉になる。
- 新しい状態も新しいスキーマ欄も増えない（既存の seed 機構の再解釈で足りる）。

### 受け入れるコスト / 否定的

- **既定値は嘘になりうる。** 訂正されないまま提出された doc は、もっともらしいが本人の
  ものではない。§3 の可視化で緩和するが、消えはしない。これは意図的なトレードオフで、
  「白紙で何も作れない」よりは「既定から始めて直し漏れる」の方が回復可能と判断した
  （直し漏れは値が見えている限り後から気付けるが、白紙は成果物が存在しない）。
- 既定文書カタログの保守が継続コストとして増える。貧しい既定は退行を生む。
- ADR-063 の「ウィザード = 順序付きの器」という位置づけは保つが、各段の**タスクの型**が
  create から review へ変わるため、ウィザード定義の文言と完了条件の読み替えが要る。

### 検証（証拠）

**本 ADR の証拠はすべて未来形であり、この Status を Proposed に留める理由である。**
実装時に以下を証拠として置く（`src/**/*.test.js` は glob 実行なので置けば走る）:

- `DocBuilder.test.js` — `createDefaultCellDoc()` が `ContextValidator` でエラー 0、
  かつ actors / variables / requirements がいずれも非空（0 入力で成果物が在ることの証明）。
- `IntakeAssist.test.js` — `mintRef` の決定性と一意性（既存 ref 集合との衝突なし）を
  property ベースで。`suggestRef` を呼んでいること（採番ロジックの単一源）を参照同一性で。
- `IntakeAssist.test.js` — `pristineCount` が全欄未訂正の doc で総欄数、1 欄訂正で −1。
- self-seed 時に `SeedChips` が doc 内の ref を出さないことの単体テスト。
- e2e — 起動 → Guided → **一度も入力せず** review 段に到達でき、そこに
  「まだ既定のまま N 件」が出ている。

証拠が全面的に未来形であるため、必要なら §1.2 の鎖を `docs/gsn/` の論証木に外部化して
実装イテレーションごとに鮮度を更新する（gsn-meta-framework / gsn-maintain）。
本 ADR は Accepted 化の条件を「上記テストが緑であること」と定義しておく。

### 波及（blast radius）

`DocBuilder`（新関数）· `TemplateCatalog`（`guided` の source）· `ContextController`
（採用時に `authorSeed` を同載）· `IntakePanel`（RefField → NameField + advanced 開示、
SeedChips の絞り込み）· `IntakeAssist`（`mintRef` / `pristineCount`）·
`WizardCatalog`（文言と完了条件の読み替え）· `ChecksPanel`（pristine 件数の表示）。

契約（`packages/grasp-contract`）· `core/` · 公開スキーマ（`schema/*.json`）は**不変**。
本 ADR はフロントの起点と提示だけを動かす。

### 状態台帳への波及（核 §1.4）

新しい状態集合は増えない。ただし **Context doc エントリの基数が「起点で 0」から
「起点で N」へ変わる**。基数は状態でありながら状態に見えない（ADR-090 が発見した欠陥の
原因はまさにこれ）ため、実装コミットで `docs/STATE_LEDGER.md` に
「Context doc エントリ」の行を**基数列を埋めて**追加する。

## Lens notes

- **様態（§1.3）**: ウィザードは BPMN（逐次）のまま。変わるのはフローの形ではなく
  各タスクの型で、create から review へ。CMMN 化の必要はない。
- **§1.1（真実の源）**: ref の書き手を `mintRef` へ 1 本化。「既定のまま」判定は
  `matchesSeed` の再利用で、判定基準を二重に持たない。既定値そのものは doc と
  `authorSeed` の 2 箇所に載るが、後者は前者の**不変のスナップショット**（導出ではなく
  基準線）であり、書き手は採用時の 1 回だけ。
- **原則 #11**: 訂正されない既定値は「無言の失敗」の一種なので、数えて見せる義務を
  設計に組み込んだ（§3）。
- **Option D との関係**: 「わからない/あとで」を一級市民にする決定は状態の追加を伴い、
  台帳の閾値に乗る。本 ADR とは独立に効くので別 ADR に切り出す。
