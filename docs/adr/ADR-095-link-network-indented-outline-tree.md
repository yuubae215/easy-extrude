# 095. LINK NETWORK を「1 ノード 1 行」のインデントツリーへ — 希少な軸に可変量を割り当てるのをやめる

- Status: Accepted (実装済み — `src/view/LinkNetworkLayout.js` + `LinkNetworkView.js`。証拠は §Consequences 検証)
- Date: 2026-07-26
- Deciders: yuubae215, Claude (pairing)
- Supersedes / Superseded by: なし (ADR-048 §2.1 の *幾何割当* と ADR-094 の行/列配置を改訂。ノード集合・辺クラス・決定性・データ契約は ADR-094 から無改変で継承)

## Context — Goal と力学 (§1.2 Goal)

当事者の言葉:「LINK NETWORK は Mermaid のトップダウン記法みたいに縦にツリー状に
できないの? 見づらいのって情報が多いのもあると思ったけど、**横にツリーが同じ行として
伸びてる**のが見づらい原因の一つだと思った」。

これは解の形 (「Mermaid の TD にして」) で来ているので Goal へ持ち上げる。厳密には
Mermaid の `graph TD` は現状と同じ**階層作図** (深さ→縦、兄弟→横) であり、当事者が
指しているのはむしろ**ファイルツリー / アウトライナ形式** — 1 ノードが 1 行を占め、
深さがインデントで表現される形。持ち上げた Goal は二つ:

- **G1 — ラベルが常に読めること。** ノードの識別子 (名前) が省略もドット縮退もされずに
  読める。構造ビューの一次的な仕事は「誰が」であって「どこに点があるか」ではない。
- **G2 — 深さが一目で分かること。** 「この座標系は TF ツリーのどこにいるか」に、
  辺を目で辿らずに答えられる。

### 力学 — なぜ現状が「情報が増えるほど読めなくなる」方向に効くのか

`LinkNetworkLayout.computeLayout()` は資源配分が逆になっている:

| 軸 | 供給 | 現在そこに割り当てている量 | 実測 |
|----|------|--------------------------|------|
| 横 (x) | **固定 196px** (`PANEL_W 220 − MARGIN 12×2`)。左端占有の契約 (原則 #26 / ADR-048 §2.3) で広げられない | **兄弟数** — 実体が増えるほど増える | Solid 12 個で `denseMode` へ縮退 |
| 縦 (y) | **可変** (スクロール可能にできる) | **TF 深さ** — ADR-094 の融合後はほぼ定数 | 実測 `L = 2`、行は 2 本だけ |

固定・希少な軸に可変量を、可変にできる軸にほぼ定数を割り当てている。帰結が
`DENSE_SLOT = 22` の縮退則 (`W / maxRowCount < 22` でラベルを捨ててドット列にする)
であり、これは「情報が増えたら G1 を諦める」と明文で書いた行である。当事者の
「情報が多いのもあると思ったけど」という留保は、**情報量ではなく割り当てが問題**という
観測として正しい。

ADR-094 で 3 行 → 2 行に減らして svgH が 160→152 に戻ったのは縦の圧迫の解消であり、
横の枯渇には触れていない。今回の苦情は残っていた側。

### 位置 (グラフ / 層マップ上)

`computeLayout()` は純粋関数 (ADR-094 E1)。本 ADR が変えるのは**その返り値の幾何
(`x` / `y` / `svgH`) と `LinkNetworkView` の描画だけ**。ノード集合 (融合ノード)、
辺の 2 クラス (木辺 = 全域木 / SpatialLink = 余木辺)、決定性 (「同一シーン → 同一
ピクセル」)、`AppController._updateLinkNetwork()` のデータ契約 `{name, type, parentId}` は
すべて不変。ワイヤ契約 (grasp) には触れない — presentation 層の決定 (原則 #29)。

## Options considered

- **A: 階層作図のままパネルを広げる / 横スクロール** — tradeoff: 左端は共有資源
  (原則 #26)。`left:188px` の列は Map の縦ツールバーと共有しており、幅は増やせない。
  横スクロールは「一目で読む」という Goal そのものを壊す (スクロールしないと全体が
  分からないビューは構造ビューではない)。
- **B: 1 ノード 1 行のインデントツリー (採用)** — 行 = ノード (木の DFS 前順)、
  `x = MARGIN + depth × INDENT`、ラベルは左揃えで行の残り全幅を使う。木辺は L 字の
  ガター線。余木辺 (SpatialLink) は右側ガターのレーンに寄せる。縦は行数に比例して伸び、
  上限を超えたらパネル内スクロール。tradeoff: 縦の可視領域が有限なので「全体が一目」は
  ノード数が多いと縦スクロールに移る — ただし**縮退するのはリンクの表示であって
  ラベルではない**方向へ、縮退則の向きが反転する。
- **C: LINK NETWORK を廃止して Outliner に統合** — tradeoff: モバイルでは Outliner が
  ドロワーで既定非表示 (`OutlinerView.js` の `translateX(-100%)`) であり、LINK NETWORK が
  唯一の常設構造ビュー (ADR-094 の `MobileIsTheOnlyStandingStructureView` context)。
  委譲先が画面に無い。
- **D: 現状維持** — tradeoff: G1 が実体 12 個で明示的に放棄される (`denseMode`)。
  実運用のシーンはそこに届く。

## Decision — Strategy (§1.2 Strategy)

**案 B。** `computeLayout()` の幾何割当を「深さ→y / 兄弟→x」から
「**ノード順→y / 深さ→x**」へ入れ替える。

1. **行の割り当て。** 木辺だけで DFS 前順走査し、訪問順にそのまま行番号を振る
   (`y = TOP + row × ROW_H`)。走査の子順序は既存の `byNameId` (name, id の全順序) を
   そのまま使う — 決定性の根拠は据え置き。根が複数ある場合の根順序も既存の
   barycenter パスを流用してよいが、**インデント木では交差辺の削減が目的関数ではなく
   なる**ので、単純な `byNameId` へ落として barycenter を捨てる方が安い (§5)。
   どちらを採るかは実装時に、決定性テストが両方を固定できることを確認して決める。
2. **深さの割り当て。** `x = MARGIN + min(depth, MAX_INDENT_DEPTH) × INDENT`。
   深さが上限を超えたら**インデントを飽和させ、行頭に深さバッジ**を出す (横は有限資源の
   ままなので、可変量を無制限に流し込まない — 現状と同じ過ちを x 側で繰り返さない)。
3. **ラベル。** 行の残り全幅 (`PANEL_W − x − 右ガター幅`) を使える。省略は
   CSS の ellipsis 一段のみで、**ドット縮退 (`denseMode`) は廃止**する。縦は伸ばせる
   ので、情報量に対して縮退する必要がそもそも無い。
4. **木辺。** ノード間の直線ではなく、親の x に立てた縦線 + 子への短い横線 (L 字ガター)。
   ADR-094 が確立した「木辺は最も読める骨格」は維持し、描画形状だけが変わる。
5. **余木辺 (SpatialLink)。** 縦リストでは任意の 2 行を結ぶため、右側ガターに
   レーンを割り当てて弧を描く (git graph のレーン割当と同型の問題)。**レーン割当も
   決定的**でなければならない (辺の正準順 `(source, target, id)` はそのまま使う)。
   同時に走るレーン数が上限 `MAX_LANES` を超えたら、超過分は行の右端の**バッジ
   (`+N`)** へ縮退させる。縮退の対象がラベルからリンク表示へ移るのが本決定の核心。
6. **高さ。** `svgH` は行数から導出 (`TOP + rows × ROW_H + BOT + LEGEND_H`)、
   `MAX_PANEL_H` を上限に内部スクロール。`MIN_PANEL_H` / `MAX_PANEL_H` の値そのものは
   左端占有の契約 (ADR-048 §2.3) が決めるので据え置き。

**継承して変えないもの (第二の源を作らない — §1.1):** 融合ノード (Solid + body frame)、
`nodeIdByEntity` の非対称な往復、`isOriginFrame` 述語への委譲、辺の 2 クラスと凡例、
`computeLayout` が純粋であること、`update(entityInfos, links)` のシグネチャ。

## Consequences — Evidence と tradeoff (§1.2 Evidence)

- **肯定的:**
  - G1 — ラベル幅が「196px ÷ 兄弟数」から「196px − インデント」へ変わる。兄弟数に
    依存しなくなるので、実体が増えても 1 行あたりの読みやすさは劣化しない。
  - G2 — 深さが x 座標の階段として直接読める。辺を目で辿る必要がない。
  - 縮退則の向きが反転する: 混雑時に捨てるのが**ラベル**から**リンクの弧**に変わる。
    構造ビューが最後まで守るべきは「誰が」であって「どの線が」ではない。
  - `denseMode` という状態が 1 つ消える (台帳の行が減る)。
- **受け入れるコスト / 否定的:**
  - 「グラフ全体が一目」ではなくなる。ノード数が多いと縦スクロールが要る。ADR-048 の
    「一目で構造」は *深さ* の一目性へ再解釈され、*全体* の一目性は失われる。
  - 余木辺のレーン割当は新しい決定的アルゴリズムであり、新しいバグ面。交差の多い
    シーンでは右ガターが太り、ラベル幅を食う (レーン上限で頭打ちにする)。
  - 兄弟が横に並ばなくなるので、「兄弟同士の比較」は縦の走査になる。当事者の苦情は
    まさにその横並びだったので意図した交換だが、逆向きの不満が出うる仮説として
    GSN に立てる。
- **検証 (証拠):** 論証木は `docs/gsn/adr-095-link-network-indented-outline.gsn`
  (goal ごとの支えの正本はそちら。本節は入口のみ — §1.1)。起票時点の証拠は
  **すべて未来形**だった。実装で閉じた分:
  - `src/view/LinkNetworkLayout.test.js` — **39 本 pass**。うち決定性・純粋性・融合・
    基数 0 の各本は幾何が変わっても**1 行も書き換えずに通った** (契約不変の証拠)。
    書き換わったのは幾何期待値のみ (`rows` の意味、`nd.y <= graphH` → `contentH`)。
  - 新規: ラベル幅が兄弟数に依存しない / x は深さのみの関数 / 子は親より左に来ない /
    インデント飽和時にバッジ値が実深さと一致 / 同一レーンの区間は重ならない /
    レーン割当が入力順に依存しない / 上限超過バッジ数 = 落ちた辺数 × 2 (両端で数える) /
    行ピッチがシーン規模に依らず一定 / **`denseMode` が返り値から消えている**。
  - `pnpm test` 821/821 · `pnpm typecheck` · `pnpm build` · `pnpm test:gsn` すべて緑。
  - モバイル 390px 実測 (`docs/dogfooding/2026-07-26-link-network-indented-outline.md`) —
    **before: Solid 12 個でラベル 0 個** (凡例の 2 行以外は文字が 1 つも無く、点 24 個
    だけ)。after: 24 ラベルすべて描画、スクロール高 400px / 表示 146px。
    `denseMode` は理論上の縮退ではなく、実測で「名前が全部消える」だった。

- **波及 (blast radius) — 実際に触った到達可能ノード:**
  `src/view/LinkNetworkLayout.js` (幾何のみ — ノード集合・融合・辺解決は無改変)、
  `src/view/LinkNetworkLayout.test.js` (39 本)、`src/view/LinkNetworkView.js`
  (描画・スクロール DOM・凡例の固定)、`docs/STATE_LEDGER.md` (`denseMode` の消滅 +
  レーン / インデント飽和 / スクロール位置の 3 行を追加)、`docs/CODE_CONTRACTS.md`
  (Link Network の 2 規則)、ADR-048 (§2.1 幾何割当と §2.3 過密縮退の失効を明記)、
  `docs/NAVIGATION.md`、`docs/adr/README.md`、
  `docs/gsn/adr-095-link-network-indented-outline.gsn` (assumption → solution) と
  `docs/gsn/profit-growth.gsn` (事業木へ接続)。
  **触らなかったと宣言するもの:** `AppController` (データ契約 `{name,type,parentId}` と
  `update(entityInfos, links)` シグネチャ)、ノード集合・融合・辺の 2 クラス・
  `nodeIdByEntity` の非対称往復・`isOriginFrame` への委譲、`PANEL_W`/`MIN_PANEL_H`/
  `MAX_PANEL_H` (左端占有契約 ADR-048 §2.3)、grasp 契約・DSL・ワイヤ (presentation 層で閉じる)。

### 実装で起票時と変わった点 (黙って俯瞰を書き換えない — 原則 #19)

1. **`rows` の意味が変わったので `depth` を足した。** 旧 `rows` は層数 `L`。新しい
   `rows` は行数 (= ノード数) で、TF 深さは `depth` として別フィールドになった。
   1 つの名前に 2 つの意味を持たせるより、返り値を 1 つ増やすほうが安い (§1.1)。
   パネル高は `depth` ではなく `rows` から決まる — 深さは x が払うようになったため。
2. **barycenter パスは捨てた** (§Decision 1 の二択のうち安い側)。目的関数だった
   「列間の交差削減」がインデント木には存在しない。読み手のいないソートキーは
   反証不能な儀式になる。
3. **「ラベル幅は兄弟数に依存しない」の検査は途中で一度落ちた** — 最初の fixture が
   *兄弟数*と*リンク本数*を同時に動かしており、ガター幅 (レーン数) の差を兄弟数の
   差として読んでいた。ガター幅がリンク混雑に依存するのは本 ADR が**受け入れた**
   コスト (上限で頭打ち) であって主張の反証ではないので、レーン数を固定したまま
   兄弟数だけを動かす fixture へ作り直した。主張のほうを弱めていない。
4. **最下行が意図的に見切れる。** 表示域 146px は行ピッチ 16px の整数倍ではないので、
   スクロール可能なとき最終行が途中で切れる。行数へスナップすると `MIN_PANEL_H`
   の床 (ADR-048 §2.3) を割るため採らない。切れた行は「まだ下がある」の
   アフォーダンスとして機能する (原則 #16) ので、欠陥ではなく既知の見えとして記録する。
5. **スクロール位置の権威は DOM 要素 1 つ** (`_scrollEl.scrollTop`)。JS 側に鏡像を
   持たない — 再描画は SVG の子要素を作り直すがコンテナは触らないので、hover して
   もユーザーのスクロールは残る。台帳の行はこの「鏡像を作らない」ほうを記録する。


## Lens notes

- **層 + 契約 (§1.3):** 変更は presentation 層の内側で閉じる。層境界
  (`update(entityInfos, links)`) を跨がないことが「AppController 無改変」で確認できる。
- **黒箱 (§1.3):** `computeLayout` の入力→出力の**型**は不変で、`x`/`y` の**意味**だけが
  変わる。ADR-094 が確立した不変条件のうち「非根ノードは親より下の行にある」は
  インデント木でも成立する (DFS 前順は親を先に訪問する) ので、テストは書き換えずに
  意味が保たれる — 幾何を入れ替えても既存テストが通ることが、この決定が
  「契約の変更ではない」ことの証拠になる。
- **基数 (原則 #31):** 0 (リンク皆無 → 空の結果)、1 (単一ノード → 行 1 本。
  現行の `L === 1` ゼロ除算回避は `rows === 1` でも同型の分岐が要る)、
  N (レーン衝突・行あふれ・インデント飽和は N でしか出ない) を fixture で覆う。
