# 131. 再生成は投影を差し替える — シーンを全消しするのではない

- Status: Accepted (実装済み 2026-08-14 — 投影の footprint と部分的な取り壊し)
- Date: 2026-08-14
- Deciders: yuubae215, Claude
- Retires: なし — 置き換えたのは `_clearScene()` の**既定の意味**であって、消す形ではない。全消しは今も `loadContext` / 破棄が使う (そこでは全消しが正しい意味である)
- 段: **G-5 の前提** (`docs/grasp/implementation-order.md`)。ADR-129 D1 が着地するための条件
- Supersedes / Superseded by: なし (ADR-049 invariant 9「シーンは導出出力」を、**導出の範囲**まで具体化する)

## Context — Goal と力学 (§1.2 Goal)

**Goal:** *文書の宣言を 1 つ書き換えることが、文書が作っていない実体を消さない。*

### 見つかり方 — ADR-129 D1 の前提として

ADR-129 D1 は「ジェスチャの確定は文書への書き込みである」と決めた。実装に入る前に
書き込み先の経路を辿ると、doc-edit は必ずこう流れる:

```
ContextController._runDocEdit
  → ContextService.applyContextDoc(regenerate: true)
    → SceneService.importFromJson(scene, { clear: true })      (SceneService.js:665)
      → _clearScene()  … 全 object と全 link を dispose        (SceneService.js:929)
```

再インポートで戻るのは**文書が宣言した実体だけ**である。つまり `ref` を持たない実体
— Shift+A で足した箱、複製 (Shift+D)、輸入メッシュ、計測線 — は **doc-edit のたびに
消えていた**。

**実測 (2026-08-14, Playwright + `?graspStub=solve`):** `cell_robotics` を読み、
`ピックテーブル` を Shift+D で複製し (Outliner 12 行)、面チップで掴む場所を宣言すると
**10 行に戻る** — 複製が消える。エラーも警告も出ない。

### なぜ今日まで問題にならなかったか、そしてなぜ今から問題になるか

今日 doc-edit を起こすのは「掴む場所の宣言」(ADR-128) と合意の場の操作だけで、
どれもパネルの隣の稀な操作である。**ADR-129 D1 はこれを G / R の確定ごとに起こす** —
このアプリで最も頻繁なジェスチャである。頻度が上がったから欠陥になるのではなく、
**頻度が低かったから見つからなかった**。

### 力学 — 消滅には状態が無い (原則 #31)

削除は正当な削除とまったく同じイベント (`objectRemoved`) を出す。だから:

- ログを見ても「消してよいもの」と「消してはいけないもの」が区別できない
- *在るもの*を辿る検査は、消えたものについて何も言わない
- ユーザーから見ると「さっき置いた箱が無い」だけで、原因は 3 手前の宣言にある

ADR-129 が名指しした「動かしたのに答えが変わらない」と同じ**欄を持たない事故**で、
向きが逆 (あちらは古い値が残る、こちらは在るべき物が消える)。

### ADR-129 自身の前提と矛盾していた

ADR-129 D1 はこう書いている:

> `ref` を**持たない**実体 (文書由来でないアドホックなオブジェクト) には書かない。
> それは欠落ではなく**状態**で、「この物は宣言されていない = 探索の対象にならない」と
> 画面に出す

**状態であるからには、宣言を 1 つ書き換えるたびに黙って消えてはならない。**
ADR-129 はこの前提を要求しながら、それが今日成り立っていないことを見ていなかった
(ADR は「選択・カメラ・ゴーストが保たれるか未検証」と書いたが、消えるのは**実体
そのもの**だった — 実測すると選択とカメラは保たれる)。

### 「再生成」という語が 2 つの意味を持っていた

| 場面 | 正しい意味 | 今日の実装 |
|---|---|---|
| 文書を読み込む (`loadContext`) | 入れ替え — 前の文書の周りに生えたものも去る | 全消し ✅ |
| 文書を破棄する | 入れ替え (空へ) | 全消し ✅ |
| **宣言を 1 つ書き換える** (`applyContextDoc`) | **投影の差し替え** — 文書が作ったものだけ | 全消し ❌ |

3 行目だけが間違っている。1 つの動詞に 2 つの意味が乗っており、**強いほうが既定**
だった。

## Options considered

- **A: `ref` を持つ実体だけ消して再生成する** — tradeoff: 判定が実体ごとで安いが、
  **派生で生えたものを数え落とす**。Solid の Origin CF (`_ensureOriginFrames`) や
  `ensureRobotFrames` の upgrade は `ref` を持たないので「未宣言」として保存され、
  次の投影が同じ id を作って衝突する。母集団の取り方が間違っている。**却下。**
- **B: 投影が自分で作ったものを覚える (footprint)** — tradeoff: `ContextService` に
  状態が 1 つ増える。しかし母集団が正しい — 派生も含めて「投影が作った」で閉じる。
  **採用。**
- **C: doc-edit のたびに未宣言実体を退避して復元する** — tradeoff: B と同じ効果だが、
  退避先が**第二の源**になる (§1.1)。実体が 2 か所に居る瞬間が生まれ、その間に
  イベントが飛ぶと片方だけが更新される。**却下。**
- **D: 再生成しない (差分適用)** — tradeoff: 正しい方向だが、コンパイラの出力全体を
  差分で当てる設計が要る。ADR-129 の前提を閉じるには過大 (§5 過剰モデリング禁止)。
  **却下 — ただし将来の向きとしては正しい。**

## Decision — Strategy (§1.2 Strategy)

### D1 — 再生成は「投影の差し替え」。投影の外側は触らない

`applyContextDoc(regenerate: true)` は、**直前の投影が作った実体だけ**を取り壊して
から新しい投影を入れる。それ以外の実体はシーンに残る。

### D2 — 母集団は `ref` ではなく **footprint** で取る

`ContextService._projectedIds` = 直前の再生成がシーンに作った id の集合。不変条件:

```
footprint = 再生成直後の全 id ∖ 保存した id
未宣言    = いま在るもの ∖ footprint
```

`ref` で判定しないのは A の理由 — 派生で生えたものを数え落とすからである。
「投影が作ったもの」で閉じると、派生も自動的に投影の側に入る。

### D3 — 全消しは**消える**のではなく、**意味の合う場面に残る**

`loadContext` / 破棄は今も全消し (`preserveUndeclared: false`) で、そこでは全消しが
正しい: 別の文書を採るとき、前の文書の周りに生えた物を持ち越すと、次のプロジェクトに
前のプロジェクトの残骸が混ざる。**2 つの意味を 1 つの動詞から分離した**のであって、
片方を消したのではない。

### D4 — 再生成の入口はちょうど 1 つ (`_projectScene`)

`loadContext` / `applyContextDoc` / 破棄が別々に `importFromJson` を呼んでいると、
保存の規則を**持つ経路と持たない経路**が並ぶ。欠陥は必ず持たないほうに住む
(ADR-097 が pose で見つけた形)。呼びを 1 本に畳み、直接呼びの個数を検査が数える。

### D5 — link は両端が残るときだけ残る

片端が投影と一緒に消えた link は「弱い link」ではなく**壊れた link** である。
部分的な取り壊しでは、両端が保存されるものだけを残す。

### D6 — 検査は「消えてよかったものの個数」で書く。消えたものでは書かない

母集団は footprint で、その外側が 1 つでも消えたら落ちる。逆向きも問う —
**保存の規則が投影まで覆っていないこと** (文書から消した実体がシーンに残らないこと)。
片方だけだと、保存を広げすぎた実装が緑を出す。

## Consequences — Evidence と tradeoff (§1.2 Evidence)

### 得られるもの

- ADR-129 D1 が着地できる。G / R の確定が文書へ書き戻されても、宣言外の実体が消えない。
- 今日既に起きていたデータ消失 (掴む場所を宣言すると複製が消える) が止まる。
- 「宣言されていない」が**状態として生き延びる** — ADR-129 D1 が画面に出すと決めた
  状態は、まず存在し続けなければ出しようがない。

### 受け入れるコスト / 否定的

- `ContextService` の状態が 1 つ増える (`_projectedIds`)。導出物ではなく**記録**で、
  「投影が何を作ったか」は再生成の瞬間にしか分からないので記録するしかない。
- **undo の意味が変わる。** doc-edit の undo は文書を戻して再投影するので、
  未宣言の実体は undo を跨いでも残る (消えて戻ってくるのではなく、ずっと在る)。
  これは正しい振る舞いだが、「undo で全部戻る」という素朴な期待とは違う —
  未宣言の実体は文書の履歴に載っていないので、載っていない物が文書の undo で
  動かないのは一貫している。
- **差分適用ではない。** 投影は今も毎回作り直されるので、宣言済み実体の
  meshView は再生成のたび破棄・再構築される。速度は ADR-129 が受け入れたコストのまま。
- 部分的な取り壊しは `_worldPoseCache` / `_mountLocalPositions` /
  `_fixedJointTransforms` を **id 単位で**掃除する。全消しの `clear()` と違い、
  掃除し忘れた辞書があると保存された実体が古い姿勢を持ち続ける (今日 3 つとも掃除
  しているが、4 つ目の辞書が生えた日にここが**静かに**壊れる — 個数を数える検査は
  持っていない。限界として宣言する)。

### 検証 (証拠)

`docs/gsn/adr-131-a-regeneration-swaps-the-projection.gsn` が goal ごとの支えの正本。

| 主張 | 問い所 | 実行結果 |
|---|---|---|
| 未宣言の実体が doc-edit を跨いで残る | `src/DeclaredProjectionOwnership.test.js` | **5 pass** |
| 修正が無ければ落ちる (非空虚) | 同上を preserve 無効化して実行 | **2 fail** — 空回りしていない |
| 保存の規則が投影まで覆っていない | 同上 (文書から消した実体はシーンからも消える) | pass |
| 再生成の入口が 1 つ | 同上 (`importFromJson` の直接呼びの個数) | pass |
| 実機で残る | Playwright: 複製を作る → 掴む場所を宣言 | **12 行 → 12 行** (修正前は 10 行) |

**この証拠が構造的に見逃すもの:** 単体レーンの fake は id の Map であって、
meshView の dispose も link の再構築も持たない。「残った」と「正しく残った」は
別の主張で、後者は実機の 1 例でしか見ていない。とくに **link の片端が投影側に在る
ケース**は、どちらのレーンでも通していない (D5 の規則は書いたが、その規則が要る
シーンを作る手順が今日は無い)。

## Lens notes

- **§1.1:** 「投影が作ったもの」の権威は footprint ただ 1 つ。実体ごとに
  `ref` を問い直す述語を各所に書かない。
- **原則 #31:** 消滅には状態が無い。数えるのは消えたものではなく、**消えてよかった
  ものの個数**である。
- **原則 #1:** 再生成の入口を 1 本 (`_projectScene`) に畳んだ。規則を持たない経路が
  並ぶことが欠陥の住処である (ADR-097)。
- **ADR-049 invariant 9 との関係:** 「シーンは導出出力である」は生きている。
  この ADR が足したのは**導出の範囲** — 導出物であるのは*文書が投影した部分*で
  あって、シーンという入れ物そのものではない。
