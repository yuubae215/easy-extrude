`01-inventory.md` の 48 機能をどの物差しで切るか。対話で導出した過程の記録
(結論だけでなく、**却下した物差しとその反証**を残す — 同じ誤りを再導入しないため)。

## 採用した基準: 検証の主体は単数か複数か

> 検証されているのは**値ではなくクライテリアの食い違い**であり、
> **食い違いは1人の視野の中には存在しない**。

- **単数**(自分の入力を自分の基準で測る) → 計算で出せる → **戻り値**
  対象の隣に、常時、待たずに出る。
- **複数**(各ステークホルダーの*暗黙の*クライテリアとのギャップ) → 計算で出せない → **場**
  集まる場所が要る。`Matrix` が actor × variable の行列である理由そのもの。

つまり住所は**対象の性質ではなく、クライテリアの所有者の数**で決まる。

### 系: 共有 KPI は「場」まで待たせない (shift-left)

場まで待つと収束が場の往復回数に比例する。CI が起こしたことと同型:

| | 統合 (旧) | 統合 (CI 後) |
|---|---|---|
| gap の判明 | 結合テストフェーズ (場) | push 直後の赤/緑 (戻り値) |
| 収束 | 場の往復回数だけかかる | 場に来る前にほとんど潰れている |
| 場 | — | **消えない。議題が変わる** |

したがって:

- **戻り値 = gap を発見する**(早く・自動・全員に同時に)
- **場 = gap を解消する**(交渉・決定・承認)

現状の渋滞は、**発見と解消を同じ場でやっている**ことに由来する。

## 却下した物差し ①: 入力 → 出力 → 検証(直線)

**反証は判断そのもの。** `4 Robot を置く`(入力)と `37 Grasp Search`(検証)は
直線で切ると別グループ = 遠くに置かれる。しかし両者は同じループの中にいる:

```
置く → 届くか見る → 置き直す → …
```

**現行 UI はこの直線を忠実に実装した姿である** — AddMenu(左上)と
`Context ▾` の奥のタブ(右端・4クリック)。**ワークフローを直線に写すと、
ループの両端が必ず最も遠くなる。** 直線が病気であって薬ではない。

核 §1.3「プロセス様態 (BPMN vs CMMN)」— 形の取り違えは付随的複雑性の常習的な源。
このアプリには**両方の様態が入っている**:

- **CMMN 的**(探索・裁量・ループ) — 置く / 動かす / 押し出す / 届くか見る
- **BPMN 的**(目標駆動・順序あり) — Wizard / Intake / テンプレ開始 / 承認フロー

現在この2つは**同じ 280px のタブ列に同居**している(`Wizard` の隣が `Grasp`)。

## 却下した物差し ②: 「場所か戻り値か」の二択

偽の二分法。対象の性質ではなく所有者の数が効くので、同じ「検証」でも両側に分かれる。

## UI が優先する層: 意味 > 幾何

> UI としては意味の層を優先する。幾何はバックエンドの役割。

これはリポジトリの憲法 (CLAUDE.md) と**同型**:

> `src/` は解法を持たない。IK / 干渉 / リーチ / 把持安定性の *解き方* は `core/` に
> のみ書く。フロントは DSL で参照名を**宣言**し、結果は契約経由で受け取って**表示**する。

→ **画面の構造をアーキテクチャの層構造と同型にできる**(住所を議論で決めなくてよくなる)。

### 帰結: 現状は主従が逆

| | 担当する層 | 現在の待遇 |
|---|---|---|
| Outliner | 幾何 / TF 階層 (ADR-094 以降は文字通り TF spanning tree) | 左 **200px 常設**・主ナビゲータ |
| Link Network | **意味** (SpatialLink = cotree edges + 注釈) | 左下 220px・リンク 0 本で自動消滅・Context 中は強制非表示 |

意味の層が、自分から隠れる隅のパネルに置かれている。

### 裏付け: マップ要素は関係グラフの一要素(実装で確認)

`src/controller/AppController.js:1813-1822` — `_updateLinkNetwork` は
`scene.objects` 全件を走査し、Lynch 注釈をノード種別として流し込む:

```js
: obj instanceof AnnotatedLine   ? 'annot-line'
: obj instanceof AnnotatedRegion ? 'annot-region'
: obj instanceof AnnotatedPoint  ? 'annot-point'
```

Map で描く要素と関係グラフは、仕様上も**実装上も**同じ 1 つのグラフ。

### 検出した違反

**28 Checks は共有 KPI そのもの**(全員が見るべき合否)= 最も戻り値であるべきもの。
現在の住所は `Context ▾ → New Project → テンプレ選択 → 交渉オーバーレイ → Checks タブ`
(しかも doc が checks を宣言しないとタブ自体が現れない)。
**共有 KPI が最も場に縛られた場所にある** — 上の原則からの直接の帰結として逆。

**32 Assets の発見可能性** — 作者本人が UI から到達できることを認識していなかった
(`ContextController.js:677` の `enterNegotiation` は文書未ロードだと warn トーストで
行き止まり。実際の経路は `New Project` 経由の最短 4 クリック)。原則 #16
「発見可能性は成果物である」の違反。住所が**タスクの近さではなく実装された時期と場所**で
決まった証拠 (ADR-063 Phase 4 が Context の文脈で作られたため `ContextLayer` のタブになった)。

**タブ列の物理的破綻** — `ContextLayer.jsx:133-152` はタブを `flex:1` で並べる。
パネル幅 280px / タブ 10 枚 = 1 枚 28px、`padding: 6px 2px` を引くと文字に 24px。
`fontSize: 10px` の `Overview` は約 45px 必要で**物理的に入らない**。

## 決着 (段階3-4 へ)

- **25 Matrix は両方** — ただし「1 つが両方」ではなく**解像度の違う 2 つが 1 タブに畳まれていた**。
  集約(未解決 N 件のスカラー)= 発見 = 常設 / 展開(actor × variable の行列)= 場 = 呼び出し。
  段階的開示。
- **3D ビューの位置づけ = 入力の検算 (エコーバック)**。数値だけでは空間を想像できないから置く。
  ADR-063 Goal 2「the numbers are the artifact」の一般化。ここから**禁止事項**が 1 つ導かれる:
  **3D を覆う置き方をしない**(解釈の可視化が確定後に来ると「そういう意味だったの?」事故になる)。
  面積が最大なのは変わらない — ビジュアルヒエラルキーは**注視時間**の話で正本性の話ではない。
- **Map はモードではなく視点プリセット** — 下の「副産物」を参照。

ゾーニングと各配置の根拠は**ワイヤーフレーム HTML の注釈が正本**
(`easy-extrude-wireframe-v2.html` の①〜⑧)。ここには複製しない (§1.1)。

## 副産物: `STATE_LEDGER.md` 既知の負債 #1 が解ける

台帳はこう記録していた:

> **モードの権威が二つある。** 文書上は OBJECT / EDIT / MAP の 3 択だが、実装は
> `SceneModel._selectionMode` (2 値) と `MapModeController.state.active` (boolean) の直積。
> `edit` かつ `mapMode.active` は型として表現可能。**3 値の enum 一つに畳めば**
> 不正状態が表現不能になる。

台帳の処方は「畳んで**禁止**する」。IA 側の結論は「**そもそも不正ではなかった**」:

| | 台帳の案 | 本再設計の案 |
|---|---|---|
| 手段 | OBJECT\|EDIT\|MAP を 1 enum へ | Map をモードから**降ろす** |
| `edit` × 上から見る | **禁止**される (編集中に真上から見られない) | **正当**。カメラは編集状態と直交 |
| 消えるもの | 不正状態 | **状態そのもの** |

欠陥は**論理の誤分類**(ビューのパラメータをモードとしてモデル化した)なので、
物理側で enum に畳むと誤分類が固定される (核 §0「論理 → 物理の順」)。
旧 Map モードは 3 つに分解して**全部が既存の棚に収まる**:

```
カメラ (上からの正射投影) → 視点プリセット = ビュー上のオーバーレイ (近接の原則)
描画ツール (Lynch 5 種)   → 「置く」グループ = 他のオブジェクトと同じ
オブジェクト (Annotated*) → 通常のオブジェクト ← 実装は既にこう
```

**実装する場合の必須作業**: `docs/STATE_LEDGER.md` の「マップモード」行と既知の負債 #1 の
更新、`docs/STATE_TRANSITIONS.md` §Map Mode の改稿、および**この決定の ADR**
(モードから視点プリセットへの再分類は非自明かつ不可逆寄り)。

## 未決だったもの (決着の記録)

**決着済みの項目も消さない** — 消すと「この問いは考えられたのか」が辿れなくなり、
同じ引っかかりが再導入される。決着した項目は行き先を名指しして残す (原則 #19)。

| 未決だった項目 | 決着 |

| **場で変数を選んでいる間の選択の所有者** — 右パネルは「Robot の詳細」のまま。いま選択されているのは Robot か `d_ref` か。選択モデル (ADR-099) との衝突 | **決着 (ADR-107)** — 選択モデルは 1 つのまま、**要素の種**を 2 つ (実体 / 文書の変数) へ広げる。混在は型で表現不能、変数の 3D の姿は未確定帯、制約されている実体は `contextual` 軸の DIMMED で残る。**この衝突は ADR-106 で場と N パネルが同時に見えるまで存在できなかった** — 排他が問いを隠していた |
| 残り機能への基準の適用 (ファイル / 入門系 **38-48**) | **決着 (ADR-108)** — 第二の物差し (入口は動詞で数える) を当て、48 行すべてに住所が付いた。被覆は散文ではなく `src/InventoryCoverage.test.js` が数える。**この行は 2026-08-04 まで「未着手」のまま残っていた** — 完了しても宣言が畳まれない形の実例で、ADR-109 §力学 2 が数える対象そのもの |

## 第二の物差し: 入口の個数が「動詞 × 対象」の直積になっていないか

機能 38-48 (ファイル / 入門系) への適用。**最初の物差しは効かなかった** — 「クライテリアの
所有者は単数か複数か」は *検証* の物差しであり、ファイル操作も入口もそもそも検証ではない。
効かないこと自体が導出条件になったので、実測から第二の物差しを起こす。

### 実測 (`src/components/Header/Header.jsx` から数えた)

**「始める」入口** — 覚えている個数ではなく、コードから導出した個数:

| # | 入口 | 呼び出し | 出所 |
|---|------|---------|------|
| 43 | `Layouts` → HomeScreen (レイアウトテンプレ) | `onOpenHome` (`:110`) | ADR-089 |
| 42/47 | `New Project` → TemplateGallery (Context テンプレ) | `onOpenTemplateGallery` (`:319`) | ADR-051 Phase 2 |
| 46 | `Tutorial` → 6 ステップの物語 | `onContextDemoClick` (`:332`) | ADR-047 |
| 45 | Tour カード (5 クエスト・左下・デスクトップのみ) | `uiStore.tour` / `TourCard.jsx` | ADR-065 Phase 6 |
| 31 | Wizard (誘導インテーク) | `ContextLayer` のタブ | ADR-063 Phase 3 |

**5 つある。** `03-implementation-order.md` は「入口の 4 重導線」と書いていたが、
数えると 5 だった (`Tutorial` が落ちていた)。**記憶は母集団の権威ではない** — ADR-102 の
規律がそのまま当てはまる。

**ファイル操作** — 同じくヘッダから:

| 対象 → / 動詞 ↓ | シーン JSON | サーバ | Context 文書 |
|---|---|---|---|
| **持ち出す** | `Export` (`:111`) | `Save` (`:98`) | `Save Context` (`:321`) |
| **持ち込む** | `Import` (`:112`) | `Load` (`:99`) | `Import Context…` (`:320`) |

**2 動詞 × 3 対象 = 6 入口**が、ヘッダに**平坦に並んでいる**。

### 導出された物差し

> **入口は動詞で数える。対象は入口ではなく引数である。**

両方の帯が**同じ欠陥**を持っている:

- ファイル: `{持ち出す, 持ち込む} × {シーン, サーバ, Context}` の**直積**が入口の個数
- 入口: `{始める} × {レイアウトテンプレ, Context テンプレ, 物語, クエスト, 誘導フォーム}` の直積

対象ごとに入口を生やすと、**対象が増えるたびにヘッダが伸びる**。伸びは有界でない —
これは ADR-060 が契約について禁じた「`optional` 兄弟を生やさない (無限成長の防止)」の
**UI 版**である。ワイヤ v8 が場について測った「280px に 10 タブ = 文字が入らない」も
同じ成長の別の出口であり、器を変えても**生やす側**を止めなければ再発する。

### 副産物: 機能 40 (Node Editor) は誤分類だった

`40 Geometry DAG を編集 (Node Editor)` は 25-37 の適用にも Phase 1-4 にも現れない。
ヘッダ上の住所を見ると理由が分かる — `Save` / `Load` / `Nodes` が**同じクラスタに並び**、
3 つとも「BFF 接続時のみ表示」で条件が同じ (`Header.jsx:29-30` のコメントがそう書いている)。

つまり Node Editor は**ファイル操作だから**そこに居るのではなく、**表示条件が同じだから**
そこに居る。これは `32 Assets` について見つけたのと同じ形で、住所が**タスクの近さではなく
実装された時期と条件**で決まった証拠である。Node Editor は第二の**編集器** (Geometry DAG)
であって、持ち出し / 持ち込みの動詞を持たない。

**表に在るのに誰も触れていない行**が 1 つあったということは、グルーピングの母集団は
48 ではなく実質 47 だった (原則 #31 / ADR-102 — 数えるべきは表の行ではなく、
*表が覆えていない*個数)。

## 被覆表: 48 行はどこへ行ったか

`01-inventory.md` の **48 行すべて**に住所を与える。この表は「発見の結果」ではなく
**分類の宣言**である — 覆えていない行があることは、その行を誰も考えなかったという事実
そのものなので、隠さず数える (原則 #31 / ADR-102)。

**機械が問う場所**: `src/InventoryCoverage.test.js`。母集団は `01-inventory.md` の
行番号から導出し、この表に現れない番号を数える (0 個であること)。逆向きも問う —
