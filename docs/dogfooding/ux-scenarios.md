# Grasp Search — UX 検証シナリオ

**目的:** grasp-search の UX を、バックエンド無しで・最短で・再現可能に検証する。

記録様式と既定値獲得の作法は `README.md`。この文書はその**前段** — 「何を見に行くか」
の一覧と、それぞれへの最短の行き方。実行可能な半身は `e2e/grasp-stub.spec.js` にあり、
この表の各行に対応する検査が走る (文書だけが腐る事故を防ぐ — 原則 #19 Q3)。

---

## 触り方は 3 通り

| 誰が | どう起動するか | grasp の答えは誰が出すか |
|------|--------------|----------------------|
| レビュアー (インストール無し) | 配布された URL を開く | **スタブ** (GitHub Pages はスタブレーンでビルドされる — ADR-117) |
| 開発者 (UI を見たいだけ) | `pnpm dev:stub` | **スタブ** — Python も BFF も要らない |
| 当事者 (値を獲得する) | `pnpm dev:stack` | **本物** (BFF → コアAPI)。`README.md` の記録様式はこちら専用 |

> **スタブの数値を記録に採らないこと。** ランキング・距離・スコアはスタブの創作で、
> `core/` とは一致しない。スタブ経路では画面に橙色のバッジが常時出るので、それが
> 見えている間の値は既定値候補にならない。GSN の `DefaultsAreAcceptableToPractitioner`
> を支える証拠は `dev:stack` からしか採れない。

スタブが忠実に再現するのは**答えの形**だけ — 契約適合、ファネル恒等式
(`candidatesGenerated = 各段の棄却の和 + feasible`)、段の排他と順序、宣言の無い
camera / gripper が段を素通しにする規則、そして**評価できなかった objective は鍵ごと
出ない** (0 点として載せない — ADR-120)。UI が提示を導出しているのはこの 5 つなので、
ここだけは嘘をつかせない (`mocks/graspStub/conformance.test.js` が縛っている)。

---

## 最短経路 (S1)

```
起動 → Outliner で robot_base を選ぶ → n → 「Grasp candidates…」→ 掴む対象を選ぶ → Run
```

文書は 1 つも作らない。文脈が空なら starter (`cell_robotics`) が自動で採られる
(ADR-085)。**ADR-117 以前、この経路は候補 0 件でしか終われなかった** — request が
掴む対象の幾何を載せていなかったため。加えて starter 自身がロボットを宣言して
いなかったので Run は理由つきで disabled のままだった。両方この ADR で塞いである。

---

## シナリオ一覧

`?graspStub=<name>` で状態を指定する。**未宣言の名前は既定へ倒れず、画面上で拒否
される** (打ち間違いで「見ていない画面」の所見を書かせないため — 原則 #31/#11)。

| # | シナリオ | URL | 見るもの | 焼いている検査 |
|---|---------|-----|---------|--------------|
| S1 | 到達と成功 | `?graspStub=solve` (既定) | バックエンド無しで候補が並ぶこと。スタブバッジが出ていること | `grasp-stub.spec.js` S1 |
| S2 | 前提の未充足 | `solve` | 対象未選択のあいだ Run が **理由つきで** 閉じ、選んだ瞬間に開く | S2 |
| S3 | 全棄却 | `?graspStub=allRejected` | 5 段のファネルと 3 つの near-miss メーターが同時に出たときの版面 | S3 |
| S4 | 生成 0 件 | `?graspStub=empty` | 段の説明ではなく**入力の案内**に切り替わること | S4 |
| S5 | thin 結果 | `?graspStub=thin` | 「上位 5 件」の器に 1 件だけ入ったときに崩れないこと | S5 |
| S6 | 失敗の 3 種 | `?graspStub=error503` / `error502` / `error400` | 503/502/400 が**理由つき**で出ること (無言の失敗が無い) | S6 |
| S7 | 打ち間違い | `?graspStub=emtpy` | 既定へ倒れず、画面に拒否理由が出ること | S7 |
| S8 | 測っていない objective | `solve` (既定) | 重み付けしたのに**評価できなかった** objective が、0 のバーではなく「measured していない」として出ること (ADR-120)。フロントはリーチ範囲を集めていないので `reach_margin` が常にこの状態 | S8 |

`solve` だけが要求に反応する。ロボットを動かして Run し直すと reach 棄却が増減する
ので、**「置く → 届くか見る → 置き直す」ループはスタブでも回る** — 固定フィクスチャ
だけでは検証できない唯一のシナリオがこれ。

```bash
# シナリオ検査を実行する
VITE_GRASP_STUB=1 pnpm test:e2e -- grasp-stub
```

フラグ無しでは skip される (「走らなかった」と「通った」を見分けられるように — ADR-115)。

## 本物の判定エンジンで確かめる (S9 — `dev:stack` 専用)

S8 はスタブが「鍵ごと出さない」ことを見る。**実ソルバが同じ規律で答えるか**は
スタブ経路からは原理的に確認できない (生産者が違う) ので、ここだけは `dev:stack` が要る。
ADR-120 D1 を入れた回 (2026-08-14) の検証手順をそのまま残す。

### 起動

```bash
cd core && uv sync --extra dev --extra serve   # 初回のみ
pnpm dev:stack                                  # コアAPI(4001) + BFF(3001) + vite(5173)
```

3 つ全部が上がるまで待つ。コアAPI が落ちていると grasp は 503 になり、それは
S6 の画面であって S9 ではない (**503 を見て「測っていない」の検証をしたことにしない**)。

### 画面の手順 — フォームには何も入力しない

| # | 操作 | 期待 |
|---|------|------|
| 1 | `http://localhost:5173/easy-extrude/` を開く | 起動ホームが出る |
| 2 | ホームで **`cell_robotics` (Robot Cell)** を選ぶ (既にエディタに居るなら不要 — 文脈が空なら starter が自動で採られる) | シーンにロボットと箱が並ぶ |
| 3 | Outliner (左) で **`robot_base`** の行をクリック | 行が選択色になる |
| 4 | **`n`** キー | 右に N パネルが開く |
| 5 | **「Grasp candidates…」** をクリック | 把持探索パネルが開く |
| 6 | **掴む対象**のセレクタで箱を選ぶ (対象が 1 つなら自動で決まる) | 「Run grasp search」が押せるようになる |
| 7 | **「Run grasp search」** をクリック | 候補が並ぶ |

**フォーム入力は 1 つも要らない。** 重みは既定 (`reach weight` 0.6 /
`clearance weight` 0.4 / `stability weight` 1.0)、`topN` は 5 のまま。`vision` と
`gripper` のトグルは **off のまま**でよい (off = その段が空虚に真 — 宣言しないことが
既定の経路)。既定のまま走らせることがこの検証の要点で、**リーチ範囲を宣言しないのが
フロントの通常状態**だからである。

### 見るもの — 候補カード 1 枚の中

```
#1                                    score 0.943     ← ここ
[reach ✓] [IK ✓] [clear ✓]
approach_clearance  ▬▬▬▬▬▬▬▬░░  0.80
grasp_stability     ▬▬▬▬▬▬▬▬▬▬  1.00
reach_margin        (バーではなく「測っていない」の表示)   ← ここ
   not measured: reach_margin — weighted, but the solver had nothing to measure it against
```

(この例の score は `(0.4×0.80 + 1.0×1.00) / 1.4 = 0.943`。実際の値はシーンの幾何で
変わるが、**分母が 1.4 であること**は既定重みで走らせるかぎり変わらない。)

3 点を確認する:

1. **`reach_margin` に 0 のバーが描かれていないこと。** 行は消えず、スロットは残る
   (原則 #15 / #11 — 無言の省略にしない)。重み 0.6 を付けて Run したのだから、
   「その軸はどうなった」に答えがあるべきである。
2. **カード下の `not measured:` 行に `reach_margin` が名指しされていること。**
3. **`score` が 0.7 付近ではなく 1.0 付近であること。** ← D1 が効いた印。

### 数値の期待値 (実測 2026-08-14)

既定重みでリーチ範囲を宣言しない実行では、分母が **2.0 → 1.4** になる:

| | 旧 (D1 前) | 新 (D1 後) |
|---|---|---|
| 分母 | `0.6 + 0.4 + 1.0 = 2.0` | `0.4 + 1.0 = 1.4` (reach は測れないので入らない) |
| `reach_margin` の鍵 | 在る (値 `0.0`) | **無い** |
| 上のカード例の score | 0.660 | **0.943** |
| **全候補の倍率** | — | **1.4286 倍 (= 2.0 / 1.4)** — 分子が変わらないので厳密に定数倍 |
| 順位 | — | **不変** (同上) |

倍率だけが検証可能な不変量である (score の絶対値はシーンの幾何で変わる)。旧値を
実際に見たいなら `git stash` で差分を外して同じ手順を踏むのが確実。

**順位が変わらないことを「効いていない」と読まないこと。** この実行では
`reach_margin` が全候補で等しく測れないので、順位は数学的に変わりようがない。
順位が動くのは候補ごとに測れる軸が違うときで、それが起きるのは重心 (ADR-121) が
入ってからである。ここで確認しているのは**スコアの絶対値の比較可能性**であって
並び順ではない。

### 対照 — 宣言すれば測れることも見る

「測れなかった」が単なる欠落ではないことを確かめるには、宣言した側と対照する。
UI にリーチ範囲の入力欄は無い (**それ自体が現状の限界** — §既知の限界) ので、
対照は API で採る:

```bash
curl -s localhost:4001/grasp-search -H 'content-type: application/json' \
  -d '{"contractVersion":5,"layoutVersion":"layout/1.0","graspSearch":{
       "robot":{"base":[0,0,0],"reachMin":0.5,"reachMax":1.5},
       "target":{"surfaceSamples":[{"point":[1,0,0],"normal":[1,0,0]}]},
       "objectiveWeights":{"reach_margin":0.6,"grasp_stability":1.0},"topN":1}}' \
  | grep -o '"objectiveScores":{[^}]*}'
```

`reachMin`/`reachMax` を**消すと** `reach_margin` の鍵が消え、**書くと**現れる。
鍵の有無が宣言の有無に一致することが、この ADR の主張そのものである
(`core/tests/test_engine.py` が同じ対照を焼いている)。

### 記録するとき

このシナリオで採った score は**既定値候補にならない** (リーチ範囲が未宣言のままなので、
「この設定でこの点数」は片肺の測定である)。記録するのは値ではなく
**「測っていないことが画面で読めたか」** の一点。値の獲得は ADR-119 / 121 で
入力が揃ってからになる。

## 観察の焦点

各シナリオで、値そのものより**次の 3 つ**を書き留める (`README.md` の記録様式へ):

1. **どこで手が止まったか。** 止まった事実を記録する — 回避できたことは改善不要の
   証拠にならない (`README.md` の規律をそのまま適用)。
2. **理由が読めたか。** disabled な Run、0 件の結果、502 — どれも理由が画面にあるはず。
   理由を探して devtools を開いたなら、それは原則 #11 の違反として記録する。
3. **次に何をすればいいか分かったか。** 「reach で 9 件落ちた」の次に手が動くか。
   動かないなら、それはファネルが事実を出しているのに提示が仕事をしていない。

## 既知の限界 (スタブのせいではなく、製品の現状)

この 3 つはスタブ経路でも `dev:stack` でも同じように見える。**シナリオを回すと必ず
目に入る**ので、先に名前を付けておく:

- **リーチ範囲が宣言されない。** パネルは `plan.reachMin/reachMax` を集めないので、
  `core/` は `reach_max = ∞` を使う。結果として reach 段はほぼ棄却せず、
  **`reach_margin` は「測っていない」として毎回落ちる** (2026-08-14 / ADR-120 D1 まで
  「常に 0」だった — 0 点として分母に居座り、全候補のスコアを押し下げていた)。
  「届くか」を問うている画面が、実は届かないことがない設定で動いている状況は変わって
  いない。**変わったのは、その事実が画面で読めるようになったこと**である。
  S3 が全棄却を*固定シナリオ*として持っているのはこのためで、
  `solve` から自然に全棄却へ行くにはロボットを遠くへ置くしかない。
- **対象の幾何は文書由来で、シーン由来ではない。** `robot.base` はシーンの
  ワールド姿勢 (`worldPoseOf`) から解決されるのに、掴む対象は Layout DSL から
  解決される。ビューポートでソリッドを動かしても、文書を作り直すまで対象は動かない。
  どちら側が対象幾何を所有するかは ADR が要る判断なので、ここでは非対称を**明示**する
  に留めてある (`GraspController._graspTargets` の doc コメントに同じ注記)。
- **面はハンドの種別からしか決まらない。** サンプルする面は宣言されたハンドが決める
  (`FACES_BY_GRIPPER_KIND` — ジョーは対向 2 面、吸引は上面。ADR-118 D3。**それ以前は
  種別によらず上面 9 点だけ**で、対象幅が半分に見えていた)。ユーザーが「ここを掴んで
  ほしい」と*場所*を指す手段は依然として無い — それは ADR-119 D2 の担当。どの面が
  掴めるかを解くのは解法側なので、フロントは面を*宣言*するに留める
  (境界は CLAUDE.md のとおり)。
