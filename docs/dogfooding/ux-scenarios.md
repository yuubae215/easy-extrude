# Grasp Search — UX 検証シナリオ

**目的:** grasp-search の UX を、バックエンド無しで・最短で・再現可能に検証する。

記録様式と既定値獲得の作法は `README.md`。この文書はその**前段** — 「何を見に行くか」
の一覧と、それぞれへの最短の行き方。実行可能な半身は `e2e/grasp-stub.spec.js` にあり、
この表の各行に対応する検査が走る (文書だけが腐る事故を防ぐ — 原則 #19 Q3)。

---

## 触り方は 3 通り

| 誰が | どう起動するか | grasp の答えは誰が出すか |
|------|--------------|----------------------|
| レビュアー (インストール無し) | 配布された URL を開く | **スタブ** (GitHub Pages はスタブレーンでビルドされる — ADR-117) |
| 開発者 (UI を見たいだけ) | `pnpm dev:stub` | **スタブ** — Python も BFF も要らない |
| 当事者 (値を獲得する) | `pnpm dev:stack` | **本物** (BFF → コアAPI)。`README.md` の記録様式はこちら専用 |

> **スタブの数値を記録に採らないこと。** ランキング・距離・スコアはスタブの創作で、
> `core/` とは一致しない。スタブ経路では画面に橙色のバッジが常時出るので、それが
> 見えている間の値は既定値候補にならない。GSN の `DefaultsAreAcceptableToPractitioner`
> を支える証拠は `dev:stack` からしか採れない。

スタブが忠実に再現するのは**答えの形**だけ — 契約適合、ファネル恒等式
(`candidatesGenerated = 各段の棄却の和 + feasible`)、段の排他と順序、宣言の無い
camera / gripper が段を素通しにする規則、そして**評価できなかった objective は鍵ごと
出ない** (0 点として載せない — ADR-120)。UI が提示を導出しているのはこの 5 つなので、
ここだけは嘘をつかせない (`mocks/graspStub/conformance.test.js` が縛っている)。

---

## 最短経路 (S1)

```
起動 → Outliner で robot_base を選ぶ → n → 「Grasp candidates…」→ 掴む対象を選ぶ → Run
```

文書は 1 つも作らない。文脈が空なら starter (`cell_robotics`) が自動で採られる
(ADR-085)。**ADR-117 以前、この経路は候補 0 件でしか終われなかった** — request が
掴む対象の幾何を載せていなかったため。加えて starter 自身がロボットを宣言して
いなかったので Run は理由つきで disabled のままだった。両方この ADR で塞いである。

## シナリオ一覧

`?graspStub=<name>` で状態を指定する。**未宣言の名前は既定へ倒れず、画面上で拒否
される** (打ち間違いで「見ていない画面」の所見を書かせないため — 原則 #31/#11)。

| # | シナリオ | URL | 見るもの | 焼いている検査 |
|---|---------|-----|---------|--------------|
| S1 | 到達と成功 | `?graspStub=solve` (既定) | バックエンド無しで候補が並ぶこと。スタブバッジが出ていること | `grasp-stub.spec.js` S1 |
| S2 | 前提の未充足 | `solve` | 対象未選択のあいだ Run が **理由つきで** 閉じ、選んだ瞬間に開く | S2 |
| S3 | 全棄却 | `?graspStub=allRejected` | 5 段のファネルと 3 つの near-miss メーターが同時に出たときの版面 | S3 |
| S4 | 生成 0 件 | `?graspStub=empty` | 段の説明ではなく**入力の案内**に切り替わること | S4 |
| S5 | thin 結果 | `?graspStub=thin` | 「上位 5 件」の器に 1 件だけ入ったときに崩れないこと | S5 |
| S6 | 失敗の 3 種 | `?graspStub=error503` / `error502` / `error400` | 503/502/400 が**理由つき**で出ること (無言の失敗が無い) | S6 |
| S7 | 打ち間違い | `?graspStub=emtpy` | 既定へ倒れず、画面に拒否理由が出ること | S7 |
| S8 | 測っていない objective | `solve` (既定) | 重み付けしたのに**評価できなかった** objective が、0 のバーではなく「measured していない」として出ること (ADR-120)。フロントはリーチ範囲を集めていないので `reach_margin` が常にこの状態 | S8 |

`solve` だけが要求に反応する。ロボットを動かして Run し直すと reach 棄却が増減する
ので、**「置く → 届くか見る → 置き直す」ループはスタブでも回る** — 固定フィクスチャ
だけでは検証できない唯一のシナリオがこれ。

```bash
# シナリオ検査を実行する
VITE_GRASP_STUB=1 pnpm test:e2e -- grasp-stub
```

フラグ無しでは skip される (「走らなかった」と「通った」を見分けられるように — ADR-115)。

## 観察の焦点

各シナリオで、値そのものより**次の 3 つ**を書き留める (`README.md` の記録様式へ):

1. **どこで手が止まったか。** 止まった事実を記録する — 回避できたことは改善不要の
   証拠にならない (`README.md` の規律をそのまま適用)。
2. **理由が読めたか。** disabled な Run、0 件の結果、502 — どれも理由が画面にあるはず。
   理由を探して devtools を開いたなら、それは原則 #11 の違反として記録する。
3. **次に何をすればいいか分かったか。** 「reach で 9 件落ちた」の次に手が動くか。
   動かないなら、それはファネルが事実を出しているのに提示が仕事をしていない。

## 既知の限界 (スタブのせいではなく、製品の現状)

この 3 つはスタブ経路でも `dev:stack` でも同じように見える。**シナリオを回すと必ず
目に入る**ので、先に名前を付けておく:

- **リーチ範囲が宣言されない。** パネルは `plan.reachMin/reachMax` を集めないので、
  `core/` は `reach_max = ∞` を使う。結果として reach 段はほぼ棄却せず、
  `reach_margin` は常に 0。「届くか」を問うている画面が、実は届かないことがない設定で
  動いている。S3 が全棄却を*固定シナリオ*として持っているのはこのためで、
  `solve` から自然に全棄却へ行くにはロボットを遠くへ置くしかない。
- **対象の幾何は文書由来で、シーン由来ではない。** `robot.base` はシーンの
  ワールド姿勢 (`worldPoseOf`) から解決されるのに、掴む対象は Layout DSL から
  解決される。ビューポートでソリッドを動かしても、文書を作り直すまで対象は動かない。
  どちら側が対象幾何を所有するかは ADR が要る判断なので、ここでは非対称を**明示**する
  に留めてある (`GraspController._graspTargets` の doc コメントに同じ注記)。
- **上面しかサンプルしない。** 宣言できるのは「箱の上面のグリッド 9 点」で、
  側面把持や斜めの面は表現できない。どの面が掴めるかを選ぶのは解法側の問いなので、
  フロントは面を*宣言*するに留める (境界は CLAUDE.md のとおり)。
